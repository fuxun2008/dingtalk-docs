#### Langkah 4: Permintaan mandiri untuk melewati pemeriksaan Keamanan otomatis

1. Untuk melewati pemeriksaan otomatis, konfigurasikan "Events & callbacks" sebagai berikut:

**Langkah 1**: Untuk enkripsi Aes_key, enkripsikan **systemToken** Yida dengan metode **decrypt** di bawah dan atur hasilnya.

```text
private static final char[] HEX_ARRAY = "0123456789abcdef".toCharArray();

public static String bytesToHex(byte[] bytes) {
        char[] hexChars = new char[bytes.length * 2];
        for (int i = 0; i < bytes.length; i++) {
            int v = bytes[i] & 0xFF;
            hexChars[i * 2] = HEX_ARRAY[v >>> 4];
            hexChars[i * 2 + 1] = HEX_ARRAY[v & 0x0F];
        }
        return new String(hexChars);
    }

private static String decrypt(String input) throws NoSuchAlgorithmException {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        byte[] hash = digest.digest(input.getBytes(StandardCharsets.UTF_8));
        // Konversi hash menjadi string terenkripsi 43 karakter
        return bytesToHex(hash).substring(0, 43);
}
```

Ambil systemToken Yida dari Pengaturan aplikasi Yida > Deployment & Operations.

**Langkah 2**: Tanda tangan Token adalah systemToken Yida di atas.

**Langkah 3**: URL Permintaan Callback (https://www.yidaapps.com/saasAppCallback/\{appKey}), dengan appKey adalah kode aplikasi Yida, misalnya "APP_XXX."

2. Lengkapi konten "Security review" pada pemeriksaan otomatis aplikasi. Untuk evaluasi penerimaan Keamanan, lihat 📎Panduan penerimaan Keamanan Yida Cool SaaS - ISV.pdf.

### 4.3 Manajemen organisasi Uji Coba

Gunakan manajemen organisasi Uji Coba untuk pengujian mandiri ISV pada aplikasi utama dan Cool App, baik dalam status dipublikasikan maupun belum dipublikasikan. Setelah pengujian mandiri berhasil, kirim aplikasi untuk dipublikasikan ke DingTalk App Center dan Cool App Marketplace.

<Steps>
  <Step title="Langkah 1">
    Pilih Versi aplikasi SaaS, klik "Trial organization management," dan pilih organisasi Uji Coba. Jika belum ada, klik "Buat" untuk masuk ke Open Platform dan membuatnya.
  </Step>
  <Step title="Langkah 2">
    Setelah organisasi Uji Coba dibuat, tautkan dan berikan otorisasi pada Versi aplikasi yang ingin diuji. Setelah Otorisasi berhasil, aplikasi akan muncul di Workbench > Ungrouped pada organisasi Uji Coba tersebut.
  </Step>
</Steps>

#### 4.3.1 Uji Coba aplikasi utama

<Steps>
  <Step title="Langkah 1">
    Akses aplikasi dari workbench. Jika penguji Uji Coba bukan "Admin Kontak" atau "Super Admin aplikasi," minta admin organisasi atau admin aplikasi memberikan akses ke backend aplikasi.
  </Step>
  <Step title="Setelah Anda memiliki akses ke backend Kelola Aplikasi, tinjau konfigurasi backend aplikasi SaaS yang berlangganan. Fitur tertentu dapat dimodifikasi.">
  </Step>
</Steps>

**Semua fitur berikut dapat dimodifikasi:**

> Logika umum: Setelah modifikasi dilakukan dan ISV kemudian merilis Versi baru, konfigurasi lokal pelanggan diutamakan untuk fitur yang terpengaruh. Perubahan pada aplikasi utama tidak disinkronkan turun ke aplikasi anak. Jika tidak ada modifikasi, perubahan sumber daya Inkremental di aplikasi utama disinkronkan ke aplikasi anak.
>
> Logika perubahan Proses persetujuan:
>
> 1. Jika aplikasi anak berlangganan V0 dan aplikasi utama memiliki V1 yang belum dipublikasikan, V1 tidak muncul di Riwayat Versi aplikasi anak.
> 2. Jika aplikasi anak berlangganan V0 tanpa kustomisasi dan aplikasi utama kemudian diperbarui ke V1, aplikasi anak tetap menampilkan dan berjalan pada V0 yang berlangganan.
> 3. Jika aplikasi anak berlangganan V0 dan mengkustomisasinya, Versi Riwayat V0 internal dibuat bersama dengan draf V1. Setelah aplikasi anak berlangganan Versi baru, proses saat ini tidak lagi mengikuti peningkatan aplikasi utama.
> 4. Cakupan Versi di atas mencakup semua aturan bisnis dan formula di dalam Versi.

3. Secara default, data formulir "Data bisnis dasar" dari aplikasi utama diteruskan ke aplikasi anak sehingga data dasar langsung dapat digunakan. Modifikasi juga didukung.

## 5 Operasional aplikasi

### 5.1 Peningkatan Versi

Setelah aplikasi SaaS yang dibangun ISV dipublikasikan ke App Marketplace dan pelanggan berlangganan, ISV dapat melakukan iterasi fitur dan, di "Workbench pengembangan SaaS Yida > Pengaturan aplikasi > Remote operations," meluncurkan peningkatan Versi ke organisasi tertentu satu per satu maupun secara massal.

Catatan fitur:

1. Secara default, opsi peningkatan adalah iterasi terbaru yang dirilis setelah Versi yang saat ini dipublikasikan.
2. Peningkatan Versi massal ke beberapa organisasi berbayar didukung.

> Remote operations — segera hadir.

### 5.2 Halaman landing Otorisasi aktivasi aplikasi

Setelah aplikasi SaaS Yida dipublikasikan ke DingTalk Open Platform dan App Center, Anda dapat mengkustomisasi halaman landing Otorisasi. 👉[Pelajari lebih lanjut](https://open.dingtalk.com/document/isvapp/1-product-interaction-process)

Catatan konfigurasi:

- Unggah halaman landing Otorisasi PC dan mobile secara terpisah (hanya satu Gambar per Saluran yang didukung).

- Setelah pengunggahan, salin "URL akses Uji Coba" lalu buka Partner Self-Operation Platform > Aplikasi perusahaan pihak ketiga > Manajemen publikasi produk > Detail aplikasi > Kelola > "In-app authorization settings." Setelah integrasi selesai dan penerimaan mandiri Anda lulus (👉 pelajari lebih lanjut tentang proses penerimaan), aplikasi SaaS dapat dipromosikan di lebih banyak Saluran online DingTalk, seperti DingTalk Search.
