DingTalk Open Platform menyediakan serangkaian kemampuan yang kaya, termasuk Open API serta channel pesan Webhook & Stream. Artikel ini membagikan praktik dan rekomendasi untuk membantu developer mengoptimalkan penggunaan sumber daya.

## Praktik terbaik untuk penggunaan sumber daya yang efisien

Pada beberapa skenario bisnis, sebuah fitur aplikasi dapat diimplementasikan baik dengan memanggil Open API maupun dengan mendengarkan push peristiwa. Misalnya, untuk memperoleh informasi perubahan tentang pengguna yang ditambahkan ke sebuah obrolan grup, Anda dapat melakukan polling Open API atau mendengarkan push peristiwa dan memicu tindakan terkait hanya saat diperlukan. Pertimbangkan faktor-faktor berikut untuk menentukan pilihan yang paling sesuai.

- **Kebutuhan real-time**—Jika aplikasi Anda perlu memperoleh data atau memproses peristiwa secara real time, Langganan peristiwa mungkin merupakan pilihan yang lebih baik.
- **Frekuensi pembaruan data**—Jika data sering diperbarui dan mengonsumsi lebih banyak sumber daya, Langganan peristiwa mungkin merupakan pilihan yang lebih baik. Jika Anda hanya perlu memperoleh data secara terjadwal atau sesekali, memanggil Open API mungkin merupakan pilihan yang lebih baik.
- **Kompleksitas integrasi**—Jika fitur yang Anda kembangkan kompleks dan memerlukan pemanggilan beberapa Open API, biaya pengembangan akan meningkat. Pertimbangkan apakah mengintegrasikan push peristiwa dapat mengurangi upaya pengembangan.
- **Volume data yang diambil**—Jika satu kali pengambilan mengembalikan data dalam jumlah besar, push peristiwa mungkin merupakan pilihan yang lebih baik. Memanggil Open API mengonsumsi bandwidth jaringan dan sumber daya server. Jika aplikasi Anda memanggil Open API secara sering, hal itu dapat memengaruhi performa sistem dan konsumsi sumber daya, sedangkan push peristiwa dapat mengurangi konsumsi sumber daya.

## Praktik terbaik untuk mengoptimalkan sumber daya push peristiwa

DingTalk Open Platform menyediakan push peristiwa, yang memungkinkan developer menerima notifikasi real-time saat peristiwa tertentu terjadi. Namun, berlangganan terlalu banyak peristiwa atau memproses terlalu banyak Notifikasi pesan dapat menurunkan performa aplikasi dan meningkatkan konsumsi sumber daya.

- **Berlangganan hanya peristiwa yang diperlukan**—Identifikasi peristiwa yang benar-benar dibutuhkan aplikasi Anda, hindari berlangganan tipe peristiwa yang tidak relevan, dan kurangi jumlah peristiwa yang dilanggan.
- **Deduplikasi peristiwa dalam logika bisnis Anda**—Pada beberapa kasus, sebuah Callback peristiwa bisnis dapat menerima peristiwa duplikat. Developer harus menangani peristiwa dengan eventId yang sama secara idempoten.
- **Merespons dengan cepat**—Batas waktu push DingTalk Open Platform adalah 2,5 detik (mode HTTP) / 3 detik (mode Stream). Kami menyarankan untuk memproses pesan secara tepat waktu dan mengembalikan Respons yang benar secara real time guna menghindari timeout yang dikembalikan ke DingTalk Open Platform, sehingga mengurangi frekuensi percobaan ulang akibat timeout.

## Kontrol penggunaan untuk Webhook bot grup

Saat ini dua skenario bot Webhook grup didukung untuk kontrol penggunaan:

|  |  |
| --- | --- |
| Bot kustom grup | Cari dan tambahkan bot [Aplikasi internal], lalu push pesan menggunakan Webhook |

### Prosedur

1. Buka Developer Console > [Manajemen Sumber Daya](https://open-dev.dingtalk.com/?spm=dd_developers.header.unLogin.openDevBtn&hash=%23%2F#/), gulir ke kartu **Penggunaan Webhook & Stream**, lalu klik **Kontrol Penggunaan**.

2. Anda dapat mengatur batas Webhook bot grup pada dialog Kontrol Penggunaan.

   **Catatan**

   Saat menyetel kontrol penggunaan, pilih **Batas Global** atau **Batas Tertarget** berdasarkan kebutuhan aktual Anda. Untuk detail tentang kedua tipe batas tersebut, lihat penjelasan di bawah ini.

### Penjelasan

- **[Batas Global]**—Setelah disetel, semua "Webhook bot internal di obrolan grup" dan "Webhook Bot kustom grup" dibatasi secara seragam, dengan penggunaan dibatasi per masing-masing bot.

  - Skenario: Anggota sering membuat Webhook bot grup di obrolan secara mandiri, sehingga mengonsumsi Kuota Webhook organisasi, dan Anda ingin mengontrol hal ini.
  - Solusi: Setel batas global sehingga setiap Webhook bot yang dibuat di obrolan grup dapat melakukan paling banyak 100 panggilan per bulan, mengatasi kurangnya kontrol.
- **[Batas Tertarget]**—Memungkinkan Anda menetapkan aturan batas khusus untuk bot tertentu. Setelah disetel, aturan ini menggantikan konfigurasi batas global.

  - Skenario: Setelah batas global membatasi bot anggota lain, beberapa bot grup yang dibangun oleh IT perlu melampaui batas penggunaan.
  - Solusi: Setel batas tertarget. Pilih Bot kustom Webhook yang dibangun IT di obrolan grup dan setel menjadi tanpa batas (atau setel Kuota besar).
