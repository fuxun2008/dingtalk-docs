# Integrasi persetujuan cepat untuk sistem pihak ketiga: Persetujuan satu klik di Pusat To-Do dan kartu pesan

## Ikhtisar

Solusi ini ditujukan bagi organisasi yang tugas persetujuannya tersebar di berbagai sistem bisnis. Solusi ini juga cocok bagi manajer yang ingin menangani persetujuan pihak ketiga tanpa meninggalkan DingTalk. Pusat Proses Persetujuan OA menyediakan API persetujuan cepat kustom dan mekanisme callback. Sistem bisnis pihak ketiga menggunakannya untuk menyinkronkan tugas persetujuan ke Pusat Persetujuan DingTalk. Tombol persetujuan cepat kustom kemudian muncul di daftar Pusat To-Do dan pada kartu pesan Persetujuan OA. Saat penyetuju mengklik tombol, DingTalk memanggil callback ke sistem pihak ketiga. Sistem tersebut memperbarui status tugas dan menyinkronkannya kembali ke Pusat Persetujuan DingTalk. Penyetuju mendapatkan pengalaman persetujuan terpadu yang mulus.

### Latar belakang

Organisasi menghasilkan banyak tugas persetujuan di sistem bisnis pihak ketiga, seperti sistem pengendalian biaya, pengadaan, dan HR. Karyawan harus masuk ke setiap sistem dan menangani tugas satu per satu. Prosesnya panjang dan tidak efisien. Solusi ini menghubungkan persetujuan pihak ketiga ke Pusat To-Do DingTalk dan mendukung persetujuan satu klik di kartu pesan. Karyawan menangani semua persetujuan di satu tempat di DingTalk, tanpa beralih ke sistem asal.

Organisasi umumnya menghadapi kendala berikut:

- **Masuk berulang ke berbagai sistem:** Setiap hari karyawan masuk ke 5+ sistem bisnis untuk menangani persetujuan. Setiap persetujuan memakan rata-rata 3 menit, sehingga lebih dari 40 menit terbuang per hari.
- **Progres persetujuan tidak transparan:** Setelah mengajukan persetujuan, karyawan tidak dapat memantau statusnya secara real-time di DingTalk. Mereka harus berulang kali masuk ke sistem asal untuk mengecek, dan tindak lanjut bergantung pada komunikasi manual.
- **Pengalaman persetujuan seluler yang buruk:** Sebagian besar sistem pihak ketiga tidak dioptimalkan untuk perangkat seluler. Karyawan yang sedang dinas atau bekerja dari rumah tidak dapat menangani persetujuan mendesak tepat waktu, sehingga bisnis tertunda.
- **Data persetujuan sulit dihimpun:** Metrik seperti volume persetujuan dan rata-rata waktu pemrosesan per departemen tersebar di berbagai sistem. Manajer tidak dapat memperoleh gambaran menyeluruh di DingTalk.

### Nilai utama

Solusi ini memberikan nilai di tiga area:

- **Persetujuan satu klik:** Tombol persetujuan cepat dari sistem pihak ketiga tampil langsung di daftar Pusat To-Do DingTalk dan pada kartu pesan Persetujuan OA. Penyetuju menyelesaikan persetujuan sederhana tanpa beralih ke sistem bisnis.
- **Sinkronisasi tertutup (closed-loop):** Saat penyetuju mengklik tombol cepat, DingTalk memanggil callback ke sistem pihak ketiga untuk memperbarui status tugas. Sistem pihak ketiga kemudian menyinkronkan status terbaru kembali ke Pusat Persetujuan DingTalk, sehingga siklus data lengkap.
- **Kustomisasi fleksibel:** Sistem pihak ketiga dapat menyesuaikan label, ikon, dan kondisi tampilan tombol cepat. Konfigurasikan aksi cepat yang berbeda untuk jenis persetujuan yang berbeda sesuai kebutuhan bisnis.

### Kasus penggunaan

Solusi ini cocok untuk organisasi dengan sumber persetujuan yang beragam dan proporsi persetujuan sederhana yang tinggi. Kasus penggunaan umum meliputi:

- **Persetujuan terpadu untuk eksekutif:** Eksekutif seperti CEO dan CFO menangani persetujuan dari berbagai sistem pihak ketiga setiap hari. Banyak di antaranya berupa konfirmasi sederhana yang ingin mereka selesaikan dengan satu klik di DingTalk, tanpa berganti sistem.
- **Persetujuan ringan berfrekuensi tinggi:** Persetujuan seperti konfirmasi penggantian biaya, perpanjangan cuti, dan permintaan absen susulan sering terjadi dan sederhana. Penyetuju dapat menanganinya langsung di daftar To-Do.
- **Persetujuan instan dari kartu pesan:** Setelah menerima notifikasi kartu pesan Persetujuan OA, penyetuju menyelesaikan persetujuan langsung di kartu tanpa membuka halaman detail.

## Skenario bisnis umum

### Skenario 1: Persetujuan operasional cepat untuk jaringan hotel (perhotelan dan pariwisata)

#### Kendala

Sebuah jaringan hotel nasional mengoperasikan 80+ properti. Jaringan ini menggunakan PMS internal untuk persetujuan pemesanan kamar, sistem pengadaan untuk persetujuan permintaan perlengkapan, serta sistem HR untuk penjadwalan shift staf dan cuti pengganti. Tugas persetujuan berjalan terpisah di ketiga sistem tersebut. Direktur operasional grup dan manajer toko menangani banyak persetujuan setiap hari. Proses yang ada memiliki masalah berikut:

- **Persetujuan sederhana memakan waktu:** Volume persetujuan harian melebihi 60, dan 40% di antaranya merupakan aksi sederhana seperti konfirmasi overbooking dan konfirmasi pengisian ulang stok. Setiap tugas mengharuskan masuk ke PMS atau sistem pengadaan, mencari tugas, lalu mengklik Terima, dengan waktu rata-rata 2 menit.
- **Pengalaman seluler yang buruk:** Manajer toko menangani persetujuan di ponsel saat inspeksi properti. Mereka mengklik tautan di pesan DingTalk untuk membuka halaman seluler PMS, yang lambat dimuat dan sulit digunakan. Respons yang terlambat terhadap konfirmasi overbooking mendesak menurunkan pengalaman tamu.
- **Tidak ada aksi di kartu pesan:** Saat kartu pesan "Overbooking kamar perlu dikonfirmasi" masuk, manajer hanya dapat mengklik untuk melihat detail. Mereka tidak dapat mengonfirmasi langsung di kartu dan kehilangan momen terbaik untuk mengoordinasikan pemindahan kamar.

#### Validasi nilai

- **Alur kerja otomatis**

  Integrasi mengikuti alur lima langkah:

  1. **Integrasi multisistem** – hubungkan Persetujuan OA resmi, PMS, HR, dan sistem pengadaan.
  2. **Tampilan To-Do terpadu** – daftar To-Do terpadu dengan filter berdasarkan sistem sumber.
  3. **Registrasi tombol cepat** – konfigurasikan aksi Konfirmasi/Tolak beserta callback-nya.
  4. **Persetujuan di kartu** – bertindak langsung di kartu tanpa membuka halaman detail.
  5. **Sinkronisasi status tertutup** – Callback peristiwa menjaga konsistensi data antarsistem.

  Kartu Persetujuan OA menampilkan kolom **Pemohon**, **Waktu Pengajuan**, **Jumlah**, dan **Alasan**, serta tombol tersemat **Setujui**, **Tolak**, dan **Lainnya**.
- **Keunggulan utama**

  - **Efisiensi satu klik:** Persetujuan konfirmasi sederhana berkurang dari 2 menit menjadi 5 detik, menghemat 40 menit per hari. Waktu respons konfirmasi overbooking turun dari 15 menit menjadi 30 detik.
  - **Ramah seluler:** Manajer toko menyetujui langsung dari daftar To-Do DingTalk di ponsel, tanpa membuka halaman seluler PMS. Mereka menangani overbooking mendesak secara real-time saat inspeksi.
  - **Aksi langsung di kartu:** Tombol cepat tersemat di kartu pesan Persetujuan OA. Manajer mengonfirmasi langsung di kartu saat notifikasi overbooking masuk dan tidak pernah melewatkan momen untuk mengoordinasikan pemindahan kamar.

### Skenario 2: Integrasi persetujuan multipihak untuk proyek konstruksi besar (konstruksi dan rekayasa)

#### Kendala

Sebuah perusahaan konstruksi besar menjalankan 15 proyek secara bersamaan. Perusahaan ini menggunakan sistem manajemen proyek internal untuk persetujuan progres konstruksi, sistem material untuk persetujuan inspeksi pengiriman material, dan sistem keselamatan untuk persetujuan inspeksi serta perbaikan bahaya. Ketiga proses persetujuan berjalan sendiri-sendiri. Manajer proyek dan direktur keselamatan menangani banyak persetujuan setiap hari. Proses yang ada memiliki masalah berikut:

- **Persetujuan di lapangan tidak praktis:** Manajer proyek bekerja di lokasi. Saat sinyal seluler tidak stabil, halaman seluler sistem manajemen proyek lambat dimuat. Konfirmasi pengiriman material yang tertunda memperlambat konstruksi.
- **Respons lambat terhadap bahaya keselamatan:** Saat petugas keselamatan menemukan bahaya, mereka mengajukan persetujuan perbaikan. Direktur keselamatan harus membuka halaman detail dari kartu pesan untuk melihat foto dan lokasi bahaya sebelum memutuskan. Proses tradisional terlalu lama, dan melewatkan momen perbaikan terbaik dapat menyebabkan kecelakaan.
- **Kolaborasi multipihak tidak efisien:** Satu persetujuan inspeksi material memerlukan konfirmasi dari departemen proyek, departemen material, dan pihak pengawas, masing-masing di sistem terpisah. Koordinasi memakan waktu hingga 2 hari.

#### Validasi nilai

- **Alur kerja otomatis**

  Alur integrasi terdiri atas lima tahap:

  1. **Akses multisistem** — hubungkan sistem proyek, material, dan keselamatan ke DingTalk.
  2. **Tampilan To-Do terpadu** — item tertunda dari semua sumber muncul di satu **Pusat To-Do** terpadu, dapat difilter berdasarkan **Semua**, **Proyek**, **Material**, dan **Keamanan**.
  3. **Registrasi tombol aksi cepat** — konfigurasikan tombol untuk aksi penerimaan, pemeriksaan ulang, dan perbaikan.
  4. **Setujui langsung dari kartu** — bertindak di kartu Persetujuan OA tanpa membuka halaman detail, menggunakan tombol **Setujui**, **Tolak**, dan **Lainnya**.
  5. **Sinkronisasi status real-time** — Callback peristiwa menjaga konsistensi data sistem sumber.

  Kartu persetujuan menampilkan judul permintaan, **Sumber**, pemohon, waktu pengiriman, dan konten.
- **Keunggulan utama**

  - **Efisiensi di lapangan:** Konfirmasi inspeksi material berkurang dari 3 menit menjadi 5 detik. Meski sinyal di lokasi lemah, manajer tetap dapat menyelesaikannya dengan cepat di DingTalk dan menghindari keterlambatan konstruksi.
  - **Respons keselamatan lebih cepat:** Persetujuan perbaikan bahaya ditangani langsung dari kartu pesan. Waktu respons turun dari 1 jam menjadi 5 menit, sehingga mengurangi risiko insiden keselamatan.
  - **Kolaborasi tertutup:** Persetujuan konfirmasi multipihak menggunakan tombol cepat dan callback untuk menyinkronkan status secara real-time. Waktu koordinasi turun dari 2 hari menjadi 4 jam.

## Panduan implementasi

### Arsitektur teknis

Arsitektur teknis mencakup komponen inti berikut:

- **Lapisan autentikasi:** Mengelola kredensial aplikasi dan memperoleh access token untuk memverifikasi identitas setiap panggilan API.
- **Lapisan sinkronisasi templat:** Memanggil API untuk menyimpan templat persetujuan terintegrasi eksternal di Pusat Proses. Lapisan ini menyinkronkan templat persetujuan dari sistem bisnis pihak ketiga ke Pusat Persetujuan DingTalk dan memperoleh kode templat unik `processCode`.
- **Lapisan pembuatan tugas:** Memanggil API untuk membuat atau memperbarui tugas To-Do persetujuan. Lapisan ini menyinkronkan tugas persetujuan dari sistem pihak ketiga ke Pusat Persetujuan DingTalk serta mendaftarkan tombol persetujuan cepat kustom dan URL callback.
- **Lapisan penanganan callback:** Sistem pihak ketiga menyediakan API callback HTTPS. API ini menerima callback persetujuan cepat dari DingTalk, memperbarui status tugas lokal, dan menyinkronkan status terbaru kembali ke Pusat Persetujuan DingTalk untuk melengkapi siklus data.
- **Lapisan Callback peristiwa:** Memantau peristiwa perubahan status tugas persetujuan untuk menjaga konsistensi antara sistem pihak ketiga dan Pusat Persetujuan DingTalk.

### Prasyarat

- **Persiapan aplikasi:** Selesaikan proses [pembuatan dan konfigurasi aplikasi](/id/open/dingstart/create-application).
- **Persyaratan izin:** Miliki izin Admin Organisasi atau Sub Admin DingTalk, lalu ajukan izin API berikut:

  - `qyapi_aflow` (izin pengelolaan data alur persetujuan)
  - `Workflow.Form.Write` (izin tulis templat alur kerja)
  - `Workflow.Form.Read` (izin baca templat alur kerja)
  - `Workflow.Instance.Write` (izin tulis instans alur kerja)
  - `Premium.Workflow.ReadWrite.All` (izin baca/tulis alur kerja Persetujuan OA, khusus OA Edisi Premium)
- **Lingkungan pengembangan:** Instal lingkungan pengembangan Java (JDK 1.6 atau lebih baru) dan alat build Maven.
- **Persiapan SDK:** Unduh SDK Sisi server DingTalk, tersedia untuk Java, Python, Go, dan bahasa lainnya.
- **Persiapan gateway:** Daftarkan API callback sistem pihak ketiga sebagai gateway di "Manajemen Sumber Data" DingTalk. Untuk detailnya, lihat Sumber Data.

### Implementasi kode

Langkah 1: Buka halaman detail aplikasi, lalu dapatkan Client ID dan Client Secret aplikasi.

Langkah 2: Ajukan izin API. Ajukan izin "Persetujuan OA" yang relevan.

Langkah 3: Dapatkan kredensial akses aplikasi. Lihat [Mendapatkan access token aplikasi internal](/id/open/development/obtain-the-access-token-of-an-internal-app). Saat memanggil API, gunakan access token untuk mengautentikasi pemanggil.

Langkah 4: Panggil API inti:

1. Daftarkan API callback untuk tombol persetujuan cepat kustom. Semua callback gateway ke API data di luar DingTalk wajib didaftarkan sebagai gateway di "Manajemen Sumber Data". Untuk detailnya, lihat Sumber Data.
2. Panggil Server API baru untuk menyimpan templat persetujuan terintegrasi eksternal di Pusat Proses guna memperoleh kode templat unik `processCode`.
3. Jika Anda tidak menyimpan `processCode`, panggil API [Mendapatkan kode templat](/id/open/development/obtain-the-template-code) untuk memperolehnya.
4. Setelah templat persetujuan dibuat, buka Admin Console Persetujuan OA DingTalk. Lihat templat formulir persetujuan pihak ketiga Anda, lihat atau cari data templat, serta ekspor atau hapus data templat.
5. Gunakan kode templat `processCode` untuk memanggil API penyimpanan instans persetujuan terintegrasi eksternal di Pusat Proses. Langkah ini memulai instans persetujuan dan mengembalikan ID instans persetujuan `processInstanceId`.
6. Setelah instans persetujuan dibuat, buka Pusat Persetujuan OA DingTalk. Lihat daftar persetujuan (Tertunda, Diproses, Diajukan, dan Diterima), cari data instans persetujuan, dan lakukan persetujuan.
7. Gunakan instans persetujuan `processInstanceId` dan tugas daftar To-Do untuk memanggil API penyimpanan tugas persetujuan terintegrasi eksternal di Pusat Proses. Langkah ini menyinkronkan informasi node persetujuan dari sistem pihak ketiga ke Persetujuan OA DingTalk, mengembalikan taskId setiap item To-Do, dan membuat tugas To-Do DingTalk yang sesuai.
8. Panggil API [Kueri tugas persetujuan OA yang terintegrasi melalui Pusat Proses](/id/open/development/query-oa-approval-tasks-integrated-through-process-center) untuk mengkueri tugas persetujuan pengguna yang sedang berjalan.
9. Gunakan instans persetujuan `processInstanceId` dan taskId To-Do persetujuan untuk memanggil API [Perbarui status tugas Pusat Proses](/id/open/development/update-process-center-task-status) dan menyinkronkan status item To-Do persetujuan Anda sendiri.

### Catatan

   Dalam skenario seperti persetujuan OR-sign, panggil API [Batalkan beberapa tugas tertunda di Pusat Proses](/id/open/development/cancel-multiple-oa-approval-tasks) untuk mengatur semua item To-Do yang sedang berjalan pada suatu instans persetujuan menjadi CANCELED secara massal.
10. Gunakan instans persetujuan `processInstanceId`, status instans, hasil instans, dan data lainnya untuk memicu peristiwa seperti mulai, selesai, dan alihkan tugas persetujuan, atau mulai, selesai, penghentian, dan penghapusan instans persetujuan. Peristiwa ini memperbarui status instans.
11. Untuk membersihkan data templat persetujuan, panggil API [Hapus templat](/id/open/development/self-owned-approval-deletion-template). API ini menghapus templat persetujuan yang dibuat untuk organisasi Anda, beserta semua instans dan tugas To-Do yang dibuat darinya.

## Langkah implementasi

### **Langkah 1: Dapatkan kredensial aplikasi**

1. Masuk ke [DingTalk Developer Console](https://open-dev.dingtalk.io/).
2. Pilih aplikasi target untuk membuka halaman detailnya.
3. Klik **Informasi Dasar** > **Kredensial dan Informasi Dasar**.
4. Catat `Client ID` dan `Client Secret` aplikasi.

### Catatan

   Jaga kerahasiaan `Client Secret` dan jangan pernah membagikannya kepada pihak ketiga. Simpan di variabel lingkungan atau sistem manajemen kunci, jangan di-hardcode.

### Langkah 2: Tambahkan izin API

1. Di halaman detail aplikasi, klik **Kelola izin**.
2. Masukkan pengenal izin berikut di kotak pencarian izin, lalu ajukan:

   - `qyapi_aflow` (izin pengelolaan data alur persetujuan): Memperbarui status tugas Pusat Proses.
   - `Workflow.Form.Write` (izin tulis templat alur kerja): Mendapatkan kode templat.
   - `Workflow.Form.Read` (izin baca templat alur kerja): Membuat atau memperbarui instans persetujuan.
   - `Workflow.Instance.Write` (izin tulis instans alur kerja): Membatalkan tugas tertunda di Pusat Proses secara massal.
   - `Premium.Workflow.ReadWrite.All` (izin baca/tulis alur kerja Persetujuan OA, khusus OA Edisi Premium): Mendapatkan data daftar Tertunda, Diproses, Diajukan, dan Diterima milik pengguna di Pusat Persetujuan DingTalk.

<Note>
Skenario bisnis yang berbeda mungkin memerlukan kombinasi izin yang berbeda. Ajukan sesuai kebutuhan aktual Anda.
</Note>

### Langkah 3: Dapatkan kredensial akses (Access Token)

Gunakan Client ID dan Client Secret dari Langkah 1 untuk memperoleh kredensial akses aplikasi. Lihat [Mendapatkan access token aplikasi internal](/id/open/development/obtain-the-access-token-of-an-internal-app).

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**Praktik terbaik**:

- **Strategi cache**: `accessToken` berlaku selama 2 jam. Simpan dalam cache di memori atau Redis, lalu perbarui 5 menit sebelumnya token kedaluwarsa.
- **Kontrol konkurensi**: Cegah beberapa thread memperbarui token secara bersamaan yang dapat menimbulkan konflik. Gunakan distributed lock.
- **Coba ulang saat error**: Coba ulang otomatis saat terjadi gangguan jaringan, maksimal 3 kali, dengan interval yang meningkat (1 detik → 2 detik → 4 detik).

### Langkah 4: Panggil API inti

1. **Daftarkan API callback untuk tombol persetujuan cepat kustom:** Saat penyetuju bertindak langsung di Pusat To-Do DingTalk atau pada kartu pesan Persetujuan OA, DingTalk memanggil callback ke sistem pihak ketiga. Sistem pihak ketiga memperbarui tugas dan menyinkronkan informasi tugas terbaru kembali ke Pusat Persetujuan DingTalk, sehingga siklus lengkap.

### Catatan

   Semua callback gateway ke API data di luar DingTalk wajib didaftarkan sebagai gateway di "Manajemen Sumber Data". Untuk detailnya, lihat Sumber Data.
2. **Sinkronkan data templat persetujuan ke DingTalk:** Panggil Server API baru untuk menyimpan templat persetujuan terintegrasi eksternal di Pusat Proses guna memperoleh kode templat unik `processCode`. **Dalam skenario ini, Anda tidak perlu mengonfigurasi processFeatureConfig untuk integrasi Pusat Proses.**

   ```json
   {
     "name": "Persetujuan Cepat",
     "description": "Simpan templat persetujuan terintegrasi eksternal di Pusat Proses (API Edisi Premium)",
     "formComponents": [
       {
         "componentType": "TextField",
         "props": {
           "componentId": "TextField-1",
           "label": "Kolom teks satu baris",
           "required": true,
           "bizAlias": "TextField-bizAlias",
           "disabled": false
         }
       }
     ],
     "templateConfig": {
       "disableSendCard": false
     }
   }
   ```

### Parameter permintaan

   - `name`: Nama templat persetujuan.
   - `description`: Deskripsi templat.
   - `formComponents`: Array konfigurasi komponen formulir.
   - `templateConfig`: Konfigurasi templat. `disableSendCard` menentukan apakah pengiriman kartu pesan dinonaktifkan.

### Kolom respons

   - `processCode`: Kode unik templat formulir persetujuan.
3. Jika Anda tidak menyimpan `processCode`, panggil API [Mendapatkan kode templat](/id/open/development/obtain-the-template-code) untuk memperolehnya.

   ```java
   public void getProcessCodeByName() throws Exception {
       Config config = new Config();
       config.protocol = "https";
       config.regionId = "central";

       com.aliyun.dingtalkworkflow_1_0.Client client = new com.aliyun.dingtalkworkflow_1_0.Client(config);

       GetProcessCodeByNameHeaders getProcessCodeByNameHeaders = new GetProcessCodeByNameHeaders();
       getProcessCodeByNameHeaders.xAcsDingtalkAccessToken = "accessToken";

       GetProcessCodeByNameRequest request = new GetProcessCodeByNameRequest()
               .setName("Nama");

       try {
           GetProcessCodeByNameResponse getProcessCodeByNameResponse = client.getProcessCodeByNameWithOptions(
                   getProcessCodeByNameRequest,
                   getProcessCodeByNameHeaders,
                   new com.aliyun.teautil.models.RuntimeOptions()
           );
       } catch (TeaException err) {
           if (!com.aliyun.teautil.Common.empty(err.code) && !com.aliyun.teautil.Common.empty(err.message)) {
               // err berisi atribut code dan message untuk membantu menemukan masalah
               System.out.println(err.code);
               System.out.println(err.message);
           }
       } catch (Exception _err) {
           TeaException err = new TeaException(_err.getMessage(), _err);
           if (!com.aliyun.teautil.Common.empty(err.code) && !com.aliyun.teautil.Common.empty(err.message)) {
               // err berisi atribut code dan message untuk membantu menemukan masalah
               System.out.println(err.code);
               System.out.println(err.message);
           }
       }
   }
   ```

### Parameter permintaan

   - `name`: Nama templat.

### Kolom respons

   - `processCode`: Kode unik templat formulir persetujuan.
4. Setelah templat persetujuan dibuat, pengguna dapat membuka Admin Console Persetujuan OA DingTalk. Lihat templat formulir persetujuan pihak ketiga, lihat atau cari data templat, serta ekspor atau hapus data templat.

## FAQ

- **T: Bagaimana cara menangani timeout API callback?**

  Callback DingTalk ke API sistem pihak ketiga akan timeout setelah 5 detik. Jika sistem pihak ketiga tidak mengembalikan HTTP 200 dalam 5 detik, DingTalk mencoba ulang maksimal 3 kali dengan interval 1 detik, 2 detik, dan 4 detik. Buat API callback tetap ringan dan proses logika kompleks secara asinkron.
- **T: Apakah penyetuju perlu mengonfirmasi lagi setelah mengklik tombol cepat?**

  Secara default, konfirmasi kedua tidak diperlukan. Aksi langsung dijalankan saat tombol diklik. Jika skenario bisnis Anda memerlukan konfirmasi kedua, kembalikan kode status tertentu dari API callback pihak ketiga. DingTalk kemudian menampilkan dialog konfirmasi sebelum menjalankan aksi.
