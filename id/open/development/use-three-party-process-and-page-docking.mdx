# Persetujuan OA mandiri: Integrasi alur kerja dan halaman pihak ketiga

## Ikhtisar

### Latar belakang

Banyak organisasi mengembangkan sistem OA sendiri atau membeli sistem pihak ketiga. Sistem ini biasanya memiliki proses dan halaman persetujuan masing-masing. Karyawan harus berpindah-pindah antarsistem untuk memproses persetujuan, sehingga pekerjaan menjadi terpecah dan efisiensi menurun. Hubungkan proses persetujuan mandiri Anda ke Pusat Persetujuan OA DingTalk. Dengan begitu, pengguna dapat membuka halaman sistem bisnis dan memberikan persetujuan langsung di DingTalk dalam satu pengalaman terpadu.

Organisasi umumnya menghadapi kendala berikut:

- **Titik akses persetujuan tersebar:** Karyawan memproses persetujuan secara terpisah di banyak sistem. Pengingat To-Do DingTalk tidak mencakup tugas persetujuan dari sistem mandiri, sehingga penyetuju mudah melewatkan tugas.
- **Pengalaman persetujuan tidak seragam:** Halaman persetujuan di sistem mandiri tidak sesuai dengan gaya DingTalk. Pengguna harus beradaptasi dengan berbagai antarmuka, sehingga kurva belajar meningkat.
- **Jangkauan notifikasi To-Do rendah:** Sistem mandiri mengandalkan email atau SMS untuk notifikasi persetujuan. Saluran ini lambat dan tidak dapat memanfaatkan Push pesan maupun Pusat To-Do DingTalk.
- **Data persetujuan terisolasi:** Status persetujuan dan catatan pemrosesan tersebar di berbagai sistem. Manajer tidak dapat memantau progres persetujuan di satu tempat di DingTalk.

### Nilai utama

Solusi ini menghubungkan sistem persetujuan pihak ketiga dengan halaman dalam aplikasi di DingTalk. Solusi ini memanggil API Pusat Proses persetujuan di DingTalk Open Platform untuk menyinkronkan data persetujuan dua arah.

- **Sinkronisasi templat persetujuan:** Sinkronkan templat formulir persetujuan dari sistem mandiri ke DingTalk. Pengguna dapat melihat dan mengelola templat persetujuan pihak ketiga di Admin Console Persetujuan OA DingTalk.
- **Penautan instans persetujuan:** Saat persetujuan dimulai di sistem mandiri, DingTalk otomatis membuat instans persetujuan yang sesuai. Pengguna dapat melihat dan memprosesnya di empat daftar Pusat Persetujuan DingTalk: Tertunda, Diproses, Diajukan, dan Diterima.
- **Push tugas To-Do:** Setelah informasi node persetujuan tersinkron ke DingTalk, DingTalk otomatis membuat tugas To-Do. Tugas ini menggunakan pengingat To-Do dan Push pesan DingTalk yang terpadu.
- **Penulisan balik status persetujuan:** Setelah pengguna menyelesaikan persetujuan di DingTalk, tulis balik hasilnya (misalnya Setujui atau Tolak) ke sistem mandiri agar data di kedua sisi tetap konsisten.

### Kasus penggunaan

Solusi ini cocok untuk skenario bisnis umum berikut:

- **Integrasi persetujuan pengadaan ERP:** Karyawan mengajukan permintaan pembelian di sistem ERP. Permintaan otomatis tersinkron ke DingTalk. Penyetuju menyelesaikan persetujuan di DingTalk, lalu hasilnya ditulis balik ke sistem ERP untuk memperbarui status pesanan pembelian.
- **Penautan persetujuan cuti HR:** Permohonan cuti dari sistem HR tersinkron ke DingTalk. Karyawan menerima pengingat di Pusat To-Do DingTalk dan memprosesnya di sana. Hasil persetujuan otomatis memperbarui modul kehadiran HR.
- **Integrasi penggantian biaya manajemen proyek:** Proses penggantian biaya di sistem manajemen proyek terhubung ke Pusat Persetujuan DingTalk. Manajer proyek memberikan persetujuan di DingTalk, lalu data penggantian biaya tersinkron kembali ke modul anggaran proyek.
- **Kolaborasi persetujuan kontrak CRM:** Proses persetujuan kontrak di sistem CRM tersinkron ke DingTalk. Tim penjualan menyelesaikan persetujuan bertingkat di DingTalk, dan status kontrak diperbarui di sistem CRM secara real time.

## Skenario bisnis umum

### Skenario 1: CIMC Ruijiang menyatukan persetujuan dari berbagai sistem bisnis di DingTalk

#### Kendala

CIMC Ruijiang merupakan pusat percontohan pengembangan TI internal CIMC Group. Perusahaan ini telah membangun lebih dari selusin sistem bisnis independen, seperti MES, IOT, dan SRM. Setiap sistem menangani data dan alur kerja untuk fungsi tertentu. Model yang sangat terspesialisasi ini meningkatkan efisiensi setiap unit bisnis. Namun, model ini juga memecah dan memutus aliran informasi di dalam organisasi:

- Karyawan memproses tugas persetujuan secara terpisah di lebih dari selusin sistem. Prosesnya merepotkan, dan persetujuan mendesak mudah terlewat.
- Gaya halaman persetujuan berbeda di setiap sistem. Pengguna harus beradaptasi dengan berbagai antarmuka, sehingga kurva belajar meningkat.
- Notifikasi persetujuan bergantung pada pesan internal masing-masing sistem dan tidak dapat memanfaatkan pengingat To-Do serta Push pesan DingTalk yang terpadu.
- Manajer tidak dapat memantau seluruh progres persetujuan di satu tempat di DingTalk. Mereka harus masuk ke banyak sistem untuk memeriksanya.

#### Nilai yang terbukti

- **Proses otomatis**

  Alur integrasi:

  1. Sistem **MES/IOT/SRM** mengajukan persetujuan.
  2. API Pusat **Persetujuan OA DingTalk** dipanggil untuk membuat instans persetujuan.
  3. Tugas persetujuan disinkronkan ke daftar **To-Do DingTalk**.
  4. Penyetuju menyelesaikan persetujuan di DingTalk.
  5. Hasil persetujuan ditulis balik ke sistem bisnis asal secara real time.

  Efisiensi meningkat lebih dari **83%** dibandingkan cara tradisional, yaitu mengajukan dan menyetujui di setiap sistem satu per satu.
- **Keunggulan utama**

  - **Akses terpadu untuk persetujuan lintas sistem:** Proses persetujuan, item To-Do, dan Notifikasi Kerja penting dari lebih dari selusin sistem independen, seperti MES, IOT, dan SRM, terkumpul di DingTalk untuk diproses secara terpadu.
  - **Berbagi data dan kolaborasi yang efisien:** Hilangkan silo informasi antarsistem. Wujudkan berbagi data lintas sistem dan Otomatisasi proses untuk meningkatkan daya tanggap organisasi secara keseluruhan.
  - **Pengalaman persetujuan yang lebih baik:** Karyawan tidak perlu lagi masuk ke banyak sistem satu per satu. Cukup buka DingTalk dan proses semuanya dengan satu ketukan. Kompleksitas operasional turun drastis, dan waktu respons persetujuan jauh lebih singkat.

### Skenario 2: Persetujuan cuti HR yang terhubung dengan kehadiran DingTalk

#### Kendala

Sistem HR mengelola persetujuan cuti secara terpisah, sementara data absen kehadiran tersimpan di DingTalk. Data tidak mengalir antara kedua sistem. Setelah mengambil cuti, karyawan masih harus mengajukan permohonan absen susulan secara manual di DingTalk. Staf HR harus mencocokkan catatan cuti dan kehadiran di berbagai sistem.

#### Nilai yang terbukti

- **Proses otomatis**

  Proses Otomatisasi end-to-end berjalan dalam lima langkah:

  1. Sistem **MES** membuat perintah kerja produksi.
  2. **API Persetujuan OA DingTalk** dipanggil untuk membuat instans persetujuan.
  3. Sistem **ERP** memeriksa stok material (bahan baku, bahan pembantu, kemasan).
  4. Supervisor bengkel meninjau di DingTalk lalu mengetuk **Tolak** atau **Setujui**.
  5. Hasil persetujuan tersinkron kembali ke ketiga sistem: **MES** (status perintah kerja), **ERP** (stok), dan **QMS** (catatan kualitas).

  Dibandingkan cara tradisional yang mengharuskan masuk ke MES, ERP, dan QMS secara terpisah (sekitar 15 menit per persetujuan), pendekatan terintegrasi menyelesaikan persetujuan dalam 2 menit melalui satu pintu masuk DingTalk, dengan peningkatan efisiensi persetujuan sebesar 87%.
- **Keunggulan utama**

  - **Integrasi persetujuan perintah kerja produksi:** Node persetujuan perintah kerja dari MES, ERP, dan QMS seluruhnya muncul di Daftar tugas DingTalk. Penyetuju tidak perlu lagi berpindah antarsistem.
  - **Visibilitas Proses persetujuan secara real time:** DingTalk menampilkan data perintah kerja lengkap yang dihimpun dari ketiga sistem, termasuk daftar material, persyaratan inspeksi kualitas, dan riwayat perintah kerja. Progres persetujuan terlihat jelas dalam sekejap.
  - **Sinkronisasi data end-to-end:** Hasil persetujuan ditulis balik ke sistem bisnis asal secara real time. Saat persetujuan ditolak, tugas To-Do hilir dibatalkan secara massal. Dengan begitu, data di kedua sisi tetap konsisten dan dapat dilacak.

## Panduan implementasi

### Arsitektur teknis

Solusi ini menggunakan lima komponen teknis inti berikut untuk menghubungkan sistem persetujuan mandiri Anda dengan Pusat Persetujuan OA DingTalk:

- **Lapisan Autentikasi identitas:** Berbasis protokol OAuth 2.0 DingTalk Open Platform. Lapisan ini menggunakan Kredensial aplikasi untuk memperoleh access token, yang menyediakan verifikasi identitas terpadu bagi semua panggilan API serta menjamin keamanan dan keabsahan panggilan.
- **Lapisan manajemen templat persetujuan:** Menyinkronkan templat persetujuan mandiri ke Pusat Persetujuan OA DingTalk dan memperoleh kode templat yang unik secara global sebagai pengenal. Lapisan ini mendukung pembuatan, pembaruan, dan penghapusan templat untuk pengelolaan struktur formulir persetujuan secara terpadu di cloud.
- **Mesin instans persetujuan:** Membuat instans persetujuan di DingTalk dan menghasilkan pengenal instans yang unik. Mesin ini membawa data bisnis persetujuan spesifik, seperti pemohon, Konten persetujuan, dan Lampiran, serta mendukung pengelolaan siklus hidup persetujuan secara penuh.
- **Lapisan sinkronisasi tugas To-Do:** Menyinkronkan tugas persetujuan secara massal ke Pusat Proses DingTalk, menghasilkan pengenal tugas, dan mengikatnya ke pengguna DingTalk. Penyetuju dapat melihat dan memproses tugas persetujuan dari berbagai sistem bisnis dalam satu Daftar tugas DingTalk.
- **Lapisan sinkronisasi status dua arah:** Menyinkronkan status persetujuan dua arah. Saat pengguna menyelesaikan persetujuan di DingTalk, status ditulis balik ke sistem bisnis secara real time. Saat sistem bisnis menghentikan atau menyelesaikan persetujuan, status tugas DingTalk ikut diperbarui. Dengan begitu, data di kedua sisi tetap konsisten.

### Prasyarat

- **Persiapan aplikasi**: Selesaikan [pembuatan dan konfigurasi aplikasi](/id/open/dingstart/create-application).
- **Persyaratan izin**: Miliki izin Admin Organisasi atau Sub Admin DingTalk, lalu ajukan izin API berikut:

  - `Workflow.Form.Write` (izin tulis templat alur kerja)
  - `Workflow.Form.Read` (izin baca templat alur kerja), opsional
  - `Workflow.Instance.Write` (izin tulis instans alur kerja)
  - `Workflow.Instance.Read` (izin baca instans alur kerja)
  - `qyapi_aflow` (izin pengelolaan data alur persetujuan)
- **Lingkungan pengembangan**: Lingkungan pengembangan Java (JDK 1.6 atau lebih baru) dan build tool Maven sudah terpasang.
- **Persiapan SDK**: Unduh SDK Sisi server DingTalk, yang mendukung berbagai bahasa seperti Java, Python, dan Go.

### Implementasi kode

Langkah 1: Dapatkan informasi Kredensial aplikasi, termasuk client ID dan Client Secret.

Langkah 2: Ajukan izin API untuk API terkait persetujuan.

Langkah 3: Dapatkan Kredensial akses. Lihat [Mendapatkan access token Aplikasi internal](/id/open/development/obtain-the-access-token-of-an-internal-app). Saat Anda memanggil API, access token digunakan untuk mengautentikasi identitas pemanggil.

Langkah 4: Panggil API persetujuan Sisi server.

1. Panggil Server API baru [Membuat atau memperbarui templat persetujuan](/id/open/development/create-orupdate-the-approval-template-new) untuk mendapatkan kode templat unik `processCode`.
2. Jika Anda tidak menyimpan `processCode`, panggil API [Mendapatkan kode templat](/id/open/development/obtain-the-template-code) untuk mengambilnya.
3. Setelah templat persetujuan dibuat, pengguna dapat membuka Admin Console Persetujuan OA DingTalk untuk melihat templat formulir persetujuan mandiri pihak ketiga, melihat atau mencari data templat, serta mengekspor atau menghapus data templat.
4. Dengan kode templat `processCode`, panggil Server API baru [Membuat instans](/id/open/development/create-a-ticket-approval-instance) untuk mengajukan instans persetujuan dan mendapatkan ID instans persetujuan `processInstanceId`.
5. Setelah instans persetujuan dibuat, pengguna juga dapat membuka Pusat Persetujuan OA DingTalk untuk melihat empat daftar persetujuan (Tertunda, Diproses, Diajukan, dan Diterima), mencari data instans persetujuan, dan memproses persetujuan.
6. Dengan instans persetujuan `processInstanceId` dan daftar To-Do `tasks`, panggil API [Membuat tugas tertunda di Pusat Proses](/id/open/development/create-pending-tasks-in-process-center). API ini menyinkronkan informasi node persetujuan dari sistem pihak ketiga ke Persetujuan OA DingTalk, mengembalikan taskId setiap item To-Do, dan membuat tugas To-Do DingTalk yang sesuai.
7. Setelah tugas tertunda dibuat, panggil API [Mengkueri tugas persetujuan OA yang terintegrasi melalui Pusat Proses](/id/open/development/query-oa-approval-tasks-integrated-through-process-center) untuk mengkueri tugas persetujuan pengguna yang sedang berjalan.
8. Dengan instans persetujuan `processInstanceId` dan taskId To-Do persetujuan, panggil API [Memperbarui status tugas Pusat Proses](/id/open/development/update-process-center-task-status) untuk menyinkronkan pembaruan status item To-Do persetujuan mandiri Anda. Dalam skenario seperti tanda tangan OR (cukup satu penyetuju yang menyetujui), panggil API [Membatalkan beberapa tugas tertunda di Pusat Proses](/id/open/development/cancel-multiple-oa-approval-tasks) untuk mengatur semua item To-Do yang sedang berjalan di bawah instans persetujuan menjadi CANCELED secara massal.
9. Dengan instans persetujuan `processInstanceId`, status instans `status`, hasil instans `result`, dan parameter lainnya, panggil API [Memperbarui status instans](/id/open/development/update-instance-status) atau [Memperbarui status instans secara massal](/id/open/development/self-owned-batch-update-of-instance-status) untuk memperbarui status instans.
10. Terakhir, untuk membersihkan data templat persetujuan, panggil API [Menghapus templat](/id/open/development/self-owned-approval-deletion-template). API ini menghapus templat persetujuan yang dibuat untuk Organisasi Anda, beserta instans dan tugas To-Do yang dibuat di bawahnya.

## Langkah implementasi

### **Langkah 1: Dapatkan kredensial aplikasi**

1. Masuk ke [DingTalk Developer Console](https://open-dev.dingtalk.io/).
2. Pilih aplikasi target untuk membuka halaman detailnya.
3. Klik **Informasi Dasar** > **Kredensial dan Informasi Dasar**.
4. Catat `Client ID` dan `Client Secret` aplikasi.

### Catatan

   Jaga kerahasiaan `Client Secret` dan jangan pernah membagikannya kepada pihak ketiga. Simpan di variabel lingkungan atau sistem manajemen kunci, jangan di-hardcode.

### Langkah 2: Tambahkan izin API

1. Di halaman detail aplikasi, klik **Kelola izin**.
2. Di kotak pencarian izin, masukkan pengenal izin berikut lalu ajukan:

   - `Workflow.Form.Write` (izin tulis templat alur kerja): Membuat, memperbarui, dan menghapus templat persetujuan.
   - `Workflow.Form.Read` (izin baca templat alur kerja): Mendapatkan kode templat. Opsional.
   - `Workflow.Instance.Write` (izin tulis instans alur kerja): Membuat instans persetujuan dan memperbarui status instans.
   - `Workflow.Instance.Read` (izin baca instans alur kerja): Mengkueri tugas persetujuan dan informasi instans.
   - `qyapi_aflow` (izin pengelolaan data alur persetujuan): Mengelola data Proses persetujuan secara menyeluruh.

<Note>
Skenario bisnis yang berbeda mungkin memerlukan kombinasi izin yang berbeda. Ajukan izin sesuai kebutuhan aktual Anda. Misalnya, skenario impor massal juga memerlukan izin untuk operasi pengguna secara massal.
</Note>

### Langkah 3: Dapatkan Kredensial akses (Access Token)

Gunakan Client ID dan Client Secret dari Langkah 1 untuk mendapatkan Kredensial akses aplikasi. Lihat [Mendapatkan access token Aplikasi internal](/id/open/development/obtain-the-access-token-of-an-internal-app).

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**Praktik terbaik**:

- **Strategi cache**: `accessToken` berlaku selama 2 jam. Simpan dalam cache di memori atau Redis, lalu muat ulang secara proaktif 5 menit sebelumnya kedaluwarsa.
- **Kontrol konkurensi**: Cegah beberapa thread memuat ulang token secara bersamaan yang dapat menimbulkan Konflik. Gunakan distributed lock.
- **Coba ulang saat error**: Coba ulang secara otomatis saat terjadi gangguan jaringan, maksimal 3 kali, dengan interval yang bertambah (1s → 2s → 4s).

## FAQ

- **Q1: Parameter apa saja yang wajib diisi saat membuat templat persetujuan?**

  A: Parameter Wajib adalah:

  - `name`: Nama templat persetujuan.
  - `formComponents`: Daftar komponen formulir. Daftar ini harus berisi minimal satu komponen.
  - Parameter Opsional mencakup `description` (deskripsi templat) dan lainnya.
- **Q2: Bagaimana cara mendapatkan processCode?**

  A: Gunakan salah satu metode berikut:

  - Setelah memanggil API Membuat atau memperbarui templat persetujuan, ambil `result.processCode` dari respons.
  - Jika Anda tidak menyimpan processCode, panggil API Mendapatkan kode templat dan lakukan kueri berdasarkan nama templat.
- **Q3: Apa yang berubah di DingTalk setelah saya membuat tugas tertunda?**

  A: Setelah Anda membuat tugas tertunda:

  1. Halaman detail formulir persetujuan menampilkan tombol Setujui dan Tolak.
  2. Pusat Proses menyinkronkan tugas persetujuan sebagai tugas To-Do DingTalk.
  3. Penyetuju melihat pengingat persetujuan di Pusat To-Do DingTalk.
- **Q4: Bagaimana cara menyinkronkan data tugas To-Do?**

  A: Ikuti langkah berikut:

  1. Panggil API Membuat tugas tertunda di Pusat Proses untuk menyinkronkan informasi node persetujuan dari sistem pihak ketiga ke DingTalk.
  2. Panggil API Mengkueri tugas persetujuan OA untuk memastikan tugas telah tersinkron dengan benar.
  3. Saat status persetujuan berubah, panggil API Memperbarui status tugas Pusat Proses untuk menyinkronkan status terbaru.
- **Q5: Izin apa saja yang perlu saya ajukan di DingTalk Open Platform?**

  A: Ajukan izin berikut untuk terhubung ke Pusat Proses Persetujuan OA:

  | **Kode cakupan izin** | **Nama cakupan izin** | **Deskripsi** |
  | --- | --- | --- |
  | Workflow.Form.Write | Izin tulis templat alur kerja | Membuat, memperbarui, dan menghapus templat persetujuan |
  | Workflow.Instance.Write | Izin tulis instans alur kerja | Membuat instans persetujuan dan memperbarui status instans |
  | Workflow.Instance.Read | Izin baca instans alur kerja | Mengkueri tugas persetujuan dan informasi instans |
  | qyapi_aflow | Izin pengelolaan data alur persetujuan | Mengelola data Proses persetujuan secara menyeluruh |

  Skenario bisnis yang berbeda mungkin memerlukan kombinasi izin yang berbeda. Ajukan izin sesuai kebutuhan aktual Anda.
