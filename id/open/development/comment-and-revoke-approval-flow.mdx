# Integrasi alur kerja Persetujuan OA: menambahkan komentar persetujuan dan menghentikan persetujuan

## Ikhtisar

### Latar belakang

Sistem bisnis yang dibangun atau dibeli organisasi sering kali perlu melampirkan dokumen pendukung ke instans persetujuan selama alur kerja persetujuan, seperti hasil pindaian kontrak atau laporan serah terima. Sistem ini umumnya tidak memiliki titik masuk terpadu untuk mengunggah lampiran. Sistem ini juga tidak memiliki cara standar untuk membatalkan persetujuan yang diajukan secara keliru atau saat kebutuhan berubah. Hubungkan komentar dan pembatalan persetujuan ke Pusat Persetujuan Persetujuan OA DingTalk agar pengguna dapat menambahkan lampiran dan menghentikan persetujuan langsung di DingTalk.

- **Tidak ada titik masuk untuk lampiran:** Pengaju persetujuan tidak dapat menambahkan dokumen pendukung di luar sistem bisnis. Informasi persetujuan menjadi tidak lengkap, dan keputusan tidak memiliki dasar yang kuat.
- **Pembatalan tidak standar:** Formulir persetujuan yang diajukan secara keliru ditarik melalui komunikasi offline. Tidak ada catatan pembatalan maupun sinkronisasi status di tingkat sistem.
- **Ruang Drive terputus:** Lampiran persetujuan tersebar di folder Drive pribadi atau penyimpanan lokal. Lampiran tidak dapat ditautkan ke instans persetujuan sehingga menyulitkan audit.
- **Tidak ada konfirmasi skema:** Struktur formulir tidak divalidasi sebelum persetujuan diajukan. Hal ini menyebabkan error saat runtime, seperti ID kontrol yang tidak cocok dan pengiriman data yang gagal.

### Nilai utama

Solusi ini memanfaatkan kembali manajemen ruang Drive dan mesin komentar dari Persetujuan OA resmi. Solusi ini mengintegrasikan unggahan lampiran, pembuatan komentar, dan pembatalan ke sistem bisnis Anda untuk mengelola seluruh siklus hidup persetujuan.

- **Manajemen lampiran terpusat:** Semua lampiran persetujuan diunggah ke ruang Drive persetujuan khusus dan diikat ke instans. Unduh dengan sekali klik dan telusuri saat audit.
- **Komentar yang dapat ditelusuri:** Komentar persetujuan beserta lampirannya disimpan secara permanen. Komentar membentuk jejak komunikasi yang lengkap dan mencegah hilangnya informasi.
- **Pembatalan terstandar:** Picu pembatalan melalui API. Status persetujuan otomatis berubah menjadi "Dihentikan", dan Callback sinkron memberi tahu sistem bisnis.
- **Pravalidasi skema:** Dapatkan skema formulir sebelum mengajukan persetujuan. Pastikan pengaturan kontrol sesuai dengan templat dan kurangi biaya integrasi serta debugging.

### Kasus penggunaan

Solusi ini cocok untuk skenario umum berikut dalam mengintegrasikan komentar dan pembatalan persetujuan:

- Firma hukum perlu melampirkan bukti dan menambahkan komentar tinjauan pengacara selama proses persetujuan perkara.
- Lembaga pendidikan dan pelatihan perlu membatalkan persetujuan perubahan kursus yang telah diajukan setelah menemukan konflik penjadwalan shift, lalu mengajukannya kembali.
- Organisasi medis perlu menambahkan dokumen kualifikasi pemasok sebagai lampiran komentar selama persetujuan pengadaan obat.
- Proyek konstruksi perlu menghentikan persetujuan serah terima yang sedang berjalan setelah menemukan data inspeksi yang salah, lalu memperbaiki dan mengajukannya kembali.

## Skenario bisnis umum

### Skenario 1: Menambahkan bukti pada persetujuan perkara firma hukum

#### Kendala

Sebuah firma hukum menggunakan sistem manajemen perkara internal untuk menangani persetujuan perkara. Setelah pengacara mengajukan persetujuan pendaftaran perkara, mereka sering perlu menambahkan bukti atau pendapat hukum baru. Proses awal memiliki masalah berikut:

- **Tidak ada saluran untuk menambahkan bukti:** Setelah persetujuan pendaftaran perkara dimulai, pengacara tidak dapat melampirkan bukti yang baru dikumpulkan melalui sistem. Mereka mengirim email ke partner secara offline sehingga dokumen persetujuan tetap tidak lengkap.
- **Catatan komunikasi tersebar:** Catatan tambahan pengacara tersebar di WeChat, email, dan saluran lainnya. Penyetuju tidak dapat melihat seluruh komunikasi di formulir persetujuan sehingga keputusan menjadi lambat.
- **Lampiran tidak teratur:** File bukti disimpan di komputer pribadi atau drive jaringan bersama dan tidak ditautkan ke instans persetujuan. Audit memerlukan pencocokan manual.
- **Sulit memperbaiki persetujuan yang keliru:** Jika informasi pendaftaran salah, tidak ada mekanisme pembatalan yang sistematis. Pengacara meminta penyetuju menolak secara lisan sehingga tidak ada catatan penghentian resmi maupun sinkronisasi status.

#### Validasi nilai

- **Alur kerja otomatis**

  Alur persetujuan otomatis berjalan dalam lima langkah:

  1. Pengacara mengajukan pendaftaran perkara, mengisi informasi perkara, dan mengunggah dokumen bukti.
  2. **Instans persetujuan** dibuat dan diinisialisasi melalui API **DingTalk OA**.
  3. Partner meninjau perkara di DingTalk, tempat Persetujuan dirutekan dan formulir ditampilkan.
  4. **Penyetuju** bertindak melalui perangkat seluler dan memilih **Tolak** atau **Setujui**.
  5. Hasilnya disinkronkan kembali ke sistem, yang mencatat status dan menyinkronkan data.

  Dibandingkan proses manual (berpindah antarsaluran, status tidak sinkron, dan notifikasi tersebar), integrasi otomatis menyediakan titik masuk terpadu, sinkronisasi real-time, dan pengiriman pesan.
- **Keunggulan utama**

  - **Tambahkan bukti secara online:** Pengacara dapat melampirkan file bukti ke formulir persetujuan kapan saja melalui API komentar persetujuan. Penyetuju melihat dokumen lengkap di DingTalk dan mengambil keputusan.
  - **Jejak komunikasi lengkap:** Semua catatan dan lampiran ditautkan secara permanen ke instans persetujuan melalui komentar. Hal ini menghasilkan catatan persetujuan perkara yang lengkap untuk audit berikutnya.
  - **Pembatalan terstandar:** Jika informasi pendaftaran salah, API pembatalan menghentikan Proses persetujuan secara resmi. Sistem mencatat alasan pembatalan dan menyinkronkan status sehingga tanggung jawab tidak lagi kabur akibat komunikasi lisan.

### Skenario 2: Membatalkan dan mengajukan ulang persetujuan perubahan kursus di lembaga pelatihan

#### Kendala

Sebuah lembaga pendidikan dan pelatihan menggunakan sistem akademik internal untuk mengelola persetujuan perubahan kursus. Setelah mengajukan permintaan perubahan jadwal, staf terkadang menemukan bentrokan waktu atau kekurangan ruang kelas. Proses awal memiliki masalah berikut:

- **Konflik terdeteksi terlambat:** Bentrokan waktu dengan kursus lain baru ditemukan setelah persetujuan diajukan. Saat itu persetujuan sudah berjalan dan tidak dapat ditarik melalui sistem.
- **Informasi perubahan tidak lengkap:** Penyetuju hanya melihat formulir permintaan perubahan. Mereka tidak dapat melihat siswa yang terdampak, jadwal pengajar, atau penggunaan ruang kelas di formulir persetujuan sehingga sulit menilai dampaknya.
- **Pembatalan tidak standar:** Permintaan yang keliru hanya dapat ditolak dengan memberi tahu penyetuju secara offline. Tidak ada catatan pembatalan di tingkat sistem sehingga log akademik tidak sesuai dengan status sebenarnya.
- **Pengajuan ulang tidak efisien:** Setelah pembatalan, staf harus mengisi ulang seluruh formulir untuk mengajukan persetujuan baru. Data dari formulir awal tidak dapat digunakan kembali sehingga menambah beban kerja.

#### Validasi nilai

- **Alur kerja otomatis**

  Alur terintegrasi end-to-end berjalan dalam lima langkah:

  1. **Bagian akademik mengajukan perubahan jadwal:** Isi permintaan perubahan dan tandai siswa yang terdampak.
  2. **Buat instans persetujuan:** Panggil API Persetujuan OA DingTalk untuk menginisialisasi instans.
  3. **Tinjau di konsol admin akademik:** Rutekan Formulir persetujuan dan jalankan deteksi konflik. Formulir mencakup kolom seperti **Nama kursus**, **Waktu awal**, **Waktu baru**, **Ruang kelas**, **Pengajar pemohon**, dan **Jumlah terdampak**.
  4. **Penyetuju bertindak:** Penyetuju meninjau melalui perangkat seluler dan mengetuk **Setujui** atau **Tolak**.
  5. **Sinkronkan hasil kembali ke sistem akademik:** Perbarui jadwal pelajaran dan sinkronkan data.
- **Keunggulan utama**

  - **Batalkan jadwal yang bentrok dengan segera:** Jika permintaan perubahan salah, API pembatalan langsung menghentikan Proses persetujuan. Sistem mencatat alasan pembatalan dan mencegah persetujuan yang keliru memengaruhi pengaturan pengajaran.
  - **Nilai dampak perubahan secara online:** Staf dapat menggunakan komentar untuk menambahkan daftar siswa yang terdampak dan rencana penyesuaian ruang kelas ke formulir persetujuan. Penyetuju melihat semua informasi perubahan di satu tempat di DingTalk.
  - **Sinkronisasi status real-time:** Hasil pembatalan ditulis kembali ke sistem akademik secara real-time sehingga jadwal pelajaran tetap konsisten dengan status persetujuan. Staf dapat dengan cepat memperbaiki data saat mengajukan persetujuan baru dan mengurangi entri data berulang.

## Panduan implementasi

### Arsitektur teknis

Arsitektur teknis solusi ini mencakup komponen inti berikut:

- **Lapisan Autentikasi**: Mengelola kredensial Aplikasi dan memperoleh access token untuk memverifikasi identitas setiap panggilan API.
- **Lapisan manajemen templat**: Membuat dan memperbarui templat formulir persetujuan serta menentukan struktur dan kolom Proses persetujuan.
- **Lapisan eksekusi instans**: Mengajukan, mengkueri, dan membatalkan instans persetujuan untuk menjalankan Proses persetujuan.
- **Lapisan komentar dan lampiran**: Mengelola ruang Drive persetujuan dan menambahkan komentar untuk menuntaskan siklus komunikasi persetujuan.

### Prasyarat

- **Persiapan Aplikasi**: Selesaikan [pembuatan dan konfigurasi Aplikasi](/id/open/dingstart/create-application).
- **Izin**: Miliki izin Admin Organisasi atau Sub Admin DingTalk, dan ajukan izin API berikut:

  - `Workflow.Form.Write` (izin tulis templat alur kerja)
  - `Workflow.Form.Read` (izin baca templat alur kerja)
  - `Workflow.Instance.Write` (izin tulis instans alur kerja)
  - `Workflow.Instance.Read` (izin baca instans alur kerja)
- **Lingkungan pengembangan**: Instal lingkungan pengembangan Java (JDK 1.6 atau yang lebih baru) dan alat build Maven.
- **Persiapan SDK**: Unduh SDK Sisi server DingTalk, yang mendukung Java, Python, Go, dan bahasa lainnya.

### Implementasi kode

Langkah 1: Buka halaman detail Aplikasi dan dapatkan client ID serta Client Secret.

Langkah 2: Ajukan izin API. Ajukan izin "Persetujuan OA" yang terkait.

Langkah 3: Dapatkan Kredensial akses Aplikasi. Lihat [Mendapatkan Access Token Aplikasi internal](/id/open/development/obtain-the-access-token-of-an-internal-app). Saat memanggil API, gunakan access token untuk mengautentikasi pemanggil.

Langkah 4: Panggil API Persetujuan OA:

Langkah 1: Buka halaman detail Aplikasi dan dapatkan client ID serta Client Secret.

Langkah 2: Ajukan izin API. Ajukan izin "Persetujuan OA" yang terkait.

Langkah 3: Dapatkan Kredensial akses Aplikasi. Lihat [Mendapatkan Access Token Aplikasi internal](/id/open/development/obtain-the-access-token-of-an-internal-app). Saat memanggil API, gunakan access token untuk mengautentikasi pemanggil.

Langkah 4: Panggil API Persetujuan OA:

1. Panggil Server API baru [Membuat atau memperbarui templat formulir persetujuan](/id/open/development/create-an-approval-form-template) untuk mendapatkan kode templat unik `processCode`.
2. Gunakan `processCode` untuk memanggil Server API baru [Mendapatkan skema formulir](/id/open/development/obtain-the-form-schema) dan dapatkan skema templat formulir. Tinjau dan konfirmasi detail skema templat formulir.
3. Gunakan `processCode` untuk memanggil Server API baru [Membuat instans persetujuan](/id/open/development/create-an-approval-instance) guna mengajukan instans persetujuan dan mendapatkan `instanceId` instans persetujuan.
4. Gunakan `instanceId` untuk memanggil Server API baru [Mendapatkan detail satu instans persetujuan](/id/open/development/obtains-the-details-of-a-single-approval-instance-pop) guna mendapatkan detail instans persetujuan.
5. Untuk menambahkan lampiran ke komentar persetujuan, unggah file ke ruang Drive persetujuan. Langkah ini menyediakan parameter API spaceId, fileType, fileName, fileId, dan fileSize. Dapatkan parameter tersebut sebagai berikut:

   1. Panggil Server API baru [Mendapatkan informasi ruang Drive persetujuan](/id/open/development/obtains-the-information-about-approval-nail-disk) untuk mendapatkan izin unggah ke ruang Drive dan spaceId ruang Drive persetujuan.
   2. Panggil JSAPI Sisi klien untuk mendapatkan informasi ruang Drive persetujuan guna memperoleh informasi dasar file.
6. Setelah mendapatkan spaceId ruang Drive persetujuan, gunakan `instanceId` untuk memanggil Server API baru [Menambahkan komentar persetujuan](/id/open/development/official-approval-adds-approval-comments) guna menambahkan komentar ke Formulir persetujuan.
7. Setelah meninjau persetujuan, gunakan `instanceId` untuk memanggil Server API baru [Membatalkan instans persetujuan](/id/open/development/revoke-an-approval-instance) guna membatalkan Formulir persetujuan.

## Langkah implementasi

### **Langkah 1:** **Dapatkan kredensial Aplikasi**

1. Masuk ke [DingTalk Developer Console](https://open-dev.dingtalk.io/).
2. Pilih Aplikasi target untuk membuka halaman detailnya.
3. Klik **Informasi Dasar** > **Kredensial dan Informasi Dasar**.
4. Catat `Client ID` dan `Client Secret` Aplikasi.

### Catatan

   Jaga kerahasiaan `Client Secret` dan jangan bagikan kepada pihak ketiga. Simpan di variabel lingkungan atau sistem manajemen kunci, bukan di-hard-code.

### Langkah 2: Tambahkan izin API

1. Di halaman detail Aplikasi, klik **Kelola izin**.
2. Masukkan pengidentifikasi izin berikut di kotak pencarian izin, lalu ajukan:

   - `Workflow.Form.Write` (izin tulis templat alur kerja): Membuat dan memperbarui templat formulir persetujuan.
   - `Workflow.Form.Read` (izin baca templat alur kerja): Mendapatkan skema formulir.
   - `Workflow.Instance.Write` (izin tulis instans alur kerja): Mengajukan dan membatalkan instans persetujuan.
   - `Workflow.Instance.Read` (izin baca instans alur kerja): Mengkueri detail instans persetujuan.

<Note>
Skenario bisnis yang berbeda mungkin memerlukan kombinasi izin yang berbeda. Ajukan sesuai kebutuhan Anda. Misalnya, skenario impor massal juga memerlukan izin untuk operasi pengguna secara massal.
</Note>

### Langkah 3: Dapatkan Kredensial akses (Access Token)

Gunakan Client ID dan Client Secret dari Langkah 1 untuk mendapatkan Kredensial akses Aplikasi. Lihat [Mendapatkan Access Token Aplikasi internal](/id/open/development/obtain-the-access-token-of-an-internal-app).

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**Praktik terbaik**:

- **Caching**: `accessToken` berlaku selama 2 jam. Simpan di cache memori atau Redis, lalu perbarui 5 menit sebelumnya masa berlakunya habis.
- **Kontrol konkurensi**: Cegah beberapa thread memperbarui token secara bersamaan. Gunakan distributed lock.
- **Percobaan ulang saat error**: Coba ulang secara otomatis saat terjadi gangguan jaringan, maksimal 3 kali dengan interval yang meningkat (1 dtk → 2 dtk → 4 dtk).

## FAQ

- **T1: Apa yang harus dilakukan jika error 403 muncul saat mendapatkan skema formulir?**

  Pastikan izin `Workflow.Form.Read` telah diberikan dan access token belum kedaluwarsa. Izin memerlukan waktu 1 hingga 2 menit untuk berlaku setelah disetujui.
- **T2: Mengapa lampiran tidak ditampilkan setelah saya menambahkan komentar persetujuan?**

  Pastikan semua parameter wajib telah diperoleh dengan benar dari API ruang Drive persetujuan dan JSAPI Sisi klien, serta file berhasil diunggah ke ruang Drive yang sesuai.
- **T3: Mengapa status tidak diperbarui setelah saya membatalkan instans persetujuan?**

  Pembatalan berjalan secara asinkron. Berlangganan event Callback perubahan instans persetujuan untuk memantau perubahan status, atau lakukan polling ke API untuk mendapatkan detail satu instans persetujuan guna memastikannya.
- **T4: Apakah saya dapat menambahkan komentar ke instans persetujuan yang telah dibatalkan?**

  Tidak. Instans persetujuan yang telah dibatalkan berada dalam status akhir dan tidak menerima komentar maupun lampiran apa pun. Untuk menambahkan informasi, ajukan instans persetujuan baru.
