# OA承認の統合：承認フローの承認・却下

## 概要

### 背景

自社開発やサードパーティの業務システムには、それぞれ独自の承認フローと承認画面があることが少なくありません。従業員は承認のたびに複数のシステムを行き来する必要があり、作業が分断されて効率が下がります。承認フローを DingTalk のOA承認センターに接続すると、ユーザーは DingTalk の単一の入口からすべての承認を確認・処理できます。

- **頻繁なシステム切り替え：** 従業員は業務システムと DingTalk を何度も行き来します。操作経路が長く、緊急の承認を見落としやすくなります。
- **承認ステータスの不一致：** 業務システムと DingTalk のデータが一致せず、承認の進捗をリアルタイムに追跡・管理できません。
- **承認フローの分散：** 管理者は DingTalk ですべての承認の進捗を確認できず、システムごとに個別にログインする必要があります。
- **通知の遅延：** 承認通知がメールやオフラインでの連絡に依存しており、DingTalk の統一された ToDo リマインダーやメッセージプッシュを活用できていません。

### 導入のメリット

本ソリューションは、DingTalk の公式 OA 承認のプロセスエンジンとフォームコンポーネントを再利用します。業務システムの承認フローを DingTalk に統合し、一元管理と効率的なコラボレーションを実現します。

- **承認の入口を一元化：** ユーザーは DingTalk の承認一覧から、すべての自社システムの承認を確認・処理できます。システム間の切り替えが減ります。
- **低い統合コスト：** 少数の API を呼び出すだけで統合が完了します。既存の業務プロセスや画面ロジックを作り直す必要はありません。
- **ステータスのリアルタイム同期：** 承認結果は業務システムにリアルタイムで書き戻されます。双方のデータの整合性とトレーサビリティを確保します。
- **メッセージの即時配信：** DingTalk の ToDo リマインダーとメッセージ通知により、承認タスクを承認者に即座にプッシュします。

### ユースケース

本ソリューションは、次のような代表的な承認統合シナリオに適しています。

- 自社開発の ERP、OA などの業務システムを DingTalk 承認センターと連携させたい場合
- 小売チェーンの店舗運営に関する承認（改装申請、販促承認など）
- 物流・輸送の配車に関する承認（車両修理申請、ルート変更承認など）
- 人事関連の承認（休暇申請、経費精算、入社・退職手続きなど）

## 代表的な業務シナリオ

### シナリオ 1：医療機器の調達承認（医療）

#### 課題

ある大規模総合病院では、自社開発の HIS システムで医療機器の調達を管理しています。診療科が調達申請を提出すると、設備部 → 財務部 → 担当副院長の 3 段階で承認が行われます。従来のフローには次の課題がありました。

- **調達対応の遅さ：** 緊急の機器購入でも紙の申請書に段階ごとの署名が必要で、平均 3〜5 日の遅延が発生し、診療に影響していました。
- **承認情報の不足：** 承認者が確認できるのは機器名と予算のみでした。技術仕様、サプライヤーの資格、調達履歴を DingTalk で確認できず、的確な判断が困難でした。
- **承認責任の不明確さ：** 多段階承認に明確な順序や期限がなく、責任の押し付け合いや重複承認が発生し、意思決定までの期間が長くなっていました。
- **深刻なデータのサイロ化：** HIS システムの調達ステータスと DingTalk の承認進捗が同期されていませんでした。診療科は承認結果をリアルタイムに把握できず、何度も電話で確認する必要がありました。

#### 導入効果

- **自動化された作業フロー**

  統合フロー：

  1. HIS システムが調達申請を開始します。
  2. API 経由で DingTalk に承認インスタンスを作成します。
  3. DingTalk 内で調達申請の承認を行います。
  4. 承認者が詳細を確認し、操作（**承認** または **却下**）を行います。
  5. 結果が HIS システムに同期されます。

  DingTalk の承認カードには、申請者、申請部門、調達品名、金額、サプライヤーなどのフィールドが表示されます。
- **主なメリット**

  - **機器仕様と資格のオンライン確認：** HIS システムに機器が登録されると、DingTalk の承認インスタンスが自動で作成されます。承認者はシステムを切り替えずに、DingTalk 上で機器の詳細を確認して操作できます。
  - **透明でトレーサブルな多段階の合議：** DingTalk には技術仕様、サプライヤーの資格、調達履歴を含む機器データがすべて表示されます。承認の進捗がひと目でわかり、コメントや催促にも対応しています。
  - **緊急調達の迅速化：** 承認結果は HIS システムにリアルタイムで書き戻されます。申請が却下されると、後続の ToDo は自動で取り消されます。双方のデータの整合性とトレーサビリティが保たれ、承認処理の所要時間が 50% 以上短縮されます。

### シナリオ 2：大学の研究費精算承認（教育）

#### 課題

ある有力大学では、自社開発の研究管理システムで研究費の精算を管理しています。教員が精算申請を提出すると、研究責任者 → 学部 → 財務部の 3 段階で承認が行われます。従来のフローには次の課題がありました。

- **精算サイクルの長さ：** 紙の申請書を承認者間で手渡しで回付しており、平均 7〜10 営業日かかっていました。立て替え払いをする教員にとって大きな経済的負担となっていました。
- **請求書確認の難しさ：** 承認者は DingTalk で請求書の原本や費用明細を確認できず、紙の書類を印刷して 1 件ずつ照合する必要があり、非効率でした。
- **部門間連携の不足：** 研究責任者、学部の事務担当者、財務の審査担当者の間にリアルタイムの連絡チャンネルがなく、差し戻された申請は最初からフローをやり直す必要がありました。
- **高いコンプライアンスリスク：** 手書きの精算申請書は勘定科目の誤りや上限超過の申請が起こりやすく、後の監査で違反が見つかると責任追及と是正が必要になっていました。

#### 導入効果

- **自動化された作業フロー**

  統合された研究費精算フローは、次の 5 ステップでエンドツーエンドに実行されます。

  1. 研究システムで精算を開始します（申請者が精算申請を提出）。
  2. 統合 API 経由で **承認インスタンス** を作成します。
  3. 精算申請書が DingTalk に連携され、アプリ内で詳細を表示して審査します。
  4. **承認者** がモバイルで **却下** または **承認** を選択します。
  5. 結果が研究システムに書き戻され、同期されます。

  従来の手作業によるフロー（提出 > メール > 手動処理 > メール通知 > 手動入力）と比べて、自動統合により入口の一元化、リアルタイム同期、メッセージ配信の集約を実現します。
- **主なメリット**

  - **請求書画像のインテリジェントな認識と確認：** 研究システムに請求書がアップロードされると、DingTalk の承認インスタンスが自動で作成されます。承認者はシステムを切り替えずに、DingTalk 上で請求書画像を確認して操作できます。
  - **予算残高のリアルタイム検証：** DingTalk には請求書画像、費用明細、予算残高を含む精算データがすべて表示されます。承認の進捗がひと目でわかり、コメントや催促にも対応しています。
  - **差し戻しと修正のクローズドループ：** 承認結果は研究システムにリアルタイムで書き戻されます。申請が却下されると、申請者に追加資料の提出が自動で通知されます。双方のデータの整合性とトレーサビリティが保たれ、精算サイクルが 60% 以上短縮されます。

## 実装ガイド

### 技術アーキテクチャ

本ソリューションの技術アーキテクチャは、次のコアコンポーネントで構成されます。

- **認証レイヤー：** App の認証情報を管理し、アクセストークンを取得して、すべての API 呼び出しの身元を検証します。
- **テンプレート管理レイヤー：** 承認フォームテンプレートを作成・更新し、承認フローの構造とフィールドを定義します。
- **インスタンス実行レイヤー：** 承認インスタンスの開始・照会・実行を行い、承認フローを進めます。
- **イベントコールバックレイヤー：** 承認タスクと承認インスタンスのステータス変更イベントを受信し、業務システムと DingTalk の双方向同期を実現します。

### 前提条件

- **App の準備：** [App の作成と設定](/ja/open/dingstart/create-application) を完了し、Client ID と Client Secret を取得します。
- **権限の要件：** DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請します。

  - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）
  - `Workflow.Instance.Write`（承認インスタンスの書き込み権限）
  - `Workflow.Instance.Read`（承認インスタンスの読み取り権限）
- **開発環境：** Java 開発環境（JDK 1.6 以降）と Maven ビルドツールをインストールします。
- **SDK の準備：** DingTalk サーバーサイド SDK をダウンロードします。Java、Python、Go などの言語に対応しています。

### コードの実装

ステップ 1：App の詳細ページに移動し、クライアント ID と Client Secret を取得します。

ステップ 2：API 権限を申請します。「OA承認」関連の権限を申請してください。

ステップ 3：App のアクセス認証情報を取得します。[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app) を参照してください。API を呼び出す際は、アクセストークンで呼び出し元を認証します。

ステップ 4：OA承認 API を呼び出します。

1. 新しいサーバー API [承認フォームテンプレートを作成または更新する](/ja/open/development/create-an-approval-form-template) を呼び出し、テンプレートの一意なコード `processCode` を取得します。
2. `processCode` を使用して、新しいサーバー API [承認インスタンスを作成する](/ja/open/development/create-an-approval-instance) を呼び出して承認インスタンスを開始し、承認インスタンスの `instanceId` を取得します。

### 注意

   承認インスタンスの `instanceId` を保存していない場合は、新しいサーバー API [承認インスタンス ID の一覧を取得する](/ja/open/development/obtain-an-approval-list-of-instance-ids) を呼び出し、インスタンスを開始した期間の `instanceId` を取得してください。
3. `instanceId` を使用して、新しいサーバー API [単一の承認インスタンス詳細の取得](/ja/open/development/obtains-the-details-of-a-single-approval-instance-pop) を呼び出し、承認インスタンスの詳細と各タスクノードの `taskId` を取得します。
4. `instanceId` と対応する `taskId` を使用して、新しいサーバー API [承認タスクを承認または却下する](/ja/open/development/approve-or-reject-the-approval-task) を呼び出し、承認タスクを処理します。すべての承認ノードで承認されると、承認フォームの承認が完了します。このステップはサードパーティの企業アプリには対応していません。

## 実装手順

### **ステップ 1：** **App の認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/) にログインします。
2. 対象の App を選択し、App の詳細ページに移動します。
3. **基本情報** > **認証情報と基本情報** をクリックします。
4. App の `Client ID` と `Client Secret` を控えます。

### 注意

   `Client Secret` は安全に管理し、第三者と共有しないでください。コードにハードコーディングせず、環境変数やキー管理システムに保存してください。

### ステップ 2：API 権限を追加する

1. App の詳細ページで **権限管理** をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）：承認フォームテンプレートを作成・更新します。
   - `Workflow.Instance.Write`（承認インスタンスの書き込み権限）：承認インスタンスを開始・実行します。
   - `Workflow.Instance.Read`（承認インスタンスの読み取り権限）：承認インスタンスの詳細を照会します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。実際の要件に応じて申請してください。
</Note>

### ステップ 3：アクセス認証情報（アクセストークン）を取得する

ステップ 1 で取得した Client ID と Client Secret を使用して、App のアクセス認証情報を取得します。[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app) を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ戦略**：`accessToken` の有効期間は 2 時間です。メモリまたは Redis にキャッシュし、有効期限の 5分前に事前に更新してください。
- **同時実行制御**：複数のスレッドが同時にトークンを更新して競合が発生しないよう、分散ロックを使用してください。
- **エラー時の再試行**：ネットワークが不安定な場合は自動で再試行します。再試行は最大 3 回とし、間隔を段階的に延ばします（1 秒 → 2 秒 → 4 秒）。

## よくある質問

- **Q1：承認テンプレートを作成する際、formComponents の componentId にはどのような要件がありますか？**

  componentId はフォーム内で一意である必要があり、業務上の意味は持ちません。コントロールを識別するためだけに使用します。業務上の識別子を使用したい場合は、代わりに bizAlias フィールドを使用してください。
- **Q2：承認インスタンスを開始する際、approvers の actionType にはどの値を指定できますか？**

  actionType には、NONE（単独承認）、OR（いずれか承認：承認者のうち 1 人が承認すれば承認）、AND（全員承認：すべての承認者の承認が必要）などの値を指定できます。詳細は API ドキュメントを参照してください。
- **Q3：保存していない processCode を取得するにはどうすればよいですか？**

  承認テンプレートの作成時に返された processCode を保存していない場合は、DingTalk のOA承認管理コンソールにログインして確認するか、テンプレートコードを取得する API を呼び出してください。
- **Q4：承認タスクを実行する際、actionerUserId にはどのような要件がありますか？**

  actionerUserId には、現在の承認ノードに割り当てられたユーザーの userId を指定する必要があります。それ以外の userId を指定すると、操作は失敗します。
- **Q5：承認完了後のステータス変更を、業務システムで検知するにはどうすればよいですか？**

  承認インスタンスの変更コールバックイベントをサブスクライブすると、ステータスの変更をリアルタイムに検知できます。または、承認インスタンスの詳細取得 API を定期的に呼び出し、status フィールドをポーリングしてください。
