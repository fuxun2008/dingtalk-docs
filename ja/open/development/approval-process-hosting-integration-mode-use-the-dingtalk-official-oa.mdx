# 承認フローホスティング：DingTalk の承認フローとサードパーティページを連携する

## 概要

本ソリューションでは、承認フローホスティング連携モードを使用します。DingTalk の公式 OA 承認の作業フローエンジンと、サードパーティが構築したカスタム業務ページを連携します。業務システムは DingTalk の OA承認 API を呼び出して承認ワークフローインスタンスを作成し、その際にサードパーティ承認システムの詳細ページ URL を指定します。承認者が DingTalk で承認の詳細を開くと、DingTalk は承認者を業務システムのカスタムページへ自動的にリダイレクトし、そこで承認を完了します。DingTalk 公式の作業フローエンジンを再利用しながら、複雑な業務フォームの独自表示を維持できるため、低コストで迅速に連携できます。

### 背景

多くの組織では、独自の承認フローとページを備えたサードパーティの OA システムを構築または導入しています。従業員は複数のシステムを行き来して承認を処理する必要があり、業務が分断され効率が低下します。自社の承認フローを DingTalk の OA承認センターに接続すると、ユーザーは DingTalk 上で業務システムのページを開いて直接承認でき、ワンストップの体験を実現できます。

組織が直面しがちな課題は次のとおりです。

- **承認の入口が分散している：** 従業員は複数のシステムで個別に承認を処理しています。DingTalk ToDo のリマインダーは自社システムの承認タスクを対象としないため、タスクの見落としが発生しやすくなります。
- **承認体験が統一されていない：** 自社システムの承認ページは DingTalk のスタイルと一致していません。ユーザーは異なる操作方法に慣れる必要があり、習得の負担が増えます。
- **ToDo 通知が届きにくい：** 自社システムはメールや SMS で承認を通知しています。これらの手段は即時性に欠け、DingTalk のメッセージプッシュや ToDo センターを活用できません。
- **承認データが孤立している：** 承認ステータスや処理記録などのデータがシステムごとに分散しています。管理者は DingTalk で承認の進捗を一元的に確認できません。

### 主な価値

本ソリューションは、次の 3 つの面で価値を提供します。

- **柔軟な連携：** DingTalk 公式 OA 承認の作業フローと、サードパーティのカスタム業務ページを組み合わせます。公式 OA 承認エンジンの作業フロー機能を再利用し、DingTalk のチャット・ToDo・通知とシームレスに連携して、効率的な承認を実現します。
- **コスト削減：** サードパーティのカスタム業務ページを承認の詳細ページとして使用します。すべてのフォームコンポーネントのフィールドを DingTalk に同期する必要はありません。連携の工数を削減し、ユーザーが使い慣れたフローとページレイアウトを維持できます。
- **統一された体験：** 業務システムから承認フローを開始し、DingTalk 公式の OA承認 API を呼び出して OA承認フローを作成します。承認者は DingTalk の OA承認・ToDo・メッセージカードから業務システムのカスタムページを直接開けるため、一貫した体験が得られます。

### ユースケース

本ソリューションは、DingTalk 公式の作業フローエンジンを利用したいものの、フォームページが複雑な業務システムに適しています。代表的なケースは次のとおりです。

- **複雑なフォームの承認：** 業務システムの承認フォームに多数のカスタムコンポーネントフィールドがあります。DingTalk の管理コンソールで 1 つずつ設定するのは現実的ではないため、カスタムページでフォーム全体をレンダリングする必要があります。
- **既存システムとの連携：** 成熟した承認ページと操作ロジックがすでにあります。最小限の変更で DingTalk の作業フローを導入し、既存のユーザー体験を維持したい場合に適しています。
- **システム横断の共同承認：** 承認フローで複数の業務システム間のデータ連動が必要です。カスタムページでシステム横断の情報をリアルタイムに照会・表示する必要があります。

## 代表的な業務シナリオ

### シナリオ 1：大手メーカーの生産指示書承認（製造業）

#### 課題

ある大手メーカーは、自社開発の MES システムで生産指示書を管理しています。指示書の承認には、設備番号、工程ルート、部品表、品質検査基準など数十のフィールドが含まれます。また、ERP の在庫データや PLM の図面とリアルタイムに連携する必要もあります。既存のフローには次の課題があります。

- **フォーム設定の負担が大きい：** 指示書の全フィールドを DingTalk OA承認の管理コンソールに同期するには、数百のコンポーネントマッピングを保守する必要があります。フィールドを追加するたびに DingTalk の設定と業務システムの両方を変更する必要があり、保守コストが増大します。
- **データ連動ができない：** DingTalk 標準の承認フォームでは、ERP の在庫や PLM の図面をリアルタイムに照会できません。承認者はシステム間を行き来する必要があり、処理が遅くなります。
- **ユーザーの操作習慣が崩れる：** 現場の班長は MES の指示書承認カスタムページを長年使用しており、そのレイアウトやショートカットキーに慣れています。DingTalk 標準フォームに切り替えると習得の負担が増し、強い抵抗が予想されます。

#### 価値の検証

- **自動化されたフロー**

  自動化された統合フローは、次の 5 つのステップで構成されます。

  1. **MES で指示書を発行** — 生産計画 / 指示書の作成。
  2. **承認インスタンスを作成** — 連携インターフェース / インスタンスの作成。
  3. **DingTalk 内で承認** — 承認ルーティング / フォームの表示。
  4. **承認者による処理** — モバイルでの承認 / 迅速な処理。
  5. **結果を MES に同期** — ステータスの書き戻し / データ同期。

  従来の手作業によるフロー（Excel にエクスポート → メール送信 → 手入力 → 複数回のメールのやり取り → 手作業でのアーカイブ）は、非効率でミスが起こりやすく、追跡が難しく、体験も良くありません。これに対し、自動化されたフロー（MES システム → DingTalk 承認 → モバイルでの承認 → MES へのデータ書き戻し）は、効率と正確性が高く、追跡が可能で、より良い体験を提供します。
- **主なメリット**

  - **フォーム移行が不要：** MES 指示書の数十のフィールドを DingTalk の管理コンソールに同期せず、カスタムページで直接レンダリングします。フィールドを追加しても MES のフロントエンドを変更するだけで済み、DingTalk 側の変更は不要です。
  - **リアルタイムのデータ連動：** カスタムページから ERP と PLM の API を直接呼び出します。承認者は在庫残数、図面のバージョン、過去の指示書を 1 つのページで確認でき、意思決定の効率が 50% 以上向上します。
  - **シームレスな体験：** 現場の班長は使い慣れた MES の承認画面と作業フローをそのまま使用できます。基盤の作業フローのみが DingTalk のエンジンに切り替わるため、研修コストはほぼゼロです。

### シナリオ 2：金融機関の与信審査システム連携（金融業）

#### 課題

ある商業銀行は、自社開発の与信審査システムでローン申請を処理しています。承認フォームには、顧客の信用情報レポート、収入証明、担保評価、リスク格付けモデルの出力結果などの機密データが含まれます。また、承認段階に応じて異なるフィールドの組み合わせを表示する必要があります。既存のフローには次の課題があります。

- **データの安全性に関する懸念：** 信用情報レポートや収入証明などの機密フィールドを DingTalk OA承認の管理コンソールに同期すると、データ漏えいのリスクが生じるため、コンプライアンス部門の承認が得られません。
- **複雑な動的フィールド：** 与信審査には一次審査、二次審査、最終審査の 3 段階があります。段階ごとに表示するフィールドやコンポーネントが異なります。DingTalk 標準フォームでは、条件付きレンダリングや動的な表示・非表示のロジックに対応しにくいという問題があります。
- **承認チェーンが長い：** 承認者はすべての資料を確認するために与信システムと DingTalk を何度も行き来する必要があり、1 件の承認につき平均 15 分の余分な時間がかかります。

#### 価値の検証

- **自動化されたフロー**

  統合フローは、次の 5 つのステップで構成されます。

  1. **融資システムで申請** — ローン申請 / フォームの作成。
  2. **承認インスタンスを作成** — `detailUrl` を指定し、`instanceId` を取得。
  3. **DingTalk 内で承認** — 承認ルーティング / フォームの表示。
  4. **承認者による処理** — **却下** と **承認** ボタンを使ってモバイルで承認し、**承認コメント** 欄に承認コメントを入力。
  5. **結果を融資システムに同期** — ステータスの書き戻し / データ同期。
- **主なメリット**

  - **機密データを社内に留める：** 信用情報レポートや収入証明などの機密フィールドは与信システムのカスタムページにのみ表示され、DingTalk の管理コンソールを経由しないため、金融コンプライアンスの要件を満たします。
  - **適応型の動的フォーム：** カスタムページは承認段階に応じてフィールドの組み合わせと検証ルールを自動的に切り替えます。一次審査では基本情報、二次審査ではリスク評価を追加し、最終審査では最終結論を表示するため、ロジックが明確に保たれます。
  - **承認効率の向上：** 承認者はシステムを切り替えることなく、1 つのページですべての資料を確認して処理できます。1 件あたりの承認時間が 12 分短縮され、1 日の処理件数が 30% 増加します。

## 導入ガイド

### 技術アーキテクチャ

本ソリューションの技術アーキテクチャは、次の主要コンポーネントで構成されます。

- **認証レイヤー：** アプリ認証情報を管理してアクセストークンを取得し、すべての API 呼び出しの呼び出し元を検証します。
- **作業フローエンジンレイヤー：** DingTalk 公式 OA 承認の作業フローエンジンを再利用し、承認ルーティング、ノードのルーティング、タスクの割り当てなどの主要ロジックを処理します。
- **ページ統合レイヤー：** 承認の開始時にサードパーティの詳細ページ URL を指定し、DingTalk で開かれた際に業務システムのカスタムページへリダイレクトします。
- **イベントコールバックレイヤー：** DingTalk OA承認のインスタンスステータスの変更と承認タスクのコールバックイベントを監視し、業務システム側の承認ステータスを同期します。

### 前提条件

- **App の準備：** [App の作成と設定](/ja/open/dingstart/create-application)を完了してください。
- **権限の要件：** DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請してください。

  - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）
  - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）
  - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）
- **開発環境：** Java 開発環境（JDK 1.6 以降）と Maven ビルドツールをインストールしてください。
- **SDK の準備：** DingTalk のサーバーサイド SDK をダウンロードしてください。Java、Python、Go などの言語に対応しています。

### コードの実装

ステップ 1：App の詳細ページに移動し、クライアント ID と Client Secret を取得します。

ステップ 2：API 権限を申請します。「OA承認」に関連する権限を申請してください。

ステップ 3：App のアクセス認証情報を取得します。[社内アプリのアクセストークンを取得](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。API を呼び出す際、アクセストークンによって呼び出し元が認証されます。

ステップ 4：OA承認 API を呼び出します。

1. 新しいサーバー API [承認フォームテンプレートの作成または更新](/ja/open/development/create-an-approval-form-template)を呼び出し、テンプレートの一意のコード `processCode` を取得します。
2. 承認テンプレートの作成後、ユーザーは DingTalk OA承認の管理コンソールで、公式 OA 承認フォームテンプレートの表示と **編集**、テンプレートデータの表示と検索、テンプレートデータのエクスポートと削除を行えます。
3. テンプレートコード `processCode` を使用して新しいサーバー API [承認インスタンスの作成](/ja/open/development/create-an-approval-instance)を呼び出し、承認インスタンスを開始して承認インスタンス ID `instanceId` を取得します。
4. 承認インスタンスの作成後、DingTalk の OA承認センターで 4 つの承認リスト（未処理、処理済み、申請済み、CC 受信）の表示、承認インスタンスデータの検索、承認操作を行います。
5. 承認コメントに添付ファイルを追加するには、まずファイルを承認用ドライブスペースにアップロードしてから、新しいサーバー API [承認コメントの追加](/ja/open/development/official-approval-adds-approval-comments)を呼び出します。
6. 新しいサーバー API [承認用ドライブスペース情報の取得](/ja/open/development/obtains-the-information-about-approval-nail-disk)を呼び出し、ドライブスペースへのアップロード権限と承認用ドライブスペース ID `spaceId` を取得します。
7. クライアントサイドの JSAPI `uploadAttachmentToDingTalk` を呼び出し、ファイルの基本情報を取得します。この例では [JSAPI Explorer](https://open.dingtalk.io/tools/explorer/jsapi?id=10318) を使用します。
8. 承認用ドライブスペースの `spaceId` を取得したら、承認インスタンスの `instanceId` を指定して新しいサーバー API [承認コメントの追加](/ja/open/development/official-approval-adds-approval-comments)を呼び出し、承認フォームにコメントを追加します。
9. 添付ファイルをプレビューまたはダウンロードするには、サーバー API [承認ドライブファイルのダウンロード権限付与](/ja/open/development/download-the-approval-nail-file)と[承認添付ファイルのプレビュー権限付与](/ja/open/development/official-authorized-preview-approval-attachment)を呼び出し、承認ドライブファイルへのアクセスを許可します。次に、サーバー API [承認添付ファイルのダウンロード](/ja/open/development/download-an-approval-attachment)を呼び出してファイルリンク `downloadUri` を取得し、ファイルをダウンロードします。詳しいチュートリアルは、[OA承認連携：承認内の添付ファイルのダウンロードとプレビュー](/ja/open/development/new-version-of-attachment-approval-process)を参照してください。
10. 業務システムは承認インスタンスの `instanceId` を使用して新しいサーバー API [単一承認インスタンスの詳細取得](/ja/open/development/obtains-the-details-of-a-single-approval-instance-pop)を呼び出し、承認インスタンスの詳細と各承認タスクノードの情報を取得します。
11. 承認インスタンスの `instanceId` と `taskId` を使用して新しいサーバー API [承認タスクの承認または却下](/ja/open/development/approve-or-reject-the-approval-task)を呼び出し、承認タスクを処理します。
12. 提出済みの承認フォームに誤りがあり、承認インスタンスを取り消す必要がある場合は、承認インスタンスの `instanceId` を指定して新しいサーバー API [承認インスタンスの取り消し](/ja/open/development/revoke-an-approval-instance)を呼び出し、承認フォームを取り消します。
13. 承認フォームのステータスが変化すると、OA承認は業務システムにコールバックイベントをプッシュします。対象となるイベントは、承認タスクの開始・終了・転送、および承認インスタンスの開始・終了・終止・削除です。

## 実装手順

### **ステップ 1：アプリ認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/)にログインします。
2. 対象の App を選択し、App の詳細ページを開きます。
3. **基本情報** > **認証情報と基本情報** をクリックします。
4. App の `Client ID` と `Client Secret` を控えておきます。

### 注意

   `Client Secret` は厳重に管理し、第三者と共有しないでください。ハードコーディングせず、環境変数またはキー管理システムに保存してください。

### ステップ 2：API 権限を追加する

1. App の詳細ページで **権限管理** をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）：承認フォームテンプレートを作成または更新します。
   - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）：承認インスタンスを開始し、承認結果を送信します。
   - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）：承認インスタンスの詳細と承認タスクの情報を取得します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。シナリオに必要な権限を申請してください。
</Note>

### ステップ 3：アクセス認証情報（アクセストークン）を取得する

ステップ 1 で取得した Client ID と Client Secret を使用して、App のアクセス認証情報を取得します。[社内アプリのアクセストークンを取得](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ戦略**：`accessToken` の有効期限は 2 時間です。メモリまたは Redis にキャッシュし、有効期限が切れる5分前に事前に更新してください。
- **同時実行制御**：複数のスレッドが同時にトークンを更新して競合が発生するのを防ぐため、分散ロックを使用してください。
- **エラー時のリトライ**：ネットワークが不安定な場合は自動的にリトライします。最大 3 回まで、間隔を段階的に延ばしてください（1 秒 → 2 秒 → 4 秒）。

### 実装チェックリスト

- ✅ App を作成し、Client ID と Client Secret を取得済みである。
- ✅ Workflow.Form.Write、Workflow.Instance.Write、Workflow.Instance.Read の権限が付与されている。
- ✅ アクセストークンを正常に取得し、キャッシュ戦略を設定済みである。
- ✅ 承認フォームテンプレートの作成または更新 API を正常に呼び出せる。
- ✅ detailUrl を指定して承認インスタンスを開始し、API 呼び出しが成功する。
- ✅ 承認タスクの承認または却下 API を正常に呼び出せる。
- ✅ 承認インスタンスのコールバックイベントを登録し、正しく受信できる。
- ✅ DingTalk からサードパーティの詳細ページ URL へ正しくリダイレクトされる。
- ✅ 業務システムの承認ステータスが DingTalk の承認インスタンスのステータスと同期している。
- ✅ フロントエンドでカスタム承認ページをレンダリングし、承認操作を送信できる。
- ✅ 権限によるフィルタリングが機能し、ロールごとに異なる承認タスクが表示される。

## よくある質問

- **Q：detailUrl 内の `{processInstanceId}` プレースホルダはどのように置き換えられますか？**

  DingTalk が承認の詳細を開く際に、`{processInstanceId}` を実際の承認インスタンス ID に自動的に置き換えます。業務システム側での処理は不要です。追加のパラメーターを渡す場合は、URL にカスタムのクエリ文字列を付加してください。
- **Q：サードパーティの詳細ページは DingTalk のサイレントログインに対応する必要がありますか？**

  はい。承認者が DingTalk からサードパーティの詳細ページへリダイレクトされる際、DingTalk はサイレントログイン用の認可コードパラメーター `code` を URL に付加します。業務システム側でサイレントログインを実装する必要があります。
- **Q：承認インスタンスのコールバックイベントのプッシュ先 URL はどのように設定しますか？**

  DingTalk 開発者コンソールの App の詳細ページで、イベントサブスクリプションにサブスクリプションを追加し、業務システムの HTTPS のコールバック URL を入力します。DingTalk はイベントデータを JSON 形式で POST によりプッシュします。
- **Q：サードパーティの詳細ページの読み込みに失敗した場合やタイムアウトした場合、DingTalk はどのように処理しますか？**

  DingTalk はデフォルトのエラーページを表示し、承認フロー自体は停止しません。詳細ページの高可用性を確保し、読み込みに失敗した場合はわかりやすいエラーメッセージとリトライ機構を提供してください。
- **Q：カスタムページで送信した承認結果は DingTalk ToDo に同期されますか？**

  はい。承認タスクの承認または却下 API で承認結果を送信すると、DingTalk ToDo の該当タスクのステータスが自動的に更新され、承認者に通知が届きます。
