# 公式 OA 承認：DingTalk のフローおよびページとの連携

## 概要

### 背景

企業が独自に構築または導入した業務システムには、通常それぞれ独自の承認フローと承認ページがあります。そのため、従業員は複数のシステムを切り替えながら承認を処理する必要があり、業務が分断されて効率が低下します。業務システムの承認を DingTalk 公式 OA 承認の承認センターに接続すると、ユーザーは DingTalk の単一の入口からすべての承認を確認・処理でき、標準化されたワンストップの体験を得られます。この方法により、次の課題を解決できます。

- **システム間の切り替えによる非効率**：従業員は業務システムと DingTalk を行き来して承認を処理する必要があります。操作が煩雑で、緊急の案件を見落としやすくなります。
- **承認ステータスの不整合**：業務システムと DingTalk のデータが一致しません。承認の進捗をリアルタイムで把握できず、意思決定が遅れます。
- **通知チャネルの分散**：承認通知は各システムの社内メッセージやメールに依存しています。DingTalk の統一された To-Do リマインダーやメッセージプッシュ機能を活用できません。
- **管理者による確認の手間**：管理者は承認の進捗を確認するために複数のシステムにログインする必要があります。DingTalk 上で承認状況の全体を追跡できません。

### 主なメリット

本ソリューションは、DingTalk 公式 OA 承認のプロセスエンジンとフォームコンポーネントを再利用し、企業に標準化された承認体験を提供します。

- **標準化の推進**：DingTalk OA のフローとページを使用し、DingTalk のチャット、To-Do、通知とシームレスに連携して効率的に承認を処理できます。
- **ワンストップの体験**：DingTalk 公式の承認エンジンとフォームコンポーネントを再利用し、すべてのデバイスで統一された OA承認の体験をユーザーに提供します。
- **高度な統合**：チャット、To-Do、ドライブなど DingTalk の主要機能とシームレスに連携します。承認結果はコールバックイベントを通じて業務システムにリアルタイムで同期されます。
- **開発コストの削減**：承認エンジンやフォームデザイナーを自社で構築する必要はありません。DingTalk の成熟した機能を再利用して、承認フローを迅速に立ち上げられます。

### ユースケース

本ソリューションは、次のような代表的な承認連携シナリオに適しています。

- **製造業における生産作業指示の承認**：MES で作業指示の承認を申請すると、DingTalk の承認インスタンスが自動的に作成されます。承認者は DingTalk 上で作業指示の詳細を確認し、そのまま処理できます。
- **小売チェーンにおける店舗運営の承認**：店長が業務システムで申請を提出すると、承認フローが DingTalk OA承認の承認センターに自動的に集約され、一元管理されます。
- **グループ企業における部門横断のコラボレーション**：本社と支社が DingTalk の統一された承認入口からあらゆる種類の業務申請を処理し、コラボレーションを強化します。
- **成熟した承認システムを持つ組織**：申請と管理は業務システムで行いつつ、DingTalk ネイティブの承認エンジンとフォームコンポーネントを再利用します。

## 代表的な業務シナリオ

### シナリオ 1：製造業における生産作業指示の承認を統合する

#### 課題

ある製造業者は、自社開発の MES で生産作業指示の流れを管理しています。従来の承認フローはオフラインでの署名とメールでの確認に依存しており、処理が遅く追跡も困難でした。従業員は MES と DingTalk を行き来する必要があり、承認ステータスがリアルタイムで同期されないため生産に遅れが生じていました。

- 従業員は MES と DingTalk を行き来して承認を処理していました。操作が煩雑で、緊急の作業指示を見落としやすい状況でした。
- 承認ステータスは手動の同期に依存していました。MES と DingTalk のデータが一致せず、生産が遅れていました。
- 管理者は DingTalk 上で作業指示の承認進捗を確認できず、複数のシステムにログインして確認する必要がありました。
- 承認通知はメールやオフラインでの連絡に依存しており、DingTalk の統一された To-Do リマインダーやメッセージプッシュ機能を活用できませんでした。

#### 導入効果

- **フローの自動化**

  統合フローは次の 5 つのステップで構成されます。

  1. MES で作業指示を申請します。
  2. 連携 API が DingTalk で**承認インスタンスを作成**します。
  3. 承認は **DingTalk 内で**処理されます。作業指示の承認フォームには、**作業指示番号**、**作業指示の種類**、**申請部門**、**優先度**、**申請者**などのフィールドと、**承認を申請**ボタンが表示されます。
  4. 承認者がモバイルで**却下**または**承認**の操作を行います。
  5. 結果が **MES に同期**されます。

  従来の手動フロー（指示書をエクスポート > メールを送信 > 手動で処理 > メールで通知 > 結果を記録）と比べて、自動化されたフローでは入口が統一され、リアルタイムで同期され、メッセージ通知がプッシュされます。
- **主な利点**

  - **生産作業指示の承認を統合：** MES で作業指示の承認を申請すると、DingTalk の承認インスタンスが自動的に作成されます。承認者はシステムを切り替えることなく、DingTalk 上で作業指示の詳細を確認して処理できます。
  - **承認フローをリアルタイムで可視化：** DingTalk には部品表、品質検査要件、過去の作業指示を含む作業指示の全データが表示されます。承認の進捗がひと目でわかり、コメントやリマインダーにも対応しています。
  - **エンドツーエンドのデータ同期：** 承認結果は MES にリアルタイムで書き戻されます。却下された場合は、後続の To-Do が自動的にキャンセルされます。双方のデータの一貫性とトレーサビリティを確保し、承認の処理時間を 60% 以上短縮します。

### シナリオ 2：小売チェーンにおける店舗運営の承認

#### 課題

ある小売チェーンは全国で数百の店舗を運営しており、店舗改装、販促、人員異動などの承認が頻繁に発生します。店長が申請を提出した後、承認フローが複数のシステムに分散していたため、エリアマネージャーや本社の責任者が一か所で処理することが難しく、承認の応答時間が長くなっていました。

- 店長は複数の業務システムでそれぞれ申請を提出していました。操作が煩雑で、重要な情報を見落としやすい状況でした。
- 承認フローが複数のシステムに分散していました。エリアマネージャーや本社の責任者は複数のプラットフォームにログインし、承認を 1 件ずつ処理する必要がありました。
- 承認通知は各システムの社内メッセージに依存しており、DingTalk の統一された To-Do リマインダーやメッセージプッシュ機能を活用できませんでした。
- 管理者は DingTalk 上で全店舗の承認進捗を確認できず、複数のシステムにログインして集計する必要がありました。

#### 導入効果

- **フローの自動化**

  エンドツーエンドの承認フローは次のとおりです。

  1. 店舗が申請を提出します。
  2. 申請が API を通じて DingTalk に集約されます。
  3. 申請が DingTalk OA の統一された**承認センター**に登録されます。
  4. エリアマネージャーが承認します。
  5. 本社の責任者が承認します。
- **主な利点**

  - **店舗承認の入口を統一：** 店長が業務システムで申請を提出すると、承認フローが DingTalk OA承認の承認センターに自動的に集約されます。エリアマネージャーと本社の責任者は、すべての承認を DingTalk で処理できます。
  - **To-Do とメッセージをリアルタイムで配信：** DingTalk の To-Do リマインダーとメッセージ通知により、承認タスクが承認者に即座にプッシュされるため、緊急の承認を見落としません。
  - **承認の応答時間を 80% 短縮：** 承認の平均応答時間が 2 日から 4 時間未満に短縮されました。店舗運営の意思決定が大幅に迅速化し、数百店舗の効率的な管理を支えています。

## 実装ガイド

### 技術アーキテクチャ

本ソリューションの技術アーキテクチャは、次の主要コンポーネントで構成されます。

- **認証レイヤー**：アプリの認証情報を管理してアクセストークンを取得し、すべての API 呼び出しの ID を検証します。
- **承認テンプレート管理レイヤー**：承認フォームテンプレートの作成・更新・照会を行い、業務システムの承認フォーム構造を DingTalk OA承認の承認センターに同期します。
- **承認インスタンスエンジン**：承認インスタンスの申請・取り消し・ステータス管理を行い、承認フローのライフサイクルを制御します。
- **承認タスク処理レイヤー**：タスクノードを照会し、承認・却下・転送の操作を実行して承認フローをノード間で進めます。
- **添付ファイル・コメントサービス**：承認用ドライブスペースへの権限付与、ファイルのアップロードとダウンロード、承認コメントの管理を行い、リッチメディアによる承認操作をサポートします。
- **イベントコールバックチャネル**：承認タスクと承認インスタンスのステータス変更イベントを業務システムにプッシュし、承認データをリアルタイムで双方向に同期します。

### 前提条件

- **アプリの準備**：[アプリの作成と設定](/ja/open/dingstart/create-application)を完了していること。
- **権限要件**：DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請していること。

  - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）
  - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）
  - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）
- **開発環境**：Java 開発環境（JDK 1.6 以降）と Maven ビルドツールをインストールしていること。
- **SDK の準備**：DingTalk のサーバーサイド SDK をダウンロードしていること。Java、Python、Go など複数の言語に対応しています。

### コードの実装

ステップ 1：アプリの詳細ページに移動し、アプリの Client ID と Client Secret を取得します。

ステップ 2：API 権限を申請します。関連する「OA承認」の権限を申請してください。

ステップ 3：アプリのアクセス認証情報を取得します。詳しくは、[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。API を呼び出す際、アクセストークンによって呼び出し元の ID が認証されます。

ステップ 4：サーバーサイドの OA承認 API を呼び出します。

1. サーバー API [承認フォームテンプレートを作成または更新する](/ja/open/development/create-an-approval-form-template)を呼び出して公式 OA 承認のテンプレートを作成し、一意のコード processCode を取得します。
2. サーバー API [承認インスタンスを作成する](/ja/open/development/create-an-approval-instance)を呼び出し、テンプレートコードに基づいて承認インスタンスを申請し、インスタンス ID の instanceId を取得します。
3. サーバー API [承認用ドライブスペースの情報を取得する](/ja/open/development/obtains-the-information-about-approval-nail-disk)を呼び出し、ドライブスペースへのアップロード権限と spaceId を取得します。
4. クライアントサイドの JSAPI uploadAttachmentToDingTalk を呼び出し、承認添付ファイルをドライブスペースにアップロードします。
5. サーバー API [承認コメントを追加する](/ja/open/development/official-approval-adds-approval-comments)を呼び出し、承認インスタンスにコメントと添付ファイルを追加します。
6. サーバー API [承認用ドライブファイルのダウンロードを許可する](/ja/open/development/download-the-approval-nail-file)を呼び出し、承認用ドライブファイルのダウンロード権限を取得します。
7. サーバー API [承認添付ファイルのプレビューを許可する](/ja/open/development/official-authorized-preview-approval-attachment)を呼び出し、承認添付ファイルのプレビュー権限を取得します。
8. サーバー API [承認添付ファイルをダウンロードする](/ja/open/development/download-an-approval-attachment)を呼び出し、添付ファイルのダウンロードリンク downloadUri を取得します。
9. サーバー API [単一の承認インスタンスの詳細を取得する](/ja/open/development/obtains-the-details-of-a-single-approval-instance-pop)を呼び出し、承認インスタンスの詳細と各タスクノードの taskId を取得します。
10. サーバー API [承認タスクを承認または却下する](/ja/open/development/approve-or-reject-the-approval-task)を呼び出し、指定したタスクノードを承認または却下します。
11. サーバー API [承認インスタンスを取り消す](/ja/open/development/revoke-an-approval-instance)を呼び出し、申請済みの承認インスタンスを取り消します。
12. 承認タスク変更のコールバックイベントをサブスクライブし、タスクの開始、終了、転送などのステータス変更通知を受信します。
13. 承認インスタンス変更のコールバックイベントをサブスクライブし、インスタンスの開始、終了、終了処理、削除などのステータス変更通知を受信します。

## 実装手順

### **ステップ 1：アプリの認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/)にログインします。
2. 対象のアプリを選択して、アプリの詳細ページを開きます。
3. **基本情報** > **認証情報と基本情報**をクリックします。
4. アプリの `Client ID` と `Client Secret` を控えておきます。

### 注意

   `Client Secret` は安全に保管し、第三者と共有しないでください。ハードコードせず、環境変数またはキー管理システムに保存してください。

### ステップ 2：API 権限を追加する

1. アプリの詳細ページで、**権限管理**をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）：承認フォームテンプレートを作成・更新します。
   - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）：承認インスタンスを申請・取り消します。
   - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）：承認インスタンスの詳細を照会します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。実際の要件に応じて申請してください。たとえば、一括インポートのシナリオでは、ユーザーの一括操作に関する権限も必要です。
</Note>

### ステップ 3：アクセス認証情報（アクセストークン）を取得する

ステップ 1 で取得した Client ID と Client Secret を使用して、アプリのアクセス認証情報を取得します。詳しくは、[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ**：`accessToken` の有効期間は 2 時間です。メモリまたは Redis にキャッシュし、有効期限の5分前に更新してください。
- **同時実行の制御**：複数のスレッドが同時にトークンを更新することによる競合を防ぐため、分散ロックを使用してください。
- **エラー時の再試行**：ネットワークが不安定な場合は自動的に再試行します。再試行は最大 3 回とし、間隔を段階的に延ばしてください（1 秒 → 2 秒 → 4 秒）。

### ステップ 4：主要な API を呼び出す

1. **承認フォームテンプレートを作成または更新する：** 管理者は OA 管理コンソールでテンプレートを手動で作成できます。または、新しいサーバー API [承認フォームテンプレートを作成または更新する](/ja/open/development/create-an-approval-form-template)を呼び出して、テンプレートの一意のコード `processCode` を取得します。

   **注意** 
   - API から返されたテンプレートコード `processCode` を業務システムで保存していない場合は、DingTalk の管理コンソールにログインして確認してください。
   - テンプレートの作成後は、DingTalk OA承認の管理コンソールで公式 OA 承認のフォームテンプレートを**表示・編集**したり、テンプレートデータの表示・検索、エクスポート・削除を行ったりできます。

   管理コンソールで公式 OA 承認のフォームテンプレートを作成または更新する場合は、**基本設定** > **フォーム設計** > **フロー設計** > **高度な設定**の 4 つのステップで設定し、**プレビュー**または**公開**をクリックします。**基本設定**のステップには、次のフィールドがあります。

   | フィールド | 説明 |
   | --- | --- |
   | **フォーム名** | 必須、最大 50 文字 |
   | **グループ** | 必須 |
   | **フォームの説明** | 最大 100 文字 |
   | **申請可能なユーザー** | 適用範囲を選択します |
   | **テンプレート管理者** | テンプレートの編集とデータのエクスポートが可能です |

   テンプレートの `processCode` はページ下部に表示されます。

   ```json
   {
     "name": "DingTalk OA承認のフローおよびページとの連携",
     "description": "業務システムでフローを申請し、DingTalk 公式 OA 承認の API を呼び出して DingTalk OA の承認フローを作成し、DingTalk の承認詳細ページで処理します。",
     "templateConfig": {
       "disableStopProcessButton": false,
       "disableFormEdit": false,
       "disableHomepage": false,
       "hidden": false
     },
     "formComponents": [
       {
         "componentType": "TextField",
         "props": {
           "label": "1行入力", // コンポーネントのタイトル
   ```

- ✅ 承認コメントの添付ファイルのアップロードとダウンロードを検証済みである。
- ✅ 承認タスクと承認インスタンスのコールバックイベントのサブスクリプションを設定し、ステータス変更がリアルタイムでプッシュされる。

## FAQ

- **Q1：承認テンプレートを作成する際、formComponents の componentId にはどのような要件がありますか？**

  componentId はフォーム内で一意である必要があります。業務上の意味は持たず、コンポーネントの識別にのみ使用されます。業務識別子を使用する場合は、代わりに bizAlias フィールドを使用してください。
- **Q2：承認インスタンスを作成する際、approvers の actionType にはどのような値を指定できますか？**

  actionType には、NONE（単一の承認者）、OR（いずれかの承認者が承認するとタスクが承認される）、AND（すべての承認者の承認が必要）などの値を指定できます。詳しくは API ドキュメントを参照してください。
- **Q3：保存していない processCode はどのように取得できますか？**

  承認テンプレートの作成時に返された processCode を保存していない場合は、DingTalk OA承認の管理コンソールにログインして確認するか、テンプレートコードを取得する API を呼び出してください。
- **Q4：承認添付ファイルをアップロードする前に、ドライブスペースの情報を取得する必要がありますか？**

  はい、必要です。承認コメントに添付ファイルを追加する前に、承認用ドライブスペースの情報を取得する API を呼び出して、spaceId とアップロード権限を取得してください。次に、JSAPI を使用してファイルをドライブスペースにアップロードします。最後に、承認コメントを追加する API を呼び出して添付ファイルを関連付けます。
- **Q5：承認のコールバックイベントはどのように設定しますか？**

  開発者コンソールでイベントサブスクリプションを設定します。「承認タスクの変更」と「承認インスタンスの変更」のイベントを選択し、業務システムのコールバック URL を入力してください。詳しくは、イベントプッシュ方式の設定ガイドを参照してください。
