## よくある質問

**スクリーンショットを撮影する際は、ツールのインターフェイス全体（リクエスト内容とレスポンス内容を含む）をキャプチャしてください。圧縮せずにそのままレポートに添付してください。**

1. Q: レポートにはどのような情報を記載する必要がありますか。すべてのテストケースをテストする必要がありますか。

   A: レポートに指定されているすべてのテストケースは、必須のセキュリティチェックポイントです。レポートは、セキュリティ評価時に注意すべき代表的なリスクタイプを示しています。ISV は、レポートの要件と自社のビジネスタイプに基づいて、**該当するすべての API に対してセキュリティテストを実施する必要があります。レポートには主要な API のテストプロセスを反映すべきですが、実際のテスト範囲はレポートに反映された API テストに限定されません。**
2. Q: 当社には専任のセキュリティ担当者がいません。セキュリティ評価レポートの提出を省略できますか。

   A: いいえ。レポートには、Burp Suite など、各テストケースで推奨されるテスト方法とツールが記載されています。これらのツールの詳細な使用ガイドラインはオンラインで確認できます。ビジネスの公開後の安全を確保するため、公開前のセキュリティテストは必須かつ不可欠です。
3. Q: レポートの各テストケースには、テスト基準の要件がありますか。

   A: テストケースは、データチェックとセキュリティテストの 2 種類に分類されます。データチェックは、ポートスキャンやミドルウェア情報の使用に類似しています。データの変更は伴いませんが、システムの実際の状態を記録し、必要な情報を提供する必要があります。ツールを使用して実施するチェックについては、Nmap のスキャン結果など、スクリーンショットを提供する必要があります。

   **セキュリティテストケースについては、以下の基準に従ってください。**

   1. **システムに通常のリクエストを送信させます。ツールを使用して、通常のリクエストとサーバーサイドのレスポンスのスクリーンショットをキャプチャし、さらにビジネスアプリのページに表示される情報のスクリーンショットもキャプチャします。**
   2. **ツール内でネットワークリクエスト情報を変更します（例：ID の変更）。変更後のネットワークリクエストとサーバーサイドのレスポンスのスクリーンショットをツール内でキャプチャし、さらにビジネスアプリのページで返された結果のスクリーンショットもキャプチャします。**
   3. **ツールのスクリーンショットとビジネスアプリのスクリーンショットの両方をレポートに添付します。**
4. Q: レポートに記載されているテストケースが自社のビジネスに存在しない場合は、どうすればよいですか。

   A: その場合は、該当しない理由、または使用している代替技術を記載してください。たとえば、SMS モジュールがない場合は、SMS 機能を使用していないことを記載します。
5. Q: すでにパラメータ改ざん防止を実装しています。権限検証テストの目的は何ですか。

   A: パラメータ改ざん防止と権限検証は、対象とするシナリオが異なります。前者はデータの偽造を防ぎ、データの整合性を検証します。一部の API では、正規のユーザーが権限のないデータへのアクセスを試みる場合があります。たとえば、他部門の情報を閲覧するケースです。送信された情報は有効ですが、操作者が権限の範囲外にあります。
6. Q: テスト手順が多いのですが、スクリーンショットを省略できますか。

   A: テストの目的は、リスクをできるだけ早く発見し、ビジネスの公開後の安全を確保することです。スクリーンショットはテストプロセスを記録するために使用します。DingTalk セキュリティチームはスクリーンショットの情報を分析し、潜在的な追加のビジネスリスクの特定を支援するため、スクリーンショットは不可欠です。
7. Q: ビジネスの公開前に実施したテストが、レポートで要求される範囲より広範囲だった場合は、どうすればよいですか。

   A: セキュリティレポートでカバーされていないシナリオを他の方法でテストした場合は、その内容をドキュメントにまとめ、ワークシートに新しいワークシートとして添付することをお勧めします。DingTalk セキュリティチームがレポートの分析とリスク評価を支援します。
8. Q: テストのスクリーンショットの目的は何ですか。

   A: スクリーンショットの目的は、テスト方法が正しいかどうか、およびテストが要求どおりに実施されたかどうかを確認することです。

### NO.04 権限昇格の脆弱性

使用ツール: パケットキャプチャツール

1. **脆弱性の概要:**

URL に直接アクセスしたり、ID などの URL パラメータを変更したりすることで、他人のエントリに属する情報を閲覧でき、場合によっては変更することも可能になります。

2. **根本原因:**

ユーザー ID（ユーザー ID）が URL パラメータまたは暗号化されていない cookie から取得され、データクエリや機能操作の根拠として使用されています。ユーザーがこのパラメータを変更できるため、水平方向または垂直方向の権限昇格が発生します。

3. **修正計画:**

適切なユーザー ID 検証を実装します。現在のユーザーが操作を実行する権限を持っているかどうかを検証します。URL パラメータを読み取って現在のユーザー ID を判定するのではなく、暗号化された cookie またはセッションからユーザー ID 情報を取得します。

4. **テスト方法:**

自社のビジネスシナリオに基づいてテストします。

- **水平方向の権限昇格:** たとえば、注文情報を閲覧するシナリオを考えます。ユーザー A の注文番号は 1、ユーザー B の注文番号は 2 です。ユーザー A は `.com/my?orderid=1` にアクセスして、注文番号 1 の自分の注文を閲覧します。パケットキャプチャツールを使用してリクエスト内の API パラメータを変更し、ユーザー A の `.com/my?orderid=1` リクエストの `orderid=1` を `orderid=2` に変更して、注文番号 2 のユーザー B の注文情報を取得できるかどうかを確認します。情報を閲覧できる場合、水平方向の権限昇格の脆弱性が存在します。同様に、情報を閲覧するシナリオに加えて、追加/削除/変更操作 API も同じ方法でテストします。
- **垂直方向の権限昇格:** たとえば、情報を変更するシナリオを考えます。ユーザー A の注文番号は 1 ですが、ユーザー A には自分の注文情報を変更する権限がありません。管理者 B にはすべての注文情報を変更する権限があります。管理者 B は `.com/my?orderid=all` API にアクセスすることで、すべての注文を閲覧できます。ユーザー A に、本来は管理者のみが操作できるべき API である `.com/my?orderid=all` にアクセスさせ、すべての注文情報を取得できるかどうかを確認します。取得できる場合、垂直方向の権限昇格の脆弱性が存在します。同様に、情報の閲覧および追加/削除/変更操作 API のシナリオも同じ方法でテストします。

5. **テスト結果:**

表を記入し、テストのスクリーンショットを添付してください。

**要件: すべての API をテストし、権限昇格の脆弱性が存在しないようにする必要がありますが、スクリーンショットは一部の API のテストのみを示すことができます。**

**スクリーンショット要件: 少なくとも 2 枚のスクリーンショットが必要です。1 枚はユーザー A の通常のリクエストを示し、もう 1 枚はユーザー A の URL パラメータを変更したリクエストを示します。スクリーンショットには、リクエストした URL と返却された内容が表示されている必要があります。**

### NO.05 クロスサイトスクリプティング（XSS）の脆弱性（ミニプログラムはこのテストをスキップ可）

1. **脆弱性の概要:**

悪意のある攻撃者が Web ページに悪意のある HTML コードを挿入します。ユーザーがそのページを閲覧すると、ページに埋め込まれた HTML コードが実行され、ユーザーを悪意を持って攻撃するという特殊な目的が達成されます。

2. **根本原因:**

XSS の脆弱性の原因は、攻撃者の入力が厳密に制御されず、最終的に訪問ユーザーに表示されてしまうことにあります。攻撃者は巧妙な方法で悪意のあるコマンドコードを Web ページに注入し、ユーザーに攻撃者が作成した悪意のある Web プログラムをロードして実行させます。これらの悪意のある Web プログラムは通常 JavaScript ですが、実際には Java、VBScript、ActiveX、Flash、あるいは単純な HTML も含まれます。攻撃が成功すると、攻撃者はより高い権限（特定の操作の実行など）、個人の Web ページの内容、セッション、cookie などの内容を取得する可能性があります。

3. **修正計画:**

XSS を防御するには、実際の状況に基づいてユーザーの入力を厳密にフィルタリングします。たとえば、PHP では `htmlspecialchars()` 関数を使用して、ユーザーが入力した内容を HTML エスケープします。また、cookie に httponly 属性を追加することで、ユーザーの cookie をある程度保護し、XSS が発生した際の損失を軽減できます。

4. **テスト方法:**

自社のビジネスシナリオに基づいてテストします。

たとえば、ユーザー A がフォーム情報を送信するシナリオを考えます。ユーザー A に入力フィールドで `"` や `<script>alert(123)</script>` などの HTML コードを入力させます。ユーザー A または管理者が、送信されたフォーム内容を表示するページを閲覧したときに、挿入された HTML コードが実行されるかどうか（たとえばポップアップが表示されるかどうか）を確認します。実行される場合、クロスサイトの脆弱性が存在します。

5. **テスト結果**

表を記入し、テストのスクリーンショットを添付してください。

**要件: 入力内容があるすべてのページをテストし、クロスサイトの脆弱性が存在しないようにする必要がありますが、スクリーンショットは一部の API のテストのみを示すことができます。**

**スクリーンショット要件: 少なくとも 1 枚のスクリーンショットが必要で、内容に HTML コードが挿入されたページを示します。スクリーンショットには、内容内の HTML コードが実行されていることが表示されている必要があります。**

| **入力と出力の内容があるページ** | **機能の説明** | **表示名** |
| --- | --- | --- |
| \*\*\*\*.com/my | プロフィールを変更するページ | クロスサイトの脆弱性なし |
| \*\*\*\*.com/my | プロフィールを閲覧するページ | クロスサイトの脆弱性なし |

### NO.06 SQL インジェクションの脆弱性

1. **根本原因:**

SQL インジェクション攻撃は、ユーザーが制御可能なパラメータに SQL 構文を注入し、元の SQL 構造を破壊して、開発者が意図しない結果を達成する攻撃と説明できます。その原因は、以下の 2 つの要因の組み合わせに起因します。

- アプリケーションとデータベースのインタラクションを処理する際、開発者が文字列連結を使用して SQL 文を構築している。
- ユーザーが制御可能なパラメータが、その内容が SQL 文に連結される前に十分にフィルタリングされていない。

2. **修正計画:**

プリコンパイルされた SQL 文を使用します。SQL 文の連結は厳格に禁止されています。たとえば、Java では MyBatis を、Python では SQLAlchemy を使用します。

Ibatis を使用する場合は、var を #var# に置き換えます

MyBatis を使用する場合は、$&#123;var&#125; を #&#123;var&#125; に置き換えます

3. **テスト結果**:

表を記入し、テストのスクリーンショットを添付してください。

**スクリーンショット要件: SQL 文の実行に関連する主要なコードのスクリーンショットを撮影し、SQL 文の連結が使用されていないことがわかるようにします。**

| SQL 操作のコード実装方法 | 表示名 |

### NO.07 クロスサイトリクエストフォージェリ（CSRF）の脆弱性

使用ツール: パケットキャプチャツール

1. **根本原因:**

攻撃者は、信頼できるユーザーからのものであるかのように見えるリクエストを偽造し、ウェブサイトのコンテンツの追加、削除、または改ざんの目的を達成します。

ユーザーが攻撃者の作成した悪意のあるリンクをクリックすると、対応する操作がユーザーに代わって「実行」されます。

たとえば、銀行の送金機能（BOB のアカウントに 100 を送金）が以下のように実装されているとします。

`GET http://bank.com/transfer.do?acct=BOB&amount=100 HTTP/1.1`

攻撃者がユーザーを誘導して以下のリンクをクリックさせたとき、ユーザーの銀行ウェブサイトへのログイン認証情報がまだ有効期限切れになっていなければ、ユーザーは知らないうちに MARIA に 100,000 を送金してしまいます。

`http://bank.com/transfer.do?acct=MARIA&amount=100000`

単純な ID 検証では、リクエストが特定のユーザーのブラウザから送信されたことしか保証できず、リクエスト自体がユーザーの意思で送信されたことは保証できません。

2. **修正計画（いずれか 1 つを選択）:**

| 修正計画 | 説明 |
| --- | --- |
| HTTP Referer フィールドを検証する | 通常、セキュリティ制限されたページにアクセスするリクエストは、同じウェブサイトから送信されます。HTTP ヘッダー内の Referer フィールドには、HTTP リクエストの送信元アドレスが記録されています。Referer 内のアドレスが本ウェブサイトから発信されたものでない場合、そのリクエストは安全でないとみなし、辞退する必要があります。この方法はシンプルで実装が容易です。既存のシステムの場合、Referer 値をチェックするフィルタを追加するだけで、現在のシステムの既存のコードやロジックを変更する必要はありません。 |
| token を追加する | CSRF 攻撃が成功するのは、攻撃者がユーザーのリクエストを偽造できるためです。これに対する最善の防御は、攻撃者がリクエストを偽造できないようにすることです。したがって、HTTP リクエストのパラメータとしてランダムな token を追加し、この token が正しいかどうかをサーバー側でチェックできます。正しくない場合や存在しない場合、そのリクエストは安全でないとみなし、関連するサービスを辞退します。 |
| 認証コードを追加する | データを送信する前に、ユーザーに認証コードを入力させます。 |

3. **テスト方法:**

たとえば、情報を変更するリクエストが以下のとおりだとします。

```
GET my?username=BOB&age=18 HTTP/1.1
Host: ***.com
Referer: ***.com/my
......
```

パケットキャプチャツールを使用して、変更リクエスト内の `Referer: ***.com/my` を他の内容に変更し、リクエストを再送信します。

```
GET my?username=BOB&age=18 HTTP/1.1
Host: ***.com
Referer: ***111.com
......
```

変更操作が正常に実行された場合、クロスサイトリクエストフォージェリの脆弱性が存在します。同様に、ランダムな token を使用している場合は token 値を変更します。変更操作が正常に実行された場合、脆弱性が存在します。すべての追加/削除/変更操作 API をテストする必要があります。

4. **テスト結果**

表を記入し、テストのスクリーンショットを添付してください。

**要件: すべての API をテストし、クロスサイトリクエストフォージェリの脆弱性が存在しないようにする必要がありますが、スクリーンショットは一部の API のテストのみを示すことができます。**

**スクリーンショット要件: 少なくとも 2 枚のスクリーンショットが必要です。1 枚は通常の Referer または token を持つリクエストを示し、もう 1 枚は変更した Referer または token を持つリクエストを示します。スクリーンショットには、リクエスト内容と返却された内容が表示されている必要があります。**

| **関連 API** | **機能の説明** | **表示名** |
| --- | --- | --- |
| \*\*\*.com/my?username=&age | プロフィールを変更する API | クロスサイトリクエストフォージェリの脆弱性なし |
| \*\*\*.com/my?delusername= | プロフィールを削除する API | クロスサイトリクエストフォージェリの脆弱性なし |

## Burp Suite の使用と証明書のインポート

### プロキシの設定

以下の図に示すようにプロキシを設定します。ポートはカスタマイズ可能です。

**PC の場合:**

Burp Suite のプロキシ待ち受けアドレスとポートを設定します。

デフォルトでは、127.0.0.1 のポート 8080 で待ち受けます。実際のテストのニーズに応じて、待ち受けアドレスやポートを追加または変更できます。

**モバイルの場合（iOS を例に）:**

Burp Suite のプロキシアドレスとポートを入力します。

**Wi-Fi** > **HTTP プロキシ** > **プロキシを設定**

### 証明書のインポート

モバイルデバイスで、ブラウザからプロキシアドレス `http://ip:port` にアクセスして、証明書をダウンロードしてインポートします。

お知らせ: iOS では、信頼を設定する必要がある箇所が 2 つあります。

1. **設定** > **一般** > **このアプリについて** > **証明書信頼設定**
2. **設定** > **一般** > **プロファイルとデバイス管理**

### パケットの傍受と改変

1. パケットを傍受し、Repeater ウィンドウに送信します。
2. Repeater ウィンドウでパケットを改変し、再送信します。
3. 左側のウィンドウで、リクエストパケットの内容を直接改変し、`Go` ボタンをクリックしてリクエストを送信します。右側のウィンドウで返却された内容を確認できます。
