# 自社 OA 承認：サードパーティの作業フローとページの統合

## 概要

### 背景

多くの組織は、独自に OA システムを開発するか、サードパーティ製のシステムを導入しています。これらのシステムには、通常それぞれ独自の承認フローと承認ページがあります。社員は複数のシステムを切り替えて承認を処理する必要があり、業務が分断されて効率が低下します。自社の承認フローを DingTalk OA承認センターに接続すると、ユーザーは DingTalk 上で業務システムのページを開き、そのまま承認できます。これにより、ワンストップの承認体験を実現できます。

組織が一般的に抱える課題は次のとおりです。

- **承認の入口が分散している：** 社員は複数のシステムで個別に承認を処理しています。DingTalk ToDo のリマインダーは自社システムの承認タスクに対応していないため、承認者がタスクを見落としやすくなります。
- **承認体験に一貫性がない：** 自社システムの承認ページは DingTalk のスタイルと異なります。ユーザーは異なるインターフェースに慣れる必要があり、学習コストが増えます。
- **ToDo 通知の到達率が低い：** 自社システムは承認通知をメールや SMS に頼っています。これらのチャネルは反応が遅く、DingTalk のメッセージプッシュや ToDo センターを活用できません。
- **承認データがサイロ化している：** 承認ステータスや処理履歴が複数のシステムに分散しています。管理者は DingTalk 上で承認の進捗を一元的に確認できません。

### 主な価値

本ソリューションは、サードパーティの承認システムと DingTalk 内のアプリページを連携させます。DingTalk オープンプラットフォームの承認プロセスセンター API を呼び出し、承認データを双方向に同期します。

- **承認テンプレートの同期：** 自社システムの承認フォームテンプレートを DingTalk に同期します。ユーザーは DingTalk OA承認の管理コンソールで、サードパーティの承認テンプレートを確認・管理できます。
- **承認インスタンスの連携：** 自社システムで承認が開始されると、DingTalk に対応する承認インスタンスが自動的に作成されます。ユーザーは DingTalk 承認センターの 4 つのリスト（未処理、処理済み、申請済み、受信）で、その承認を確認・処理できます。
- **ToDo タスクのプッシュ：** 承認ノードの情報が DingTalk に同期されると、DingTalk が ToDo タスクを自動生成します。これらのタスクには、DingTalk 共通の ToDo リマインダーとメッセージプッシュが適用されます。
- **承認ステータスの書き戻し：** ユーザーが DingTalk で承認を完了したら、その結果（同意・却下など）を自社システムに書き戻し、双方のデータの整合性を保ちます。

### ユースケース

本ソリューションは、次のような代表的な業務シナリオに適用できます。

- **ERP 購買承認の統合：** 社員が ERP システムで購買申請を提出すると、申請が DingTalk に自動で同期されます。承認者が DingTalk で承認を完了すると、結果が ERP システムに書き戻され、発注書のステータスが更新されます。
- **HR 休暇承認の連携：** HR システムの休暇申請を DingTalk に同期します。社員は DingTalk ToDo センターでリマインダーを受け取り、そのまま処理できます。承認結果は HR の勤怠モジュールに自動反映されます。
- **プロジェクト管理における経費精算の統合：** プロジェクト管理システムの経費精算フローを DingTalk 承認センターに接続します。プロジェクトマネージャーが DingTalk で承認すると、精算データがプロジェクト予算モジュールに同期されます。
- **CRM 契約承認のコラボレーション：** CRM システムの契約承認フローを DingTalk に同期します。営業チームは DingTalk で多段階の承認を完了し、契約ステータスが CRM システムにリアルタイムで反映されます。

## 代表的な業務シナリオ

### シナリオ1：CIMC Ruijiang が複数の業務システムの承認を DingTalk に一元化

#### 課題

CIMC Ruijiang は、CIMC グループの社内 IT 開発パイロットセンターとしての役割を担っています。同社は MES、IOT、SRM など 10 を超える独立した業務システムを構築しており、各システムが特定の機能のデータと作業フローを担当しています。この高度に専門化されたモデルは、各事業部門の効率を高める一方で、組織内の情報を分断し、その流れを途切れさせています。

- 社員は 10 を超えるシステムで個別に承認タスクを処理しています。手順が煩雑で、緊急の承認を見落としやすくなります。
- システムごとに承認ページのスタイルが異なります。ユーザーは異なるインターフェースに慣れる必要があり、学習コストが増えます。
- 承認通知は各システムの内部メッセージに依存しており、DingTalk 共通の ToDo リマインダーやメッセージプッシュを活用できません。
- 管理者は DingTalk 上ですべての承認の進捗を一元的に確認できず、複数のシステムにログインして確認する必要があります。

#### 導入効果

- **自動化されたプロセス**

  統合フロー：

  1. **MES/IOT/SRM** システムが承認を開始します。
  2. **DingTalk OA承認** センターの API を呼び出し、承認インスタンスを作成します。
  3. 承認タスクが **DingTalk ToDo** リストに同期されます。
  4. 承認者が DingTalk 上で承認を完了します。
  5. 承認結果が元の業務システムにリアルタイムで書き戻されます。

  各システムで個別に申請・承認する従来の方法と比べて、効率が **83%+** 向上します。
- **主なメリット**

  - **複数システムの承認を統一窓口で処理：** MES、IOT、SRM など 10 を超える独立システムの承認フロー、ToDo、重要な業務通知が DingTalk に集約され、一元的に処理できます。
  - **効率的なデータ共有とコラボレーション：** システム間の情報サイロを解消し、システムをまたいだデータ共有とプロセスの自動化を実現して、組織全体の対応力を高めます。
  - **承認体験の向上：** 社員は複数のシステムに 1 つずつログインする必要がなくなり、DingTalk を開いてワンタップですべてを処理できます。操作の複雑さが大幅に軽減され、承認の対応時間も大きく短縮されます。

事例の詳細：[CIMC Ruijiang デジタルトランスフォーメーション事例](https://page.dingtalk.io/wow/tianyuan/act/toufang?wh_showError=true&caseId=NTMzNg==)

### シナリオ2：HR 休暇承認と DingTalk 勤怠の連携

#### 課題

HR システムは休暇承認を独自に管理している一方、打刻データは DingTalk にあります。2 つのシステム間でデータが連携していないため、社員は休暇取得後も DingTalk で打刻修正を手動で申請する必要があります。HR 担当者は、休暇記録と勤怠記録をシステムをまたいで照合しなければなりません。

#### 導入効果

- **自動化されたプロセス**

  エンドツーエンドの自動化プロセスは、次の 5 ステップで実行されます。

  1. **MES** システムが製造指図を作成します。
  2. **DingTalk OA承認 API** を呼び出し、承認インスタンスを作成します。
  3. **ERP** システムが資材在庫（原材料、副資材、包装材）を確認します。
  4. 工場の現場責任者が DingTalk で内容を確認し、**却下** または **承認** をタップします。
  5. 承認結果が **MES**（製造指図ステータス）、**ERP**（在庫）、**QMS**（品質記録）の 3 システムすべてに同期されます。

  MES、ERP、QMS にそれぞれログインする従来の方法（1 件あたり約 15 分）と比べ、統合後は DingTalk の単一窓口から 2 分以内に承認を完了でき、承認効率が 87% 向上します。
- **主なメリット**

  - **製造指図承認の統合：** MES、ERP、QMS の製造指図の承認ノードがすべて DingTalk のタスクリストに表示されます。承認者はシステムを切り替える必要がありません。
  - **承認フローのリアルタイムな可視化：** DingTalk には、部品表、品質検査要件、過去の製造指図データなど、3 システムから集約した製造指図の全データが表示されます。承認の進捗がひと目でわかります。
  - **エンドツーエンドのデータ同期：** 承認結果は元の業務システムにリアルタイムで書き戻されます。承認が却下された場合は、後続の ToDo タスクが一括でキャンセルされます。これにより、双方のデータの整合性とトレーサビリティを確保します。

## 実装ガイド

### 技術アーキテクチャ

本ソリューションでは、次の 5 つのコア技術コンポーネントを使用して、自社の承認システムと DingTalk OA承認センターを接続します。

- **認証レイヤー：** DingTalk オープンプラットフォームの OAuth 2.0 プロトコルに基づきます。アプリ認証情報を使用してアクセストークンを取得し、すべての API 呼び出しに統一された本人確認を提供して、呼び出しの安全性と正当性を確保します。
- **承認テンプレート管理レイヤー：** 自社の承認テンプレートを DingTalk OA承認センターに同期し、識別子としてグローバルに一意なテンプレートコードを取得します。テンプレートの作成・更新・削除に対応し、承認フォームの構造をクラウドで一元管理します。
- **承認インスタンスエンジン：** DingTalk に承認インスタンスを作成し、一意のインスタンス識別子を生成します。申請者、承認コンテンツ、添付などの具体的な承認業務データを保持し、承認のライフサイクル全体を管理します。
- **ToDo タスク同期レイヤー：** 承認タスクを DingTalk プロセスセンターに一括同期し、タスク識別子を生成して DingTalk ユーザーに紐付けます。承認者は、複数の業務システムの承認タスクを DingTalk の 1 つのタスクリストで確認・処理できます。
- **双方向ステータス同期レイヤー：** 承認ステータスを双方向に同期します。ユーザーが DingTalk で承認を完了すると、ステータスが業務システムにリアルタイムで書き戻されます。業務システム側で承認を終了または完了した場合は、DingTalk のタスクステータスもそれに応じて更新されます。これにより、双方のデータの整合性を確保します。

### 前提条件

- **アプリの準備**：[アプリの作成と設定](/ja/open/dingstart/create-application)を完了していること。
- **権限要件**：DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請していること。

  - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）
  - `Workflow.Form.Read`（作業フローテンプレートの読み取り権限）、任意
  - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）
  - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）
  - `qyapi_aflow`（承認フローデータの管理権限）
- **開発環境**：Java 開発環境（JDK 1.6 以降）と Maven ビルドツールがインストールされていること。
- **SDK の準備**：DingTalk サーバーサイド SDK をダウンロードしていること。Java、Python、Go など複数の言語に対応しています。

### コード実装

ステップ1：クライアント ID と Client Secret を含むアプリ認証情報を取得します。

ステップ2：承認関連の API の API 権限を申請します。

ステップ3：アクセス認証情報を取得します。[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。API を呼び出す際、アクセストークンによって呼び出し元の身元が認証されます。

ステップ4：サーバーサイドの承認 API を呼び出します。

1. 新しいサーバー API [承認テンプレートの作成または更新](/ja/open/development/create-orupdate-the-approval-template-new)を呼び出し、一意のテンプレートコード `processCode` を取得します。
2. `processCode` を保存していない場合は、[テンプレートコードの取得](/ja/open/development/obtain-the-template-code) API を呼び出して取得します。
3. 承認テンプレートの作成後、ユーザーは DingTalk OA承認の管理コンソールで、サードパーティの自社承認フォームテンプレートの確認、テンプレートデータの表示・検索、エクスポート・削除を行えます。
4. テンプレートコード `processCode` を使用して新しいサーバー API [インスタンスの作成](/ja/open/development/create-a-ticket-approval-instance)を呼び出し、承認インスタンスを開始して承認インスタンス ID `processInstanceId` を取得します。
5. 承認インスタンスの作成後、ユーザーは DingTalk OA承認センターでも 4 つの承認リスト（未処理、処理済み、申請済み、受信）の確認、承認インスタンスデータの検索、承認操作を行えます。
6. 承認インスタンス `processInstanceId` と ToDo リスト `tasks` を使用して、[プロセスセンターに未処理タスクを作成](/ja/open/development/create-pending-tasks-in-process-center) API を呼び出します。これにより、サードパーティシステムの承認ノード情報が DingTalk OA承認に同期され、各 ToDo 項目の taskId が返されて、対応する DingTalk ToDo タスクが生成されます。
7. 未処理タスクの作成後、[プロセスセンター経由で統合された OA 承認タスクの照会](/ja/open/development/query-oa-approval-tasks-integrated-through-process-center) API を呼び出し、ユーザーの進行中の承認タスクを照会します。
8. 承認インスタンス `processInstanceId` と承認 ToDo の taskId を使用して、[プロセスセンターのタスクステータスの更新](/ja/open/development/update-process-center-task-status) API を呼び出し、自社承認の ToDo 項目のステータス更新を同期します。OR 署名（承認者のうち 1 人が承認すればよい）などのシナリオでは、[プロセスセンターの複数の未処理タスクのキャンセル](/ja/open/development/cancel-multiple-oa-approval-tasks) API を呼び出し、承認インスタンス配下で進行中のすべての ToDo 項目を一括で CANCELED に設定します。
9. 承認インスタンス `processInstanceId`、インスタンスステータス `status`、インスタンス結果 `result` などのパラメータを使用して、[インスタンスステータスの更新](/ja/open/development/update-instance-status) または [インスタンスステータスの一括更新](/ja/open/development/self-owned-batch-update-of-instance-status) API を呼び出し、インスタンスステータスを更新します。
10. 最後に、承認テンプレートのデータを整理する場合は、[テンプレートの削除](/ja/open/development/self-owned-approval-deletion-template) API を呼び出します。社内向けに作成した承認テンプレートと、その配下で作成されたインスタンスおよび ToDo タスクが削除されます。

## 実装手順

### **ステップ1：アプリ認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/)にログインします。
2. 対象のアプリを選択して詳細ページを開きます。
3. **基本情報** > **認証情報と基本情報** をクリックします。
4. アプリの `Client ID` と `Client Secret` を控えておきます。

### 注意

   `Client Secret` は安全に保管し、第三者と絶対に共有しないでください。コードにハードコーディングせず、環境変数または鍵管理システムに保存してください。

### ステップ2：API 権限を追加する

1. アプリの詳細ページで **権限管理** をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）：承認テンプレートを作成・更新・削除します。
   - `Workflow.Form.Read`（作業フローテンプレートの読み取り権限）：テンプレートコードを取得します。任意です。
   - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）：承認インスタンスを作成し、インスタンスステータスを更新します。
   - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）：承認タスクとインスタンス情報を照会します。
   - `qyapi_aflow`（承認フローデータの管理権限）：承認フローのデータを包括的に管理します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。実際の要件に応じて申請してください。たとえば、一括インポートのシナリオでは、ユーザーの一括操作に関する権限も必要です。
</Note>

### ステップ3：アクセス認証情報（アクセストークン）を取得する

ステップ1 で取得した Client ID と Client Secret を使用して、アプリのアクセス認証情報を取得します。[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ戦略**：`accessToken` の有効期間は 2 時間です。メモリまたは Redis にキャッシュし、有効期限の 5分前に事前に更新してください。
- **同時実行の制御**：複数のスレッドによるトークン更新の予定が重なって競合しないよう、分散ロックを使用してください。
- **エラー時のリトライ**：ネットワークが不安定な場合は自動でリトライします。最大 3 回まで、間隔を段階的に延ばしてください（1 秒 → 2 秒 → 4 秒）。

### ステップ4：コア API を呼び出す

1. **承認テンプレートの作成または更新**：新しいサーバー API [承認テンプレートの作成または更新](/ja/open/development/create-orupdate-the-approval-template-new)を呼び出し、一意のテンプレートコード `processCode` を取得します。

### 注意

   このシナリオでは、processFeatureConfig でプロセスセンターの統合設定を行う必要はありません。デフォルトでは、承認時に業務システムの詳細ページが開きます。

   ```java
   public void  saveProcess() throws Exception {
     Config config = new Config();
     config.protocol = "https";
     config.regionId = "central";
     com.aliyun.dingtalkworkflow_1_0.Client client = new com.aliyun.dingtalkworkflow_1_0.Client(config);
     SaveProcessHeaders saveProcessHeaders = new SaveProcessHeaders();
   ```

## よくある質問

- **Q1：承認テンプレートの作成時に必要なパラメータは何ですか？**

  A：必須パラメータは次のとおりです。

  - `name`：承認テンプレートの名前。
  - `formComponents`：フォームコンポーネントのリスト。少なくとも 1 つのコンポーネントを含める必要があります。
  - 任意パラメータには、`description`（テンプレートの説明）などがあります。
- **Q2：processCode はどのように取得しますか？**

  A：次のいずれかの方法で取得します。

  - 承認テンプレートの作成または更新 API を呼び出した後、レスポンスから `result.processCode` を取得します。
  - processCode を保存していない場合は、テンプレートコードの取得 API を呼び出し、テンプレート名で照会します。
- **Q3：未処理タスクを作成すると、DingTalk では何が変わりますか？**

  A：未処理タスクを作成すると、次のようになります。

  1. 承認フォームの詳細ページに「同意」と「却下」のボタンが表示されます。
  2. プロセスセンターが承認タスクを DingTalk ToDo タスクとして同期します。
  3. 承認者は DingTalk ToDo センターで承認のリマインダーを確認できます。
- **Q4：ToDo タスクのデータはどのように同期しますか？**

  A：次の手順で同期します。

  1. プロセスセンターに未処理タスクを作成 API を呼び出し、サードパーティシステムの承認ノード情報を DingTalk に同期します。
  2. OA 承認タスクの照会 API を呼び出し、タスクが正しく同期されたことを確認します。
  3. 承認ステータスが変わったら、プロセスセンターのタスクステータスの更新 API を呼び出し、最新のステータスを同期します。
- **Q5：DingTalk オープンプラットフォームで申請が必要な権限は何ですか？**

  A：OA承認のプロセスセンターに接続するには、次の権限を申請してください。

  | **権限スコープコード** | **権限スコープ名** | **説明** |
  | --- | --- | --- |
  | Workflow.Form.Write | 作業フローテンプレートの書き込み権限 | 承認テンプレートを作成・更新・削除する |
  | Workflow.Instance.Write | ワークフローインスタンスの書き込み権限 | 承認インスタンスを作成し、インスタンスステータスを更新する |
  | Workflow.Instance.Read | ワークフローインスタンスの読み取り権限 | 承認タスクとインスタンス情報を照会する |
  | qyapi_aflow | 承認フローデータの管理権限 | 承認フローのデータを包括的に管理する |

  業務シナリオによって、必要な権限の組み合わせは異なります。実際の要件に応じて申請してください。
