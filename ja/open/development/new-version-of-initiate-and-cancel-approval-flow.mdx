# OA承認作業フローの統合：承認インスタンスの開始と取り消し

## 概要

### 背景

自社開発やサードパーティの業務システムには、それぞれ独自の承認フローと承認画面があることが少なくありません。従業員は承認のたびに複数のシステムを切り替える必要があり、作業が分断されて効率が下がります。承認フローを DingTalk の OA承認センターに接続すると、ユーザーは DingTalk の単一の入口からすべての承認を確認・処理できます。

- **頻繁なシステム切り替え：** 従業員は業務システムと DingTalk の間を行き来する必要があります。作業フローが長く、緊急の承認を見落としがちです。
- **承認状況の不一致：** 業務システムと DingTalk のデータが一致せず、承認の進捗をリアルタイムに追跡・管理するのが困難です。
- **承認フローの分散：** 管理者は DingTalk ですべての承認の進捗を確認できず、システムごとに個別にログインする必要があります。
- **通知の遅延：** 承認通知がメールやオフラインでの連絡に依存しており、DingTalk の統一された ToDo リマインダーやメッセージプッシュを活用できません。

### 主なメリット

本ソリューションは、DingTalk の公式 OA 承認が持つプロセスエンジンとフォームコンポーネントの機能を再利用します。業務システムの承認フローを DingTalk にシームレスに統合し、一元管理と効率的なコラボレーションを実現します。

- **承認入口の一元化：** ユーザーは自社システムのすべての承認を DingTalk の承認一覧で確認・処理でき、システムの切り替えが減ります。
- **低い統合コスト：** 数回の API 呼び出しだけで統合できます。既存の業務プロセスや画面ロジックを作り直す必要はありません。
- **リアルタイムな状況同期：** 承認結果がリアルタイムで業務システムに書き戻され、双方のデータの一貫性と追跡性を保ちます。
- **即時の通知配信：** DingTalk の ToDo リマインダーとメッセージ通知により、承認タスクが承認者に即座にプッシュされます。

### ユースケース

本ソリューションは、次のような代表的な承認統合シナリオに適しています。

- DingTalk 承認センターとの連携が必要な、自社開発の CRM・ERP・OA などの業務システム。
- 小売チェーンにおける店舗運営の承認（改装申請、販促承認など）。
- 製造業における生産作業指示の承認（品質検査報告、資材申請など）。
- 人事関連の承認（休暇申請、経費精算、入社・退職手続きなど）。

## 代表的な業務シナリオ

### シナリオ 1：CRM の顧客フォローアップ承認

#### 課題

あるテクノロジー企業は、自社開発の CRM システムで顧客のフォローアップを管理しています。営業担当者が見込み顧客の情報を登録した後、上長の承認を得なければ、共有リードの獲得や商談を開始できません。従来のプロセスには次の課題がありました。

- **商機への対応の遅れ：** リード登録後、上長のオフラインでの承認を待つ必要があり、平均 2〜3 日の遅延が発生します。その結果、購買意欲の高い顧客に競合他社が先にアプローチしてしまうことが多くありました。
- **顧客情報の不足：** 承認者が確認できるのは顧客名と連絡先のみです。DingTalk 上でコミュニケーション履歴、要件、競合分析を確認できず、的確な判断が困難です。
- **承認責任の不明確さ：** 複数人での承認に順序や期限が定められていません。そのため責任の押し付け合いや重複承認が発生し、意思決定サイクルが長くなります。
- **深刻なデータのサイロ化：** CRM の顧客ステータスが DingTalk の承認進捗と同期されていません。営業担当者は承認結果をリアルタイムに把握できず、上長に何度も電話やメールで確認する必要があります。

#### 効果の検証

- **自動化された作業フロー**

  エンドツーエンドのフロー：

  1. **CRM システム**：営業担当者が顧客情報を登録すると、次のステップがリアルタイムでトリガーされます。
  2. **API 統合**：DingTalk の**承認インスタンス**が自動的に作成されます。
  3. **DingTalk 承認センター**：承認者は PC またはモバイルで顧客のプロフィールと履歴を確認し、**却下**または**承認**をタップします。
  4. **データの書き戻し**：承認結果がリアルタイムで CRM システムに同期されます。
- **主な利点**

  - **ワンクリックでの顧客承認：** CRM システムに顧客を登録すると、DingTalk の承認インスタンスが自動的に作成されます。承認者はシステムを切り替えることなく、DingTalk 上で顧客の詳細を確認して直接処理できます。
  - **承認状況のリアルタイムな可視化：** DingTalk には、連絡先、要件、フォローアップ履歴などの顧客データがすべて表示されます。承認の進捗がひと目でわかり、コメントやリマインドにも対応しています。
  - **エンドツーエンドのデータ同期：** 承認結果はリアルタイムで CRM システムに書き戻されます。承認が却下されると後続の ToDo が自動的にキャンセルされ、双方のデータの一貫性と追跡性を保ちます。

### シナリオ 2：製造業の生産作業指示承認

#### 課題

ある製造業者は、自社開発の MES システムで生産作業指示を管理しています。作業指示には、初品検査、工程の引き継ぎ、完成品の入庫など、複数の工程承認が伴います。従来のプロセスは紙の帳票と班長による口頭確認に依存しており、次の課題がありました。

- **長い承認チェーン：** 作業指示には「班長 → 品質検査員 → 工場長」の 3 段階の承認が必要です。紙の帳票は回覧に時間がかかり、急ぎの注文に迅速に対応できません。
- **検査データの分散：** 検査報告書は PDF や写真としてローカルフォルダに保存されています。承認者は DingTalk 上で検査記録全体を確認したり、過去の作業指示と比較したりできません。
- **生産ライン間の連携不足：** 前工程と後工程の間でステータスがリアルタイムに同期されません。前工程の承認前に後工程が開始されることがあり、手戻りや無駄が発生します。
- **高いトレーサビリティコスト：** 品質問題が発生した際、責任者や承認ノードを特定するには紙の帳票を手作業で探す必要があります。時間がかかるうえ、重要な情報を見落としやすくなります。

#### 効果の検証

- **自動化された作業フロー**

  エンドツーエンドの統合フロー：

  1. MES システムが生産作業指示を作成します。
  2. DingTalk の OA承認 API を呼び出して承認インスタンスを作成します。
  3. ERP が資材の在庫を確認します。
  4. 工場の監督者が DingTalk で承認します。
  5. 承認結果が 3 つのシステム（MES、ERP、QMS）すべてに同期されます。

  承認結果に基づき、MES の作業指示ステータス、ERP の引当在庫、QMS の関連品質記録が更新されます。
- **主な利点**

  - **作業指示承認の統合：** MES システムで作業指示の承認を開始すると、DingTalk の承認インスタンスが自動的に作成されます。承認者はシステムを切り替えることなく、DingTalk 上で作業指示の詳細を確認して直接処理できます。
  - **承認状況のリアルタイムな可視化：** DingTalk には、部品表、検査要件、過去の作業指示などの作業指示データがすべて表示されます。承認の進捗がひと目でわかり、コメントやリマインドにも対応しています。
  - **エンドツーエンドのデータ同期：** 承認結果はリアルタイムで MES システムに書き戻されます。承認が却下されると後続の ToDo が自動的にキャンセルされ、双方のデータの一貫性と追跡性を保ちます。承認の処理時間は 60% 以上短縮されます。

## 実装ガイド

### 技術アーキテクチャ

本ソリューションの技術アーキテクチャは、次のコアコンポーネントで構成されます。

- **認証レイヤー**：App の認証情報を管理し、アクセストークンを取得して、すべての API 呼び出しの身元を検証します。
- **テンプレート管理レイヤー**：承認フォームテンプレートを作成・更新し、承認フローの構造とフィールドを定義します。
- **インスタンス実行レイヤー**：承認インスタンスの開始、照会、転送、取り消しを行い、承認フローの実行を制御します。
- **イベントコールバックレイヤー**：承認タスクと承認インスタンスのステータス変更イベントを受信し、業務システムと DingTalk プラットフォーム間の双方向同期を実現します。

### 前提条件

- **App の準備**：[App の作成と設定](/ja/open/dingstart/create-application)を完了してください。
- **権限**：DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請してください。

  - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）
  - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）
  - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）
- **開発環境**：Java 開発環境（JDK 1.6 以降）と Maven ビルドツールをインストールしてください。
- **SDK**：DingTalk のサーバーサイド SDK をダウンロードしてください。Java、Python、Go などの言語に対応しています。

### コードの実装

ステップ 1：App の詳細ページに移動し、クライアント ID と Client Secret を取得します。

ステップ 2：API 権限を申請します。「OA承認」関連の権限を申請してください。

ステップ 3：App のアクセス認証情報を取得します。[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。API を呼び出す際は、アクセストークンを使って呼び出し元を認証します。

ステップ 4：OA承認 API を呼び出します。

1. 新しいサーバー API [承認フォームテンプレートの作成または更新](/ja/open/development/create-an-approval-form-template)を呼び出し、テンプレートの一意なコード `processCode` を取得します。
2. テンプレートコード `processCode` を使って新しいサーバー API [承認インスタンスの作成](/ja/open/development/create-an-approval-instance)を呼び出し、承認インスタンス `instanceId` を取得します。
3. 承認インスタンス `instanceId` を使って新しいサーバー API [単一の承認インスタンスの詳細を取得](/ja/open/development/obtains-the-details-of-a-single-approval-instance-pop)を呼び出し、承認インスタンスの詳細を取得します。
4. 承認インスタンスの詳細に含まれるフィールドを使って新しいサーバー API [OA 承認タスクの転送](/ja/open/development/transfer-the-oa-approval-task)を呼び出し、承認インスタンスを転送します。
5. 承認内容を確認した後、承認インスタンス `instanceId` を使って新しいサーバー API [承認インスタンスの取り消し](/ja/open/development/revoke-an-approval-instance)を呼び出し、承認フォームを取り消します。

## 実装手順

### **ステップ 1：App の認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/)にログインします。
2. 対象の App を選択し、App の詳細ページを開きます。
3. **基本情報** > **認証情報と基本情報**をクリックします。
4. App の `Client ID` と `Client Secret` を控えておきます。

### 注意

   `Client Secret` は安全に保管し、第三者と共有しないでください。コードにハードコーディングせず、環境変数やキー管理システムに保存してください。

### ステップ 2：API 権限を追加する

1. App の詳細ページで、**権限管理**をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）：承認フォームテンプレートを作成・更新します。
   - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）：承認インスタンスを開始・取り消します。
   - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）：承認インスタンスの詳細を照会します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。実際の要件に応じて申請してください。たとえば、一括インポートのシナリオでは、ユーザーの一括操作に関する権限も必要です。
</Note>

### ステップ 3：アクセス認証情報（アクセストークン）を取得する

ステップ 1 で取得した Client ID と Client Secret を使って、App のアクセス認証情報を取得します。[社内アプリのアクセストークンを取得する](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ**：`accessToken` の有効期間は 2 時間です。メモリまたは Redis にキャッシュし、有効期限の 5分前に事前に更新してください。
- **同時実行制御**：複数のスレッドが同時にトークンを更新して競合が発生しないよう、分散ロックを使用してください。
- **エラー時の再試行**：ネットワークが不安定な場合は自動的に再試行します。最大 3 回まで、間隔を段階的に延ばして（1 秒 → 2 秒 → 4 秒）実行してください。

## よくある質問

- **Q1：承認テンプレートを作成する際、formComponents の componentId にはどのような要件がありますか？**

  componentId はフォーム内で一意である必要があり、業務上の意味は持ちません。コントロールを識別するためだけに使用します。業務上の識別子を使用したい場合は、代わりに bizAlias フィールドを使用してください。
- **Q2：承認インスタンスを作成する際、approvers の actionType にはどのような値を指定できますか？**

  actionType には、NONE（単独承認）、OR（いずれか承認：いずれかの承認者が承認すれば承認完了）、AND（合議承認：すべての承認者の承認が必要）などの値を指定できます。すべての値については API ドキュメントを参照してください。
- **Q3：保存していなかった processCode はどのように確認できますか？**

  承認テンプレートの作成時に返された processCode を保存していない場合は、DingTalk の OA承認の管理コンソールにログインして確認するか、テンプレートコードを取得する API を呼び出してください。
- **Q4：承認タスクを転送する際、operateUserId にはどのような要件がありますか？**

  operateUserId は、現在の承認ノードに属するユーザーの userId である必要があります。そうでない場合、転送は失敗します。
- **Q5：承認インスタンスを取り消した後、承認ステータスはどのように同期されますか？**

  取り消しが成功すると、承認インスタンスのステータスは「終了」に変わります。承認インスタンス変更のコールバックイベントをサブスクライブすると、ステータスの変化をリアルタイムで検知できます。
