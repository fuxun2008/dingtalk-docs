# OA承認との連携：閲覧可能なフォームと未処理の承認件数の照会

## 概要

### 背景

社員は DingTalk にログインした後、自分の承認権限、閲覧できるフォーム、自分の対応を待つ承認の件数を確認する必要があります。しかし、既存のOA承認システムには、個人向けの統一された承認ワークベンチがありません。閲覧可能なフォームと未処理の承認件数を照会する API を使うと、DingTalk 上に個人向けの承認ダッシュボードを構築できます。これにより、社員は承認業務の優先順位を効率よく判断できます。

組織は日常業務で次のような課題に直面しがちです。

- **承認権限が不明確：** 社員は、どの種類のフォームを閲覧または承認できるのかを把握していません。新しい業務シナリオでは、権限スコープを確認するために管理者へ何度も問い合わせる必要があります。コミュニケーションコストが高く、回答にも時間がかかります。
- **未処理件数が見えない：** DingTalk の ToDo センターにはタスクリストしか表示されず、未処理の承認をフォーム種別ごとに集計できません。社員は自分の業務量の内訳を把握できず、作業の順序を計画しにくくなっています。
- **システムごとに承認が分散：** OA、経費管理、人事などのシステムの承認は、それぞれ別の入口に分かれています。社員は各システムにログインして未処理項目を確認する必要があり、毎日 15 分以上を費やしています。
- **承認業務の負荷が偏る：** マネージャーは、チームメンバーの未処理の承認件数や滞留状況をリアルタイムで把握できません。業務の割り振りが主観的な判断に頼るため、一部の社員に負荷が集中する一方で、手が空いている社員もいます。

### 主なメリット

本ソリューションは、次の 3 つの面で価値を提供します。

- **動的なフォームリスト：** 社内で管理可能なすべての承認フォーム、または特定ユーザーが閲覧できるフォームを、API でリアルタイムに取得します。業務システム側で静的なフォーム設定テーブルを用意する必要はありません。
- **正確な未処理件数の集計：** userId を指定して、ユーザーの未処理の承認件数を照会します。業務システムのホーム画面やメッセージセンターに、個人向けの ToDo リマインダーを表示できます。
- **管理された権限の分離：** フォームリストの照会は、DingTalk OA承認の権限体系に自動的に従います。呼び出し元がアクセスできるフォームのみが返されるため、データの安全性が保たれます。

### ユースケース

本ソリューションは、自社の業務システムで承認フォームの入口を動的に表示し、ユーザーの未処理件数をリアルタイムに表示する必要があるシナリオに適しています。代表的なユースケースは次のとおりです。

- **統合承認ワークベンチ：** ユーザーが閲覧できるすべての承認フォームの入口と未処理件数を業務システムのホーム画面に集約し、承認業務をワンストップで行えるようにします。
- **フォームのスマートレコメンド：** ユーザーの役職や部門に応じて閲覧可能なフォームリストを動的に絞り込み、担当業務に関連する承認種別のみを表示します。
- **ToDo 通知のプッシュ：** ユーザーの未処理の承認件数の変化を定期的にポーリングし、アプリ内メッセージやモバイルのプッシュ通知をトリガーします。

## 代表的な業務シナリオ

### シナリオ 2：大学教職員向けモバイルオフィスポータル（教育）

#### 課題

ある有力大学では、教職員向けに自社開発のモバイルオフィスアプリを利用しています。教員は、授業の振替申請、研究費の精算、設備の購入など、さまざまな種類の承認を申請します。従来のプロセスには次の問題がありました。

- **フォームが見つけにくい：** アプリ内の承認の入口は固定のメニュー構成でした。新しい承認種別を追加するたびにアプリのリリースが必要となり、対応が遅れていました。
- **キャンパス間で ToDo の見落としが発生：** 本キャンパスと分校の教員への未処理の承認通知はメールに頼っていました。モバイルアプリにはリアルタイムのリマインダーがなく、遠隔キャンパスの教員は承認の処理が平均 2 日遅れていました。
- **個別最適化の不足：** すべての教員に同じ承認フォームリストが表示されていました。事務職員には教務関連のフォームが、教授には財務関連のフォームが表示され続け、本来の業務の妨げになっていました。

#### 効果の検証

- **自動化フロー**

  エンドツーエンドのフロー：

  1. 教員がモバイルで、役割に応じた入口から申請を作成します。
  2. 動的な**フォーム**レコメンドにより、利用頻度の高い順にテンプレートが並びます。
  3. **承認**は DingTalk 内で行われます。承認の詳細には**申請種別**、**申請者**、**部門**、**優先度**が表示され、**承認申請を送信**ボタンがあります。
  4. 承認者が**却下**または**承認**をタップします。
  5. 結果がローカル**通知**としてプッシュされます。

  従来の手作業によるフロー（固定メニューの入口 > メールで申請 > 手作業でフォームに記入 > 遅れて届くメールの返信 > 結果の保管）と、統合された**自動化**フロー（モバイルアプリ > DingTalk 承認センター > 承認完了 > ローカル通知の**プッシュ**）を比較します。
- **主な利点**

  - **個人に最適化されたフォームリスト：** 教員はログイン後、自分の職務に関連する承認フォームのみを確認できます。事務職には文書の回覧が、教育職には授業の振替申請が優先して表示されるため、関係のないフォームを探す時間を削減できます。
  - **即時の ToDo リマインダー：** アプリはバックグラウンドで未処理の承認件数をサイレントにポーリングし、件数がしきい値を超えるとローカル通知を送信します。これにより、各キャンパスの教員の承認対応スピードが 60% 向上しました。
  - **新しいフォームを設定不要で公開：** 管理者が DingTalk 管理コンソールで承認テンプレートを作成すると、アプリは次回起動時にそのテンプレートを取得して表示します。アプリのリリースは不要です。

## 実装ガイド

### 技術アーキテクチャ

本ソリューションの技術アーキテクチャは、次のコアコンポーネントで構成されます。

- **認証レイヤー：** アプリ認証情報を管理し、アクセストークンを取得して、各 API 呼び出しの呼び出し元の身元を検証します。
- **フォーム照会レイヤー：** 照会 API を呼び出して、管理可能な組織のフォーム、ユーザーが閲覧できるフォーム、未処理の承認件数を取得し、構造化されたフォームのメタデータを返します。
- **権限フィルタリングレイヤー：** DingTalk OA承認の権限体系を利用して、呼び出し元がアクセスできないフォームを除外し、データの安全性を確保します。
- **キャッシュ高速化レイヤー：** フォームリストと未処理件数を短時間キャッシュして API の呼び出し頻度を抑え、フロントエンドの描画パフォーマンスを向上させます。

### 前提条件

- **アプリの準備：** [アプリの作成と設定](/ja/open/dingstart/create-application)の手順を完了し、クライアント ID と Client Secret を取得します。
- **権限の要件：** DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請します。

  - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）
  - `Workflow.Form.Read`（作業フローテンプレートの読み取り権限）
  - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）
  - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）
- **開発環境：** Java 開発環境（JDK 1.6 以降）と Maven ビルドツールをインストールします。
- **SDK の準備：** DingTalk のサーバーサイド SDK をダウンロードします。Java、Python、Go などの言語に対応しています。

### コードの実装

ステップ 1：クライアント ID と Client Secret を含むアプリ認証情報を取得します。

ステップ 2：OA承認関連の API 権限を申請します。

ステップ 3：アプリのアクセス認証情報を取得します。[社内アプリのアクセストークンの取得](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。各 API 呼び出しでは、アクセストークンで呼び出し元を認証します。

ステップ 4：OA承認の API を呼び出します。

1. 新しいサーバー API [承認フォームテンプレートの作成または更新](/ja/open/development/create-an-approval-form-template)を呼び出し、テンプレートの一意なコード `processCode` を取得します。
2. 複数の承認フォームテンプレートを作成した後、新しいサーバー API [現在の組織で管理可能なすべてのフォームの取得](/ja/open/development/get-all-manageable-forms-for-the-current-enterprise)を呼び出し、現在の組織でユーザーが管理できるすべての承認フォームを取得します。userId で指定するユーザーには、組織のOA承認の権限が必要です。
3. 複数の承認フォームテンプレートを作成した後、新しいサーバー API [指定ユーザーが閲覧できる承認フォームリストの取得](/ja/open/development/obtains-a-list-of-approval-forms-visible-to-the-specified)を呼び出し、そのユーザーが閲覧できる承認フォームを取得します。
4. テンプレートコード `processCode` を指定して新しいサーバー API [承認インスタンスの作成](/ja/open/development/create-an-approval-instance)を呼び出し、承認インスタンスを作成して `instanceId` を取得します。
5. 複数の承認インスタンスを作成した後、テンプレートコード `processCode` を指定して新しいサーバー API [承認インスタンス ID リストの取得](/ja/open/development/obtain-an-approval-list-of-instance-ids)を呼び出し、権限スコープ内の関連部門の承認インスタンス ID を取得します。
6. 複数の承認インスタンスを作成した後、ユーザーの userId を指定して新しいサーバー API [ユーザーの未処理の承認件数の取得](/ja/open/development/queries-the-number-of-requests-to-be-approved-by-users)を呼び出し、そのユーザーの未処理の承認件数を取得することもできます。

## 実装手順

### **ステップ 1：アプリ認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/)にログインします。
2. 対象のアプリを選択し、詳細ページを開きます。
3. **ベーシック情報** > **認証情報とベーシック情報**をクリックします。
4. アプリの `Client ID` と `Client Secret` を控えておきます。

### 注意

   `Client Secret` は安全に保管し、第三者に絶対に開示しないでください。ハードコーディングせず、環境変数またはキー管理システムに保存してください。

### ステップ 2：API 権限を追加する

1. アプリの詳細ページで、**権限管理**をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）：承認フォームテンプレートを作成または更新します。
   - `Workflow.Form.Read`（作業フローテンプレートの読み取り権限）：管理可能な組織のフォームと、ユーザーが閲覧できるフォームリストを取得します。
   - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）：承認インスタンスを作成します。
   - `Workflow.Instance.Read`（ワークフローインスタンスの読み取り権限）：ユーザーの未処理の承認件数を取得します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。実際の要件に応じて権限を申請してください。
</Note>

### ステップ 3：アクセス認証情報（アクセストークン）を取得する

ステップ 1 で取得した Client ID と Client Secret を使用して、アプリのアクセス認証情報を取得します。[社内アプリのアクセストークンの取得](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ戦略：** `accessToken` の有効期間は 2 時間です。メモリまたは Redis にキャッシュし、有効期限の5分前に事前に更新してください。
- **同時実行制御：** 複数のスレッドが同時にトークンを更新することによる競合を防いでください。分散ロックを使用します。
- **エラー時のリトライ：** ネットワークが不安定な場合は自動的にリトライします。リトライは最大 3 回とし、間隔を段階的に延ばします（1s → 2s → 4s）。

## FAQ

- **Q：フォームリストの API が空の結果を返すのはなぜですか？**

  userId で指定したユーザーに、組織のOA承認の管理権限があるかを確認してください。管理可能なフォームのリストを照会できるのは、OA承認の権限を持つユーザーのみです。
- **Q：ユーザーが閲覧できるフォームの取得と、管理可能な組織のフォームの取得には、どのような違いがありますか？**

  管理可能な組織のフォームの取得では、userId のユーザーが管理できるすべてのフォームが返されます。主に管理者の視点で利用します。ユーザーが閲覧できるフォームの取得では、そのユーザーが申請者として送信できるフォームが返されます。主に一般社員の視点で利用します。両者は対象とする権限スコープが異なります。
- **Q：未処理の承認件数の API が返す件数には、どの承認ステータスが含まれますか？**

  現在「承認待ち」ステータスのインスタンスのみが含まれます。承認済み、辞退、取り消し、終了となった承認インスタンスは含まれません。
- **Q：フォームリスト API の結果はキャッシュすべきですか？**

  はい。フォームのメタデータは変更頻度が低いため、業務システム側で 5〜10 分程度キャッシュし、API の呼び出し回数を削減してください。一方、未処理の承認件数は長時間キャッシュしないでください。最新の状態を保つため、1〜5 分ごとにポーリングしてください。
- **Q：ユーザーが複数の部門に所属している場合、閲覧可能なフォームは重複して返されますか？**

  いいえ。API は重複を除いたフォームリストを返します。異なる部門の権限によって同じフォームが複数回該当した場合でも、結果には 1 回のみ表示されます。
