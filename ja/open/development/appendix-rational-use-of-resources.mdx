DingTalk Open Platform は、Open API や Webhook & Stream メッセージングチャネルなど、豊富な機能を提供しています。本記事では、開発者がリソース利用を最適化するためのプラクティスと推奨事項を紹介します。

## リソースの効率的な利用に関するベストプラクティス

一部のビジネスシナリオでは、アプリの機能を Open API の呼び出しでも、イベントプッシュのリッスンでも実装できます。たとえば、グループチャットに追加されたユーザーの変更情報を取得する場合、Open API をポーリングする方法と、イベントプッシュをリッスンして必要なときにのみ対応するアクションをトリガーする方法があります。最適な選択を行うために、次の要素を考慮してください。

- **リアルタイム性の要件**—アプリがリアルタイムでデータを取得したりイベントを処理したりする必要がある場合は、イベントサブスクリプションがより適した選択肢となる場合があります。
- **データ更新頻度**—データが頻繁に更新され、より多くのリソースを消費する場合は、イベントサブスクリプションがより適した選択肢となる場合があります。定期的またはたまにデータを取得するだけでよい場合は、Open API を呼び出す方が適しています。
- **統合の複雑さ**—開発する機能が複雑で、複数の Open API を呼び出す必要がある場合、開発コストが増加します。イベントプッシュを組み込むことで開発工数を削減できるか検討してください。
- **取得するデータ量**—一度の取得で大量のデータが返される場合は、イベントプッシュがより適した選択肢となる場合があります。Open API の呼び出しはネットワーク帯域とサーバーリソースを消費します。アプリが Open API を頻繁に呼び出すと、システムのパフォーマンスとリソース消費に影響する可能性がありますが、イベントプッシュを利用すればリソース消費を抑えられます。

## イベントプッシュのリソース最適化に関するベストプラクティス

DingTalk Open Platform はイベントプッシュを提供しており、特定のイベントが発生した際に開発者がリアルタイムで通知を受け取れます。ただし、過剰なイベントをサブスクライブしたり、過剰なメッセージ通知を処理したりすると、アプリのパフォーマンスが低下し、リソース消費が増加する可能性があります。

- **必要なイベントのみをサブスクライブする**—アプリが本当に必要とするイベントを見極め、無関係なイベントタイプのサブスクライブを避け、サブスクライブするイベント数を削減してください。
- **ビジネスロジックでイベントを重複排除する**—場合によっては、ビジネスのイベントコールバックで重複したイベントを受信することがあります。開発者は同じ eventId を持つイベントを冪等に処理してください。
- **迅速にレスポンスを返す**—DingTalk Open Platform のプッシュタイムアウトは 2.5s（HTTP モード）/ 3s（Stream モード）です。メッセージを速やかに処理し、リアルタイムで正しいレスポンスを返すことで、DingTalk Open Platform へタイムアウトが返されるのを防ぎ、タイムアウトによる再試行の頻度を抑えることを推奨します。

## グループボット Webhook の利用制御

現在、利用制御では次の 2 つのグループ Webhook ボットのシナリオがサポートされています。

|  |  |
| --- | --- |
| グループカスタムボット | [社内アプリ]ボットを検索して追加し、Webhook を使用してメッセージをプッシュします |

### 手順

1. デベロッパーコンソール > [リソース管理](https://open-dev.dingtalk.com/?spm=dd_developers.header.unLogin.openDevBtn&hash=%23%2F#/)に移動し、**Webhook & Stream の利用状況**カードまでスクロールして、**利用制御**をクリックします。

2. 利用制御ダイアログで、グループボット Webhook の制限を設定できます。

   **注記**

   利用制御を設定する際は、実際のニーズに応じて**グローバル制限**または**個別制限**を選択してください。2 つの制限タイプの詳細については、以下の説明を参照してください。

### 説明

- **[グローバル制限]**—設定すると、「グループチャット内の社内ボット Webhook」と「グループカスタムボット Webhook」がすべて一律に制限され、ボットごとに利用が制限されます。

  - シナリオ：メンバーがチャット内でグループ Webhook ボットを頻繁に自作し、組織の Webhook クォータを消費しているため、これを制御したい場合。
  - 解決策：グローバル制限を設定し、グループチャット内で作成された各 Webhook ボットが月あたり最大 100 回まで呼び出せるようにすることで、制御不足を解消します。
- **[個別制限]**—特定のボットに専用の制限ルールを設定できます。設定すると、これらのルールはグローバル制限の構成より優先されます。

  - シナリオ：グローバル制限で他のメンバーのボットを制限した後、IT 部門が構築した一部のグループボットを利用制限の対象外にする必要がある場合。
  - 解決策：個別制限を設定します。IT 部門がグループチャット内で構築したカスタム Webhook ボットを選択し、無制限（または大きなクォータ）に設定します。
