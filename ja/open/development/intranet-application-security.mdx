本記事では、エンタープライズアプリゲートウェイとは何か、イントラネットアプリへのアクセスにおける課題、その解決策、そしてエンタープライズアプリゲートウェイの有効化と設定方法について説明します。

## エンタープライズアプリゲートウェイとは

エンタープライズアプリゲートウェイは、組織がインターネット経由でイントラネットアプリに安全にアクセスできるようにします。従来の VPN ソリューションを置き換え、Alibaba Cloud のネットワークアクセラレーション機能を活用してアプリへのアクセス速度を向上させます。ゼロトラストの原則に基づいて構築されており、継続的かつ動的なアクセス検証を提供することで、組織のデジタル情報のセキュリティを最大限に高めます。

## イントラネットアプリへのアクセスにおける課題

組織は通常、コアとなるアプリシステムをイントラネットや DMZ に配置し、ファイアウォールによってネットワーク境界を分離します。社員がモバイルデバイスや PC デバイスを使ってインターネットからイントラネットアプリにアクセスする場合、VPN ダイヤルアップとポートマッピングという 2 つの方法のいずれかを利用します。しかし、VPN デバイスには脆弱性が存在したり、ポートが外部の IP アドレスや URL にマッピングされたりする場合があります。その結果、ハッカーがアプリに直接アクセスしたり攻撃を仕掛けたりして、組織のコアデータの漏洩につながる恐れがあります。

以下では、従来の方法でイントラネットアプリにアクセスする際にユーザーが直面する 4 つの主な課題について説明します。

| 課題 | 説明 |
| --- | --- |
| 高いコスト | 従来の VPN ソリューションは導入コストが高く、専用線には毎年多額の費用がかかります。 |
| 不十分なユーザー体験 | - 社員は事前に VPN クライアントをインストールして設定する必要があり、手間がかかります。 - 利用前にまず VPN でダイヤルアップする必要があり、電波の弱い環境では VPN が切断され、再接続が求められます。 |
| データの非セキュリティ | インバウンドのファイアウォールポートを開放したままにする必要があり、これによりハッカーがイントラネットアプリのポートをスキャンして攻撃を仕掛けられるようになります。 |
| 困難なデバイス提供 | 購入申請を出してからデバイスを受領し、インストールおよび設定するまでのプロセスには通常数か月を要し、複雑なデバッグが伴います。 |

## イントラネットアプリへのアクセスの解決策

### 推奨される解決策

DingTalk のエンタープライズアプリゲートウェイは、DingTalk の ID プラットフォーム、DingTalk のセキュリティゲートウェイ、そしてコネクタを通じて、組織のイントラネットアプリを Alibaba パブリッククラウド環境に安全に接続します。これにより、社員はオフィス、運用保守、支社などのシーンで社内アプリに便利にアクセスでき、組織のデジタル化とコラボレーション変革を支援します。

以下では、ユーザーがイントラネットアプリにアクセスするための 5 つの推奨解決策について説明します。

| 解決策 | 説明 |
| --- | --- |
| 特定アプリへのアクセスポリシー設定 | 組織、部門、ロール、または個人単位で、特定アプリへのアクセスポリシーを設定します。 |
| シンプルな設定と迅速な提供 | 組織内にコネクタのみをデプロイします（コネクタは DingTalk サーバーへのリバース持続接続を確立します）。ワンライナーのインストールスクリプトが提供されます。インストール後、管理者はゲートウェイコンソールで簡単な設定を行うだけで提供が完了します。 |
| フルリンク暗号化 | イントラネットアプリを素早く DingTalk に接続します。イントラネットサーバーにコネクタをインストールしてデプロイすると、ゲートウェイとイントラネットの間に安全に暗号化された伝送チャネルが確立されます。社員の DingTalk クライアントからのリクエストはこのチャネルを通じてイントラネットサーバーに伝送され、サーバーのレスポンスは同じチャネルを通じて社員の DingTalk クライアントに返されます。 |
| 不正な ID のブロック | DingTalk の ID 認証に基づき、ゲートウェイの認証がイントラネットリソースを保護し、外部からの悪意あるアクセスをブロックします。DingTalk の ID 認証を通過したリクエストのみが組織のサーバーに転送されます。 |
| リライトのサポート | カスタムリライトルールにより、ゲートウェイはリクエストヘッダー、リクエストボディ、レスポンスヘッダー、レスポンスボディのリライトをサポートします。 |

### プロダクト設計の推奨事項

| プロダクト | プロダクト設計の説明 |
| --- | --- |
| クライアントサイド | - DingTalk クライアントは主にユーザーの ID 情報を検証し、アクセスするユーザーの正当性を確保します。 - DingTalk アカウントに基づいて社員の ID をバインドし、安全な ID 検証と状態維持を実現します。 - DingTalk 内蔵のアカウントリスク管理ロジックによってアカウントのセキュリティを確保します。 - クレデンシャルスタッフィング、アカウント乗っ取り、総当たり攻撃などの悪意ある攻撃を防止します。 |
| セキュリティゲートウェイ | - DingTalk のゼロトラストセキュリティソリューションのコアコンポーネントであり、このゲートウェイは ID 認識型プロキシです。 - OSI モデルの第 7 層（アプリケーション層）で動作し、HTTP(S) プロトコルのリバースプロキシを実装しながら、クライアントからのすべてのアクセスリクエストの正当性を検証します。 - HTTP(S) プロトコルは短時間接続をサポートし持続接続を必要としないため、非常に安定したリモートアクセスを提供し、電波の弱い環境でも確実に動作し、決して「オフラインになる」ことがありません。 - このゲートウェイは、複数のリージョンにクラスターとしてデプロイされる SaaS サービスです。 |
| コネクタ | - コネクタは顧客のマシンルームの DMZ にデプロイされます。 - ファイアウォールを通じて DingTalk のエンタープライズアプリセキュリティゲートウェイへのリバース接続を確立し、クライアントのリクエストを社内アプリに転送し、社内アプリから返されたコンテンツを受信して、DingTalk のエンタープライズアプリセキュリティゲートウェイを通じてクライアントに送り返します。 - このコンポーネントにより、イントラネットは隠蔽され、社内アプリをファイアウォール経由でインターネットに公開する必要がなくなり、攻撃を大幅に削減できます。 |

## アプリゲートウェイの導入事例

ある金融 IT 企業では、以前は従来の VPN を通じて社内オフィスシステムにアクセスしていました。社員はイントラネットシステムに入る前に VPN でダイヤルアップする必要があり、設定が複雑なため多くの社員が使い方を理解できず、スマートフォンを機種変更するたびに再設定しなければなりませんでした。さらに、VPN は持続接続に依存していたため、高速鉄道内やエレベーター内など電波の弱い環境では頻繁に切断され、繰り返しダイヤルアップする必要があり、コラボレーション効率が低下していました。

DingTalk のエンタープライズアプリゲートウェイを導入した後は、この企業はファイアウォールのポートを開放しなくなったため、ウイルスやハッカーが侵入できなくなりました。社員はいつでもどこでも、素早く、便利に、安全に社内システムにアクセスでき、効率的なコラボレーションが可能になりました。
