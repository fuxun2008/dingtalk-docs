# DingTalk OA承認の高度な統合：専用 OpenAPI と AppLink プロトコルによる連携

## 概要

本ソリューションは、すでに複数の業務システムを DingTalk OA承認のプロセスセンターに接続しており、さらにカスタマイズを進めたい組織を対象としています。DingTalk OA承認プレミアム版の専用 OpenAPI とフロントエンドの AppLink プロトコルを使用して、自社アプリと DingTalk の公式 OA 承認を高度に統合します。承認センターの一覧取得、承認タスクの一括処理、作業フローの引き継ぎ、承認ページへの遷移といった専用機能を提供します。これらを活用すると、ソース別の絞り込み、一括操作、管理者による転送に対応したワンストップで没入型の承認ワークベンチを構築できます。

### 背景

ERP、CRM、財務システムなどの基幹業務システムで発生する承認申請は、DingTalk OA承認と高度に統合する必要があります。目指すのは、DingTalk で承認を開始し、業務システムで処理し、その結果を DingTalk に書き戻すというクローズドループです。専用 OpenAPI と AppLink プロトコルによる連携により、ユーザー体験とデータセキュリティを両立しながら、業務承認を DingTalk の承認体系にシームレスに組み込めます。

日常業務では、多くの組織が次のような課題を抱えています。

- **承認チェーンの分断**：業務システムで作成した承認フォームを、DingTalk で手動で作り直す必要があります。2 つの記録は関連付けられず、結果も業務システムに自動で同期されません。
- **機密データの露出**：承認内容が DingTalk 標準のフォームにそのまま表示されます。契約金額や顧客情報などの機密フィールドが漏えいするリスクがあります。
- **カスタム承認ロジックの制約**：DingTalk 標準の承認コンポーネントでは、予算連動や多段階の合議条件など、複雑な業務検証ルールに対応できません。そのため、業務部門はオフラインでのやり取りに頼らざるを得ません。
- **監査追跡の困難さ**：承認操作のログが DingTalk と業務システムに分散しています。コンプライアンス監査では時系列を手作業でつなぎ合わせる必要があり、時間がかかるうえにミスも発生しやすくなります。

### 主な価値

本ソリューションは、次の 3 つの価値を提供します。

- **高度なカスタマイズ**：専用 OpenAPI により、承認センターの一覧、一括処理、作業フローの引き継ぎなどの機能を利用できます。業務ロジックに合わせて、ページや機能ロジックを自由にカスタマイズできます。
- **豊富な機能**：AppLink プロトコルにより、自社アプリから DingTalk 公式 OA 承認のホームページ、インスタンス作成ページ、インスタンス詳細ページなどへ直接遷移でき、DingTalk 標準の操作体験をそのまま活用できます。
- **ニーズに合わせた対応**：自社承認センター、作業フローの引き継ぎ、承認ページの統合など、複数の業務ソリューションに対応し、より個別性の高い業務ニーズを満たします。

### ユースケース

本ソリューションは、OA承認の基本的な統合を完了し、さらに高度なカスタマイズを必要とする組織に適しています。代表的なユースケースは次のとおりです。

- **ワンストップの没入型承認**：企業の経営層は日々大量の承認を処理しています。複数のサードパーティシステムと DingTalk の承認フローを自社アプリに集約し、一元的に一括処理したいと考えています。
- **管理者による作業フローの引き継ぎ**：社員の退職や異動の際、管理者はその社員の未処理の承認タスクを、組織内の他の在籍メンバーへ一括で転送する必要があります。
- **承認ページの高度な統合**：自社アプリの特定の業務モジュールから、DingTalk 公式 OA 承認のホームページ、インスタンス作成ページ、インスタンス詳細ページなどを直接開く必要があります。

## 代表的な業務シナリオ

### シナリオ 1：大手小売チェーンの店舗運営における承認の集約（小売業）

#### 課題

全国展開する小売チェーンは 500 以上の店舗を運営しています。店舗の補充申請には自社開発の POS システム、サプライヤーへの発注には SAP、スタッフのシフト設定と代休には自社開発の HR システムを使用しており、それぞれに独自の承認フローがあります。エリアマネージャーや本社の運営責任者は、毎日 3 つのシステムにログインして承認を確認・処理する必要があり、次のような問題が生じていました。

- **頻繁なシステム切り替え**：1 日 80 件以上の承認が 3 つのシステムに分散しています。切り替えのたびに再ログインして ToDo を探す必要があり、約 25 分を要していました。
- **一括操作ができない**：一括補充や一括シフト調整など、同種の承認をまとめて処理できません。承認者は 1 件ずつ「承認」をクリックする必要があり、反復作業による負担が大きくなっていました。
- **承認コンテキストの断片化**：POS システムでは関連するサプライヤーの在庫状況を確認できず、SAP では店舗の過去の販売データを確認できないため、意思決定に必要な情報がそろっていませんでした。

#### 効果の検証

- **自動化された作業フロー**

  自動化された統合フローは、次の 5 段階で実行されます。

  1. **複数システムの接続**：公式 OA、自社 OA、サードパーティシステム（POS、SAP、HR）を接続します。
  2. **ToDo の集約表示**：すべての未処理項目を統一ビューで表示し、ソースと種類で絞り込めます。
  3. **一括操作**：同じ種類の項目を複数選択し、ワンクリックで承認します。
  4. **没入型の詳細表示**：項目の詳細ページを開くと、在庫や過去の販売実績などの関連データが表示され、意思決定を支援します。
  5. **ステータスのリアルタイム同期**：コールバックイベントを通じて結果を各ソースシステムに書き戻し、データの整合性を保ちます。
- **主なメリット**

  - **複数ソースの集約**：POS の補充、SAP の調達、HR のシフト設定に関する承認を 1 つの統一ビューに表示します。システムを切り替える必要がなく、1 日あたり 25 分を削減できます。
  - **一括処理による効率化**：同種の承認を選択して一括で承認できます。1 回あたりのクリック数が 80 回から 3 回に減り、高頻度の業務シナリオで効率が 90% 以上向上します。
  - **完全なコンテキスト**：自社承認センターの詳細ページに各システムのデータ API を組み込みます。承認者は、関連する在庫や過去の販売実績など、意思決定を支援する情報を 1 つのページで確認できます。

### シナリオ 2：全国規模の物流ハブパークにおける承認統合（物流・倉庫業）

#### 課題

全国規模の物流ハブパークには 200 以上の組織が入居しており、各組織は異なる ERP/WMS システムで倉庫業務を管理しています。パーク管理委員会は、労働安全、環境コンプライアンス、消防点検に関する承認を一元的に監督する必要があります。従来の監督体制には、次のような問題がありました。

- **監督の分断**：200 以上の組織がそれぞれ異なるシステムを使用しているため、委員会はパーク全体の安全・コンプライアンス状況を把握できません。危険源の把握は自己申告に依存しており、隠ぺいや報告漏れが多発していました。
- **是正対応の追跡が困難**：違反が見つかると、委員会はオフラインで是正通知を出し、電話でフォローアップし、現地で確認する必要がありました。デジタルで追跡できないため、是正完了率は 65% にとどまっていました。
- **緊急対応の遅れ**：危険化学品の漏えいや火災報知など、緊急時には複数部門による協働承認が必要です。従来の電話による調整では時間がかかりすぎ、最適な対応のタイミングを逃していました。

#### 効果の検証

- **自動化された作業フロー**

  統合された自動化フローは、次の 5 段階で実行されます。

  1. **200 以上の組織の接続**：安全コンプライアンス情報を一元的に集約します。
  2. **危険源の段階別アラート**：自動で等級を判定し、リアルタイムでプッシュ通知します。等級は **重大危険源**、**重要危険源**、**一般危険源**、**低リスク** の 4 段階です。
  3. **ワンクリックで是正指示**：指示の発行と進捗の追跡を行います。
  4. **緊急時の協働承認**：自動でトリガーされ、緊急指令センターを通じて複数部門が連携します。
  5. **是正率のリアルタイム同期**：是正率が 65% から 95% に向上し、データの整合性も保たれます。
- **主なメリット**

  - **リスクの完全な可視化**：200 以上の組織の安全・コンプライアンス状況を 1 つの画面に表示します。危険源は自動で等級付けされてフラグが立てられ、隠ぺいや報告漏れの発生率は 5% 未満に低下します。
  - **是正対応のクローズドループ化**：違反に対してワンクリックで是正指示を発行できます。システムが進捗を自動で追跡し、期限を過ぎた組織にリマインドを送信するため、是正完了率は 65% から 95% に向上します。
  - **緊急時の連携**：緊急事態が発生すると、複数部門による協働承認が自動でトリガーされます。対応時間は 2 時間から 10 分に短縮され、最適な対応のタイミングを逃しません。

## 実装ガイド

### 技術アーキテクチャ

本ソリューションの技術アーキテクチャは、次の主要コンポーネントで構成されます。

- **認証レイヤー**：アプリの認証情報を管理し、アクセストークンを取得して、すべての API 呼び出しの呼び出し元を検証します。
- **データ集約レイヤー**：DingTalk OA承認プレミアム版の専用 API を呼び出し、公式 OA 承認や自社 OA 承認など、複数のソースからの ToDo データを統一リストに集約します。
- **一括処理レイヤー**：承認タイプ `processType` によって公式承認タスクと自社承認タスクを区別し、それぞれに対応する一括更新 API を呼び出してステータスを同期します。
- **作業フロー引き継ぎレイヤー**：管理者が特定の社員の未処理タスクリストを照会し、組織内の他の在籍メンバーへ一括で転送できるようにします。
- **ページ統合レイヤー**：AppLink プロトコルを使用して、自社アプリから DingTalk 公式 OA 承認のホームページ、インスタンス作成ページ、インスタンス詳細ページなどへ遷移します。
- **イベントコールバックレイヤー**：承認タスクの開始・終了・転送や、承認インスタンスのステータス変更などのコールバックイベントを受信し、自社承認センターのデータを最新の状態に保ちます。

### 前提条件

- **アプリの準備**：[アプリの作成と設定](/ja/open/dingstart/create-application)を完了していること。
- **権限要件**：DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請していること。

  - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）
  - `Premium.Workflow.ReadWrite.All`（OA承認作業フローの読み取り/書き込み権限（OA プレミアム版専用））
  - `qyapi_aflow`（承認フローのデータ管理権限）
- **開発環境**：Java 開発環境（JDK 1.6 以降）と Maven ビルドツールをインストールしていること。
- **SDK の準備**：DingTalk のサーバーサイド SDK をダウンロードしていること。Java、Python、Go などの言語に対応しています。

### コードの実装

ステップ 1：アプリの詳細ページを開き、アプリのクライアント ID と Client Secret を取得します。

ステップ 2：API 権限を申請します。「OA承認」関連の権限を申請してください。

ステップ 3：アプリのアクセス認証情報を取得します。[社内アプリのアクセストークンを取得](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。API を呼び出す際は、アクセストークンを使用して呼び出し元を認証します。

ステップ 4：OA承認の API を呼び出します。

1. 統合方法を選択します。

   - **自社 OA 承認との統合**：各サードパーティ業務システムを DingTalk の自社 OA 承認に接続します。詳しくは、[自社 OA 承認：サードパーティのプロセスおよびページとの連携](/ja/open/development/use-three-party-process-and-page-docking)を参照してください。
   - **公式 OA 承認との統合**：サードパーティ業務システムを DingTalk の公式 OA 承認に接続します。詳しくは、[公式 OA 承認：DingTalk のプロセスおよびページとの連携](/ja/open/development/use-the-dingtalk-oa-approval-process-and-page-interface)を参照してください。
   - **ユーザーによる申請**：ユーザーが DingTalk 公式 OA 承認アプリから直接承認フローを申請します。上記 2 つの方法と組み合わせることで、分散した業務フローを DingTalk OA承認の承認センターに集約できます。
2. **承認センターのデータを取得する**：プレミアム版専用 API を使用して、DingTalk 承認センターからユーザーの未処理、処理済み、申請済み、受信した承認の一覧を取得します。
3. **承認タスクを一括処理する**：自社承認センターアプリでユーザーのタスクリストを取得した後、未処理一覧 API が返す承認タイプ `processType`（0：公式 OA 承認、1：自社 OA 承認）に基づき、公式 OA 承認と自社 OA 承認のタスクをそれぞれ一括更新します。

   - **自社 OA 承認タスクの一括更新**：承認インスタンスの `processInstanceId` と `taskId` に基づき、[プロセスセンターのタスクステータスを更新](/ja/open/development/update-process-center-task-status) API を呼び出して、自社承認の ToDo のステータスを同期します。いずれか 1 名の承認で完了する（OR 署名）シナリオなどでは、[プロセスセンターの未処理タスクの一括キャンセル](/ja/open/development/cancel-multiple-oa-approval-tasks) API を呼び出し、承認インスタンス配下で実行中のすべての ToDo を CANCELED に設定します。
   - **公式 OA 承認タスクの一括更新**：承認インスタンスの `processInstanceId` と `taskId` に基づき、業務システムから承認タスクを一括で承認または却下する新しいサーバー API を呼び出し、承認インスタンス ID やタスクノード ID が異なる複数のタスクをまとめて処理します。
4. 承認フォームのステータスが変わると、OA承認は承認タスクのステータス変更や承認インスタンスのステータス変更などのコールバックイベントを業務システムにプッシュします。これにより、組織のアプリと DingTalk プラットフォームをより深く統合し、情報共有と業務連携を実現できます。詳しくは、[イベントサブスクリプションガイド](/ja/open/development/event-subscription-overview)を参照してください。
5. 管理者向けの特定社員の未処理タスクリストを照会する API を呼び出します。管理者（`managerUserId`）が、現在の承認者の UserId に紐づくすべての未処理 OA承認タスクを照会します。
6. 管理者向けの特定社員の未処理タスクを一括転送する API を呼び出します。管理者は、照会 API で取得したタスクを、組織内の他の在籍メンバーへ一括で転送します。

## 実装手順

### **ステップ 1：アプリの認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/)にログインします。
2. 対象のアプリを選択し、アプリの詳細ページを開きます。
3. **基本情報** > **認証情報と基本情報** をクリックします。
4. アプリの `Client ID` と `Client Secret` を控えておきます。

### 注意

   `Client Secret` は安全に保管し、第三者と共有しないでください。コードにハードコーディングせず、環境変数やキー管理システムに保存してください。

### ステップ 2：API 権限を追加する

1. アプリの詳細ページで **権限管理** をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）：プロセスセンターの未処理タスクを一括キャンセルする際に使用します。
   - `Premium.Workflow.ReadWrite.All`（OA承認作業フローの読み取り/書き込み権限（OA プレミアム版専用））：DingTalk 承認センターからユーザーの未処理、処理済み、申請済み、受信した一覧を取得する際に使用します。
   - `qyapi_aflow`（承認フローのデータ管理権限）：プロセスセンターのタスクステータスを更新する際に使用します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。実際のニーズに応じて申請してください。
</Note>

### ステップ 3：アクセス認証情報（アクセストークン）を取得する

ステップ 1 で取得した Client ID と Client Secret を使用して、アプリのアクセス認証情報を取得します。[社内アプリのアクセストークンを取得](/ja/open/development/obtain-the-access-token-of-an-internal-app)を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ戦略**：`accessToken` の有効期間は 2 時間です。メモリまたは Redis にキャッシュし、有効期限の 5分前に事前に更新してください。
- **同時実行制御**：複数のスレッドが同時にトークンを更新して競合が発生しないよう、分散ロックを使用してください。
- **エラー時のリトライ**：ネットワークが不安定な場合は自動でリトライします。最大 3 回まで、間隔を段階的に延ばしてください（1 秒 → 2 秒 → 4 秒）。

### ステップ 4：主要な API を呼び出す

1. **統合方法を選択する**：

   - **自社 OA 承認との統合**：各サードパーティ業務システムを DingTalk の自社 OA 承認に接続します。DingTalk の **自社 OA 承認 API** を使用して、業務システムの承認タスクデータを DingTalk OA承認のプロセスセンターに同期します。詳しくは、[自社 OA 承認：サードパーティのプロセスおよびページとの連携](/ja/open/development/use-three-party-process-and-page-docking)を参照してください。
   - **公式 OA 承認との統合**：サードパーティ業務システムを DingTalk の公式 OA 承認に接続します。DingTalk の **公式 OA 承認 API** を使用して、業務システムから DingTalk 公式 OA 承認の承認フローを直接開始します。詳しくは、[公式 OA 承認：DingTalk のプロセスおよびページとの連携](/ja/open/development/use-the-dingtalk-oa-approval-process-and-page-interface)を参照してください。
   - **ユーザーによる申請**：ユーザーが DingTalk 公式 OA 承認アプリから直接承認フローを申請します。上記 2 つの方法と組み合わせることで、分散した業務フローを DingTalk OA承認の承認センターに集約できます。
2. **承認センターのデータを取得する**：OA承認プレミアム版専用 OpenAPI およびソリューションの新規リリースに関するお知らせで紹介されているプレミアム版専用 API を使用して、DingTalk 承認センターからユーザーの未処理、処理済み、申請済み、受信した承認の一覧を取得します。

   ```java
         // err には code と message 属性が含まれており、開発者が問題を特定する際に役立ちます
         System.out.println(err.code);
         System.out.println(err.message);
       }
     } catch (Exception _err) {
       TeaException err = new TeaException(_err.getMessage(), _err);
       if (!com.aliyun.teautil.Common.empty(err.code) && !com.aliyun.teautil.Common.empty(err.message)) {
         // err には code と message 属性が含まれており、開発者が問題を特定する際に役立ちます
         System.out.println(err.code);
         System.out.println(err.message);
       }
     }
   }
   ```

### リクエストパラメータ：

   - `transfereeUserId`：元の操作者の userId。在籍社員と退職済み社員の両方に対応しています。

## よくある質問

- **Q：承認タスクの一括承認・却下 API では、最大何件のタスクを処理できますか？**

  1 回の一括操作で処理できるタスクは最大 10 件です。未処理タスクが 10 件を超える場合は、タイムアウトやレート制限を避けるため、1 回あたり 10 件以下に分けて API を呼び出してください。
- **Q：processType パラメータで、公式 OA 承認と自社 OA 承認をどのように区別しますか？**

  承認センターの一覧照会 API が返す各タスクオブジェクトには、`processType` フィールドが含まれています。値が 0 の場合は公式 OA 承認、1 の場合は自社 OA 承認を表します。一括処理の際は、このフィールドに基づいて対応する更新 API を呼び出してください。
