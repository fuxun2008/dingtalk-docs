# サードパーティ作業フローの承認ページホスティング：公式詳細ページとカスタムアクションエリアの統合

## 概要

本ソリューションは、自社の作業フローエンジンを運用しているものの、モバイル版や H5 版の詳細ページを持たない組織を対象としています。こうした組織は、DingTalk の公式 OA 承認詳細ページのスタイルを再利用しながら、承認アクションエリアのボタンをカスタマイズしたいと考えています。DingTalk OA承認のプロセスセンターが提供する承認ページホスティング API を使うと、サードパーティの業務システムは承認テンプレートまたは承認インスタンスの作成時に、2 つのコールバック API を登録できます。1 つはアクションエリアのカスタムボタンを描画し、もう 1 つはボタンの操作を実行します。承認者は DingTalk で公式 OA 承認詳細ページを開き、作業フローを処理します。これにより、承認者はどのデバイスでも一貫した操作体験を得られます。サードパーティ側では、「同意」「拒否」「転送」などのアクションボタンやエラーメッセージを設定できます。

### 背景

契約審査やプロジェクト立ち上げなどの複雑な承認シナリオでは、DingTalk の承認詳細ページ内に業務専用のアクションエリアが必要です。同時に、DingTalk 公式の承認ヘッダーにあるデフォルトフィールドも必要になります。ページホスティングを利用すると、1 つの詳細ページに DingTalk の標準承認情報と業務専用のアクションパネルを統合できます。標準化と柔軟性を両立できるアプローチです。

組織は日常業務で、次のような課題に直面しがちです。

- **情報表示の分断：** DingTalk の標準承認ページでは、添付ファイルのプレビュー、関連ドキュメント、バージョン履歴などの業務固有の情報を表示できません。承認者は別のページに切り替えて確認する必要があります。
- **アクションボタンの不足：** 承認詳細ページには、「契約書原本を表示」や「添付ファイルをダウンロード」などの業務固有の導線がありません。承認者は元システムの URL を覚えておき、手動で開く必要があります。
- **スタイルの競合が頻発：** 埋め込んだ業務ページが DingTalk 公式のスタイルと合わないことがよくあります。スクロールバーの重複、ボタンの非表示、フォントのずれなどが発生し、承認体験が損なわれます。
- **複雑な権限制御：** ロールごとに、承認詳細ページで表示すべきアクションエリアやデータフィールドが異なります。既存のホスティング方式では、このような細かい粒度で権限を分離することが困難です。

### 主な価値

本ソリューションは、次の 3 つの面で価値を提供します。

- **統一された体験：** 複数の業務システムの承認フォームを、DingTalk の公式 OA 承認詳細ページ上で統一された構成とスタイルに揃えます。モバイル、PC、タブレットのいずれでも一貫した体験を提供します。
- **追加コストゼロの統合：** ホスティング後は、IM や ToDo などの DingTalk ネイティブ機能と追加コストなしで連携します。承認効率を高める多くの機能を利用でき、サードパーティの承認もネイティブの承認と同じように扱えます。
- **柔軟なカスタマイズ：** サードパーティ側で、詳細ページの承認アクションエリアにある「同意」「拒否」「転送」などのボタンをカスタマイズし、さまざまな業務要件に対応できます。

### ユースケース

本ソリューションは、自社の作業フローエンジンを運用しているものの詳細ページがなく、DingTalk 公式のスタイルを再利用しつつアクションエリアをカスタマイズしたい組織に適しています。代表的なユースケースは次のとおりです。

- **モバイル版詳細ページがない：** 企業の承認システムがモバイルや H5 のページに対応していないため、従業員、特に管理職が DingTalk 上で承認できません。承認ホスティングを利用すると、低コストで全デバイスに統一された DingTalk の承認体験を提供できます。
- **ネイティブ機能との連携：** 承認者は、承認業務を DingTalk のネイティブ機能とより効果的に連携させ、効率を高めたいと考えています。ホスティング後は、ワンクリックでのグループ作成、チャットへの共有、チャットやドキュメントへのリンクのコピー、印刷、ダウンロードなどの機能を追加コストなしで利用できます。
- **作業フロー効率のガバナンス：** 経営層は、社内の作業フロー効率を体系的に分析・改善したいと考えています。ホスティング後は、効率診断とプロセスマイニングにより、効率上の問題や不合理な作業フローを特定できます。さらに DingTalk が、自社の作業フローガバナンスの実践に基づいて最適化の提案を行います。

## 代表的な業務シナリオ

### シナリオ 1：フィットネスチェーンの店舗運営における承認ホスティング（スポーツ・フィットネス）

#### 課題

全国展開するあるフィットネスチェーンは、120 以上の店舗を運営しています。自社開発の店舗運営システムで、機器購入、パーソナルトレーニングのスケジュール、会員の返金、施設メンテナンスの 4 つの承認作業フローを運用しています。4 つの作業フローはそれぞれ独立しており、いずれもモバイル版や H5 版の詳細ページがありません。エリアマネージャーや店長は毎日多くの承認を処理しています。従来の作業フローには次の課題がありました。

- **デバイス間で体験が分断：** 1 日あたり 90 件以上の承認が発生します。承認者は承認の詳細を確認するために、PC で店舗運営システムにログインする必要があります。モバイルでは通知を受け取れるものの、詳細の確認や操作はできません。エリアマネージャーの出張中は、緊急の購入承認が遅れ、店舗運営に支障が出ていました。
- **ネイティブ機能の欠如：** 「機器の故障による緊急修理」などの承認を受け取ると、承認者は承認リンクを手動でコピーし、メンテナンス担当のグループに送信する必要があります。ワンクリックでのグループ作成やチャットへのリンク共有ができず、操作のたびに 2 分余計にかかっていました。
- **インターフェースの不統一：** 4 種類の承認詳細ページはそれぞれ異なるスタイルを採用しています。新任の店長が慣れるまでに最大 3 週間かかり、作業フローの不統一によってエラー率は最大 8% に達していました。

#### 提供価値

- **自動化された作業フロー**

  自動化された統合フローは、次の 5 つのステップで構成されます。

  1. **承認テンプレートを作成：** **processCode** を取得します。
  2. **描画コールバックを登録：** **PAGE_HOST** を設定します。
  3. **承認インスタンスを同期：** **featureConfig** を紐付けます。
  4. **ホスティングされた詳細ページを表示：** 公式スタイルとカスタムボタンを組み合わせて表示します。
  5. **アクションエリアのカスタム操作を実行：** コールバックを実行し、ステータスを同期します。
- **主なメリット**

  - **全デバイスで統一：** 詳細ページは PC、モバイル、タブレットで同じように表示されます。エリアマネージャーは出張中でもスマートフォンで承認の詳細をすべて確認し、操作できます。緊急購入の対応時間は 2 時間から 10 分に短縮されました。
  - **ネイティブ機能との統合：** 承認詳細ページに、ワンクリックでのグループ作成、チャットへのリンク共有、印刷、ダウンロードなどの機能が組み込まれています。承認者がリンクを手動でコピーする必要がなくなり、承認 1 件あたりのコミュニケーション時間は 2 分からゼロになりました。
  - **柔軟なカスタマイズ：** 機器購入の承認には「購入を確定」と「却下して再選定」のボタンを、会員返金の承認には「返金を承認」と「追加書類を依頼」のボタンを表示します。承認の種類ごとにアクションエリアを個別に設定することで、エラー率は 8% から 1% に低下しました。

### シナリオ 2：動物病院チェーンにおける承認ホスティング統合（ペットサービス）

#### 課題

ある大手動物病院チェーンは、30 以上の分院を運営しています。自社開発の診療管理システムで、薬品購入、手術計画、入院費の減免、機器修理の 4 つの承認作業フローを運用しています。4 つの作業フローはそれぞれ独立しており、いずれもモバイル版や H5 版の詳細ページがありません。院長や診療科の責任者は毎日多くの承認を処理しています。従来の作業フローには次の課題がありました。

- **緊急承認への対応の遅れ：** 1 日あたり 70 件以上の承認が発生します。動物の容態は急変することがあるため、手術計画の承認には高い即時性が求められます。しかし承認者は、計画の詳細を確認するために PC で診療システムにログインする必要があり、モバイルでは操作できません。承認の遅れが原因で、手術の最適なタイミングを逃したケースが 3 回発生しました。
- **部門間連携の非効率：** 複雑な手術計画には、外科、麻酔科、画像診断科の確認が必要です。承認者は 3 つのシステムで計画の詳細を個別に確認する必要があり、調整に最大 1 日かかっていました。待機時間が長引くほど、動物の医療リスクが高まります。
- **効率データの不在：** 経営層は各部門の承認のボトルネックを分析したいと考えています。しかし自社システムには作業フローの統計カンバンがないため、承認の滞留箇所を特定できず、最適化の判断に必要なデータも不足していました。

#### 提供価値

- **自動化された作業フロー**

  自動化された統合は次の 5 つのステップで進め、各ステップに主要な設定があります。

  1. **承認テンプレートを作成：** `processCode` を取得します。
  2. **描画コールバックを登録：** `PAGE_HOST` を設定します。
  3. **承認インスタンスを同期：** `featureConfig` で紐付けます。
  4. **詳細ページをホスティング：** 公式スタイルとカスタムボタンを組み合わせて表示します。
  5. **アクションエリアでカスタム操作を実行：** コールバックを実行し、効率カンバンに反映します。

  ホスティングされた承認詳細ページには、**申請者**、**部門**、**患畜情報**、**処置内容**、**予定日時**、**計画の説明**、**添付** などのフィールドが表示され、**却下**、**保存**、**承認** の操作が可能です。データは診療管理システム、DingTalk 承認センター、効率カンバンの間でリアルタイムに同期されます。
- **主なメリット**

  - **モバイルでの承認：** 手術計画の詳細ページがモバイルでもすべて表示されます。院長は病棟回診中でも詳細を確認して承認できます。手術の準備時間は 4 時間から 30 分に短縮され、最適なタイミングを逃すケースはゼロになりました。
  - **連携の迅速化：** 複数部門の確認が必要な承認でも、関連情報をすべて 1 つの詳細ページで確認できます。調整時間は 1 日から 2 時間に短縮され、待機中の動物のリスクが大幅に低減しました。
  - **効率の可視化：** ホスティング後、承認データは DingTalk 公式の承認効率カンバンに集約されます。経営層は、OA承認アシスタントからのプッシュ通知、またはモバイルアプリの［OA承認］>［統計］から作業フロー効率レポートを確認し、滞留箇所を特定できます。

## 実装ガイド

### 技術アーキテクチャ

本ソリューションの技術アーキテクチャは、次の主要コンポーネントで構成されます。

- **認証レイヤー：** アプリ認証情報を管理し、アクセストークンを取得して、すべての API 呼び出しの身元を検証します。
- **テンプレートホスティングレイヤー：** サードパーティ承認テンプレートを作成・更新する API を呼び出します。サードパーティ業務システムの承認テンプレートを DingTalk 承認センターに同期し、テンプレートの一意なコード `processCode` を取得します。また、アクションエリアのカスタムボタンを描画するためのコールバック URL をテンプレートに登録します。
- **インスタンスホスティングレイヤー：** 承認インスタンスを作成・更新する API を呼び出します。サードパーティシステムの承認インスタンスを DingTalk 承認センターに同期し、承認インスタンス ID `processInstanceId` を取得します。また、アクションエリアのカスタムボタンを実行するためのコールバック URL をインスタンスに登録します。
- **コールバック描画レイヤー：** サードパーティシステムが HTTPS のコールバック API を提供します。DingTalk の承認アクションエリアのボタン描画リクエストを受け取り、カスタムボタンの設定を返します。DingTalk はこのデータを使って、詳細ページ下部のアクションエリアを描画します。
- **コールバック実行レイヤー：** サードパーティシステムが HTTPS のコールバック API を提供します。DingTalk の承認アクションエリアのボタン実行リクエストを受け取り、ユーザーの承認操作を処理して結果を返します。DingTalk はこの結果を使って承認ステータスを更新します。
- **タスク同期レイヤー：** 承認 ToDo タスクを作成・更新・照会する API を呼び出します。サードパーティシステムの承認 ToDo タスクを DingTalk 承認センターに同期し、データの整合性を保ちます。

### 前提条件

- **アプリの準備：** [アプリの作成と設定](/ja/open/dingstart/create-application) の手順を完了してください。
- **権限の要件：** DingTalk の組織管理者またはサブ管理者の権限を持ち、次の API 権限を申請してください。

  - `qyapi_aflow`（承認作業フローのデータ管理権限）
  - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）
  - `Workflow.Form.Read`（作業フローテンプレートの読み取り権限）
  - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）
  - `Premium.Workflow.ReadWrite.All`（OA承認作業フローの読み取り・書き込み権限）
- **開発環境：** Java 開発環境（JDK 1.6 以降）と Maven ビルドツールをインストールしてください。
- **SDK の準備：** DingTalk のサーバーサイド SDK をダウンロードしてください。Java、Python、Go などの言語に対応しています。
- **ゲートウェイの準備：** サードパーティシステムのコールバック API を、DingTalk の「データソース管理」でゲートウェイとして登録してください。詳細はデータソースを参照してください。

### コードの実装

ステップ 1：アプリの詳細ページに移動し、アプリのクライアント ID と Client Secret を取得します。

ステップ 2：API 権限を申請します。「OA承認」関連の権限を申請してください。

ステップ 3：アプリのアクセス認証情報を取得します。[社内アプリのアクセストークンを取得](/ja/open/development/obtain-the-access-token-of-an-internal-app) を参照してください。API を呼び出す際、アクセストークンによって呼び出し元の身元が認証されます。

ステップ 4：主要な API を呼び出します。

1. 承認ボタンのカスタマイズ用コールバック API を登録します。外部データ API へのゲートウェイコールバックは、すべて「データソース管理」でゲートウェイとして登録する必要があります。詳細はデータソースを参照してください。
2. 新しいサーバー API「プロセスセンターで外部統合承認テンプレートを保存」を呼び出し、テンプレートの一意なコード `processCode` を取得します。
3. `processCode` を保存していない場合は、[テンプレートコードを取得](/ja/open/development/obtain-the-template-code) API を呼び出して取得します。
4. 承認テンプレートの作成後、ユーザーは DingTalk OA承認の管理コンソールで、サードパーティの承認フォームテンプレートの確認、テンプレートデータの表示・検索、テンプレートデータのエクスポート・削除を行えます。
5. テンプレートコード `processCode` を使って、新しいサーバー API「プロセスセンターで外部統合承認インスタンスを保存」を呼び出し、承認インスタンスを開始して承認インスタンス ID `processInstanceId` を取得します。
6. インスタンスの作成後、ユーザーは DingTalk OA承認の承認センターで、4 つの承認リスト（未処理、処理済み、申請済み、受信）の表示、承認インスタンスデータの検索、承認の処理を行えます。
7. `processInstanceId` と `tasks` を使って「プロセスセンターで外部統合承認タスクを保存」を呼び出し、各 ToDo 項目の `taskId` を取得して、対応する DingTalk の ToDo タスクを生成します。
8. 未処理タスクの作成後、[プロセスセンター経由で統合された OA 承認タスクを照会](/ja/open/development/query-oa-approval-tasks-integrated-through-process-center) API を呼び出し、ユーザーの進行中の承認タスクを照会します。
9. 承認インスタンスの `processInstanceId` と承認 ToDo タスクの taskId を使って、[プロセスセンターのタスクステータスを更新](/ja/open/development/update-process-center-task-status) API を呼び出し、自社の承認 ToDo 項目のステータス更新を同期します。OR 承認（いずれかの承認者が承認すれば完了）などのシナリオでは、[プロセスセンターの未処理タスクを一括キャンセル](/ja/open/development/cancel-multiple-oa-approval-tasks) API を呼び出し、承認インスタンス配下の進行中の ToDo 項目をすべて一括で CANCELED に設定します。
10. 承認インスタンスの `processInstanceId`、インスタンスステータス `status`、インスタンス結果 `result` などの値を使って、[インスタンスステータスを更新](/ja/open/development/update-instance-status) API または [インスタンスステータスを一括更新](/ja/open/development/self-owned-batch-update-of-instance-status) API を呼び出し、インスタンスステータスを更新します。
11. 承認テンプレートのデータをクリーンアップするには、[テンプレートを削除](/ja/open/development/self-owned-approval-deletion-template) API を呼び出します。社内向けに作成した承認テンプレートと、その配下で作成されたすべてのインスタンスおよび ToDo タスクが削除されます。

## 実装手順

### **ステップ 1：アプリ認証情報を取得する**

1. [DingTalk 開発者コンソール](https://open-dev.dingtalk.io/) にログインします。
2. 対象のアプリを選択し、アプリの詳細ページを開きます。
3. **［基本情報］** > **［認証情報と基本情報］** をクリックします。
4. アプリの `Client ID` と `Client Secret` を控えておきます。

### 注意

   `Client Secret` は安全に保管し、第三者と共有しないでください。ハードコーディングせず、環境変数またはキー管理システムに保存してください。

### ステップ 2：API 権限を追加する

1. アプリの詳細ページで **［権限管理］** をクリックします。
2. 権限の検索ボックスに次の権限識別子を入力し、申請します。

   - `qyapi_aflow`（承認作業フローのデータ管理権限）：プロセスセンターのタスクステータスを照会・更新します。
   - `Workflow.Form.Write`（作業フローテンプレートの書き込み権限）：テンプレートコードを取得します。
   - `Workflow.Form.Read`（作業フローテンプレートの読み取り権限）：承認インスタンスを作成・更新し、テンプレートを削除します。
   - `Workflow.Instance.Write`（ワークフローインスタンスの書き込み権限）：インスタンスステータスを更新します。
   - `Premium.Workflow.ReadWrite.All`（OA承認作業フローの読み取り・書き込み権限）：プロセスセンターで外部統合承認テンプレートまたは承認タスクを保存します。

<Note>
業務シナリオによって、必要な権限の組み合わせは異なります。実際の要件に応じて権限を申請してください。
</Note>

### ステップ 3：アクセス認証情報（アクセストークン）を取得する

ステップ 1 で取得した Client ID と Client Secret を使って、アプリのアクセス認証情報を取得します。[社内アプリのアクセストークンを取得](/ja/open/development/obtain-the-access-token-of-an-internal-app) を参照してください。

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**ベストプラクティス**：

- **キャッシュ：** `accessToken` の有効期間は 2 時間です。メモリまたは Redis にキャッシュし、有効期限の 5分前に更新してください。
- **同時実行制御：** 複数のスレッドが同時にトークンを更新することによる競合を防ぐため、分散ロックを使用してください。
- **エラー時のリトライ：** ネットワークが不安定な場合は自動的にリトライします。最大 3 回まで、間隔を段階的に延ばしてください（1s → 2s → 4s）。

### ステップ 4：主要な API を呼び出す

1. **承認アクションボタンエリアのカスタマイズ用コールバック API を登録する：** サードパーティシステムにアクションエリアのボタン定義を要求するコールバック（ボタン描画）を登録します。さらに、ユーザーが送信した承認内容をサードパーティの API に送って処理させるコールバック（承認操作）を登録します。プロトコルの詳細は、[承認アクションエリアのホスティング API プロトコル](/ja/open/development/detailed-explanation-of-hosting-interface-agreement-in-approval-operation-area) を参照してください。
2. **承認テンプレートのデータを DingTalk に同期する：** 新しいサーバー API「プロセスセンターで外部統合承認テンプレートを保存」を呼び出し、テンプレートの一意なコード `processCode` を取得します。

   ```java
   public void getProcessCodeByName() throws Exception {
       Config config = new Config();
       config.protocol = "https";
       config.regionId = "central";

       com.aliyun.dingtalkworkflow_1_0.Client client = new com.aliyun.dingtalkworkflow_1_0.Client(config);

       GetProcessCodeByNameHeaders getProcessCodeByNameHeaders = new GetProcessCodeByNameHeaders();
       getProcessCodeByNameHeaders.xAcsDingtalkAccessToken = "accessToken";

       GetProcessCodeByNameRequest request = new GetProcessCodeByNameRequest()
               .setName("テンプレート名");

       try {
           GetProcessCodeByNameResponse getProcessCodeByNameResponse = client.getProcessCodeByNameWithOptions(
                   getProcessCodeByNameRequest,
                   getProcessCodeByNameHeaders,
                   new com.aliyun.teautil.models.RuntimeOptions()
           );
       } catch (TeaException err) {
           if (!com.aliyun.teautil.Common.empty(err.code) && !com.aliyun.teautil.Common.empty(err.message)) {
               // err には code 属性と message 属性が含まれ、開発者が問題を特定するのに役立ちます
               System.out.println(err.code);
               System.out.println(err.message);
           }
       } catch (Exception _err) {
           TeaException err = new TeaException(_err.getMessage(), _err);
           if (!com.aliyun.teautil.Common.empty(err.code) && !com.aliyun.teautil.Common.empty(err.message)) {
               // err には code 属性と message 属性が含まれ、開発者が問題を特定するのに役立ちます
               System.out.println(err.code);
               System.out.println(err.message);
           }
       }
   }
   ```

   - `name`：テンプレート名。

### レスポンスフィールド

   - `processCode`：承認フォームテンプレートの一意なコード。
4. 承認テンプレートの作成後、ユーザーは DingTalk OA承認の管理コンソールで、サードパーティの承認フォームテンプレートの確認、テンプレートデータの表示・検索、テンプレートデータのエクスポート・削除を行えます。

### レスポンスフィールド

   - `processInstanceId`：承認インスタンスの一意な ID。
6. 承認インスタンスの作成後、ユーザーは DingTalk OA承認の承認センターでも、4 つの承認リスト（未処理、処理済み、申請済み、受信）の表示、承認インスタンスデータの検索、承認の処理を行えます。
7. **承認タスクのデータを DingTalk に同期する：** 承認インスタンスの `processInstanceId` と ToDo リスト `tasks` を使って、「プロセスセンターで外部統合承認タスクを保存」を呼び出します。サードパーティシステムの承認ノード情報が DingTalk OA承認に同期され、各 ToDo 項目の taskId が返されて、対応する DingTalk の ToDo タスクが生成されます。

## よくある質問（FAQ）

- **Q：renderCallback と executeCallback の違いは何ですか？**

  - DingTalk は `renderCallback` を使って、ボタンのテキスト、色、表示・非表示など、アクションエリアのボタン定義をサードパーティシステムに要求します。その後、詳細ページ下部にアクションエリアを描画します。
  - DingTalk は `executeCallback` を使って、ユーザーがボタンをクリックした後に承認操作をサードパーティシステムに送信します。サードパーティシステムはリクエストを処理し、結果を返します。2 つのコールバックはそれぞれ役割が異なり、相互に置き換えることはできません。
- **Q：コールバック API がタイムアウトした場合はどうなりますか？**

  DingTalk は、サードパーティのコールバック API からのレスポンスを 5 秒間待機します。サードパーティシステムが 5 秒以内に HTTP 200 を返さない場合、DingTalk は 1s、2s、4s の間隔で最大 3 回リトライします。コールバック API は軽量に保ち、複雑なロジックは非同期で処理してください。
- **Q：アクションエリアのボタンの表示・非表示を動的に制御できますか？**

  はい、できます。`renderCallback` が返すボタン設定で、`visible` フィールドを使って各ボタンを表示するかどうかを制御します。承認者のロール、承認ステータス、業務条件などに応じて、ボタンの表示を動的に切り替えられます。
- **Q：承認ページのホスティング後、作業フローの効率データはどこで確認できますか？**

  ホスティング後、サードパーティの承認フローのデータは DingTalk 公式の承認効率カンバンに集約されます。経営層は、OA承認アシスタントからのプッシュ通知、またはモバイルアプリの［OA承認］>［統計］から作業フロー効率レポートを確認し、組織の承認業務の効率と妥当性を総合的に評価できます。
