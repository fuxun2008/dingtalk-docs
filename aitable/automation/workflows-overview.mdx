# What it does

An automation workflow is a rule you preset for an AI Table — and it runs automatically. Set a **trigger** and an **action** and AI Table fires the next steps when data changes.

# Manage automations

In an AI Table you can create, modify, and look up workflows.

1. **Global management**

   Click **Automation** — the left sidebar lists all workflows configured for this AI Table.

   ![](/aitable/automation/workflows-overview/images/image_Fh5gsG3Cz9.png)
2. **Execution log**

   On the workflow editor, click **Execution log** in the top-right — see total runs, successes, and failures.

   ![](/aitable/automation/workflows-overview/images/image_q9227mit9H.png)
3. **Enable / disable a workflow**

   In the workflow list, the toggle switches state — on = running, off = disabled.

   ![](/aitable/automation/workflows-overview/images/image_nyobwfWwav.png)
4. **Edit / Copy / Delete a workflow**

   Pick a workflow → click **More** → edit / copy / delete.

   ![](/aitable/automation/workflows-overview/images/image_SzybQxju_E.png)
5.  **Troubleshoot errors**

Click into an execution record's detail to one-click copy the error and dig into the cause.

# Common automation scenarios

## 01 Project demand management

⏰ Form submit → reminder:

After a demand-collection form is submitted, AI parses the demand type, links the right reviewer, and pings them via automation.

⏰ Content change → reminder:

When a project is approved, auto-create a project-specific group chat and to-dos.

⏰ Condition met → reminder:

When a project is close to its due date but not done, ping the project lead to follow up.

## 02 Admin procurement

⏰ Form submit → reminder + card-button → secondary automation / status update:

After a goods-request form is submitted, an automation card is sent to the approver. The approver clicks a button on the card to fire a follow-up automation:

1) If stocked: click **Approve**.

2) If out-of-stock: click **Out-of-stock notice**.

The card auto-syncs back to the requester.

The ticket status auto-updates too.

# Run-count metering

Automation runs on the DingTalk Connector Platform — every workflow node consumes connection-flow node executions.

### What is a node-execution count?

**Connection-flow node executions** (or "node executions") is the **commercial billing metric** of the DingTalk Connector Platform.

It tallies node runs across AI Table, bots, OA approvals, and the connector platform for the current org. Users with developer access can [view details](https://open-dev.dingtalk.com/fe/connector#/overView "view details") on the DingTalk Connector Platform.

### How to view this month's count

Go to **Workflow management** to see the org's accumulated runs for the month.

![](/aitable/automation/workflows-overview/images/image_Rx0KX-KEPw.png)

### Counting rules

#### Counted

- Successful action node — 1.
- **Delay** node call — 1.
- **HTTP request** node call — 1.
- **Branch** node — 1 per evaluation.
- A **Loop** node counts as 1 per workflow run, regardless of how many iterations. Set **Max iterations** carefully.
- When an action returns nothing, it still counts as a successful run (e.g. directory queries with no matches still count as 1).

#### Not counted

- Trigger event execution.
- Skipped nodes; failed nodes.
- Debug runs.
