Manual steps in premium workflows correspond to approval and executor steps in standard workflows. Manual steps support more comprehensive approval actions, such as step entry rules, step submission rules, and preconditions.

## Basic settings

Basic settings include step information, rule configuration, step action buttons, and batch approval configuration.

### Step information

Step information includes the step name, English name, and description.

### Rule configuration

#### Approver rule

Approver rules define who processes the step. Supported options include frequent approvers, department liaisons, specified approvers, department managers, consecutive multi-level managers, and other rules.

- Frequent approvers: In premium workflows, frequent approvers work the same as specified Role approval in standard workflows. Multiple users are tagged as a group, using either DingTalk Roles or Yida Roles.

<Note>
For details on configuring Roles, see [Role management](/yida/platform-admin/fb7uip).
</Note>

- Specified approver: Specifies fixed approvers for this step. Multiselect is supported.

- Department liaison: Department liaisons are managed on the platform management page. Set department liaisons on the Yida platform management page. For details, see Department liaison settings.

<Note>
**Note:**

A department liaison can be understood as a department contact. Although a department may have multiple levels of hierarchy, there is typically a designated department contact.
</Note>

- Department manager: Specifies the initiator's department manager, up to 20 levels of managers.

Three department filter configurations are supported:

- Consecutive multi-level managers: After the initiator submits the approval, the initiator's managers approve in sequence from the lowest to the highest level, until the designated endpoint. The endpoint can be a specific Role or a specific manager level.

For example, if the approver is set as the third-level manager, when the workflow reaches this step, approval proceeds sequentially from the initiator's (or User field's) first-level manager up to the third-level manager. Only after the third-level manager approves will the workflow proceed to the next step.

- Other rules: In addition to the above rules, approvers can also be set using variables, third-party services, or Groovy requests. Third-party services can be configured on the Yida service registration page and then selected directly in the workflow.

All services must be registered in Yida service registration before use, as shown below. (For details, see [**Service registration module**](https://www.yuque.com/yida/help-v2/volga8).)

#### Completion policy

The completion policy defines the execution rules for the lines following the step.

Lines are matched based on the rule names in the completion policy. The actions in the rule conditions are selected from the step action buttons defined in the step's basic attributes.

### Step action buttons

Step action button settings determine which buttons the approver sees at this step, and also define the action options for subsequent line execution rules.

<Note>
Accept and Decline are required and cannot be removed.
</Note>

| **Button** | **Description** |
|---|---|
| **Accept** | Accepts the current initiator's Approval form. |
| **Decline** | Declines the current initiator's Approval form. After the approver clicks Decline, the Approval form is terminated immediately. |
| **Save** | The Save action applies when the current approver needs to fill in additional information or modify approver details on the Approval form. When enabled, the approver sees the Save button on the Approval form. |
| **Transfer** | The Transfer action applies when the current step's approver cannot decide on the Approval form and needs an upper-level manager or other approver to handle it. When enabled, the approver sees the Transfer button on the Approval form. |
| **Sign request** | Sign request users in the approval workflow support **pre-sign** and **post-sign** configurations, which can be configured together.<br />• **Pre-sign**: Adds an approval step before the current approver. The approver of the added step is specified by the current approver. Multiple users can be added.<br />• **Post-sign**: Adds an approval step after the current step ends. The approver of the added step is specified by the current approver. Multiple users can be added. |
| **Return** | A workflow return occurs when the current step's approver is not satisfied with the submitted Approval form, or when the initiator's Approval form is incomplete. The approver returns the Approval form to the initiator or to a previous step.<br />Supports the following approval methods after return:<br />• **Re-approve sequentially**: If the steps are A => B => C and C returns the workflow to A, the workflow flows through A => B => C again. Each step triggers its corresponding Message notifications and business rules. Automatic triggering can also be disabled for all steps.<br />• **Approve from the current step**: If the steps are A => B => C and C returns the workflow to A, the workflow flows through C => A => C without triggering the corresponding Message notifications or business rules. |

### Batch approval

When one person needs to approve multiple Approval forms, batch approval saves time and improves work efficiency.

## Advanced settings

### Step ID

Uniquely identifies the step. If the workflow returns an Error, use the Step ID to quickly locate the faulty step.

### Dynamic vs. static

Static steps have their operators determined before the workflow is initiated. Dynamic steps have their operators determined after the workflow is initiated.

- When the approver rule is a frequent approver, department liaison, specified approver, department manager, consecutive multi-level manager, or variable, the operator is static.
- When approvers are determined through external services (third-party services or Groovy requests), the step is dynamic.

<Note>
Dynamic steps do not appear in prediction information.
</Note>

### Task assignment method

Simultaneous assignment means that if the step requires multiple approvers, tasks are assigned to all of them at once. Sequential assignment means tasks are assigned in order — only after the previous approver completes their approval is the task assigned to the next approver. Whether to push to the task center and require approval comments can be configured based on your needs.

### Auto-execution rule

The auto-execution rule allows the current step to be executed automatically when the approver is the workflow initiator or the approver of the previous task. (Applies only to workflow Forms.)

### Preconditions

The designer supports precondition settings. If the precondition rule is not met, the step is skipped, and the workflow follows the default outgoing line or the line that meets the conditions.

### Auto-completion rule

Auto-completion rules configure automatic approval rules based on Form Fields and system Fields at workflow initiation. When the conditions are met, the Accept or Decline action is executed automatically.

<Note>
If the selected condition is the initiator, enter the corresponding user's `["userid"]/Employee ID`. Entering the user's name directly does not work.
</Note>

### Timeout rule

If an approver does not process the Approval form for a long time, the step remains stuck and cannot proceed. To avoid affecting efficiency, configure a timeout rule to send a Work Notifications reminder to the approver, jump to another step, or transfer the task. Notification Templates can be configured in Template management.

### Message settings

To notify users other than the approver when the workflow reaches this step, add a Message notifications. You can include a workflow Link in the notification. However, users who are not workflow Admins and do not have instance View Permission cannot view the workflow. For details on selecting message Templates, see [**Message templates**](https://docs.aliwork.com/docs/yida_support/yida_qalist/cmggzu/lulrb1)**.**

### Step entry rule

The step entry rule is triggered when the manual step is entered. After selecting the corresponding service, the workflow automatically calls the associated service when it reaches this step.

## FAQ

- Q: Why can't the Accept and Decline buttons be disabled?

Disabling these two buttons is not currently supported. Click the eye icon on the right to hide them, which produces the same effect as Cancel.

- Q: When an approver returns the Approval form to the initiator for resubmission, do the previously approved intermediate steps need to be re-approved?

Yes. Currently, the return logic for premium workflows re-runs all intermediate steps after a return.

- Q: How many items can be approved at once with batch approval?

Batch approval displays 10 approval items per page by default, so up to 10 items can be approved at once.
