## Kes Penggunaan

- Apabila perniagaan anda memerlukan prestasi masa nyata yang tinggi untuk data. Contohnya, apabila pekerja baharu menyertai atau meninggalkan organisasi, aplikasi perlu mengemas kini data pengguna dengan segera. Dalam kes ini, langgan Peristiwa Kenalan.
- Apabila aplikasi anda perlu bertindak balas dengan segera terhadap tindakan pengguna. Contohnya, apabila pengguna menyertai Sembang Kumpulan, aplikasi boleh melanggan Peristiwa sembang kumpulan untuk menghantar mesej selamat datang apabila pengguna memasuki sembang kumpulan tersebut.

Ini hanyalah beberapa contoh kes penggunaan mudah. Pembangun boleh mengendalikan Peristiwa yang berbeza dengan cara yang berbeza.

## Proses Langganan Peristiwa

Proses Langganan peristiwa ditunjukkan dalam rajah di bawah.

Mula-mula, konfigurasikan URL penerimaan permintaan HTTP pada DingTalk Open Platform untuk menerima Peristiwa yang dilanggan yang di-push, kemudian tetapkan Peristiwa yang hendak dilanggan. Selepas anda mengonfigurasikan URL permintaan, DingTalk Open Platform menghantar Permintaan POST kepadanya. Langganan peristiwa hanya dianggap selesai apabila string tersulit yang mengandungi "**success**" dikembalikan dengan betul dalam masa yang ditetapkan.

## Konfigurasikan URL Permintaan dan Langganan Peristiwa

1. Log masuk ke [Developer Console](https://open-dev.dingtalk.com/) dan cari Aplikasi dalaman yang telah anda cipta.
2. Klik **Langganan peristiwa**, kemudian klik Edit untuk mengonfigurasikan URL HTTP yang digunakan untuk menerima permintaan.

   **Nota**

   Pastikan URL ini boleh diakses melalui rangkaian awam.

   Selepas anda mengedit URL permintaan dan mengklik butang **Simpan**, Open Platform akan menghantar Permintaan POST application/json kepada URL yang anda konfigurasikan untuk mengesahkan kesahihannya. Permintaan tersebut adalah seperti berikut:

   ```
   {
       "encrypt": "ajls384kdjx98XX" // String tersulit. Rujuk bahagian penyulitan dan penyahsulitan mesej di bawah untuk kaedah penyahsulitan.
   }
   ```

   Apabila anda menerima Permintaan pengesahan POST daripada Open Platform, nyahsulitkannya dan kembalikan string tersulit yang mengandungi **success** (dalam **format JSON**) dalam masa **1,500 ms**. Selepas DingTalk Open Platform menerima maklumat JSON yang dikembalikan, ia akan menyahsulitkannya. Jika string success yang betul diperoleh, push callback disahkan sebagai normal. Jika tidak, ia ditentukan sebagai callback yang gagal.
3. Selepas anda berjaya mengonfigurasikan URL permintaan, aktifkan Peristiwa yang hendak dilanggan dalam kawasan senarai **Langganan peristiwa**.

## Terima dan Balas Maklumat Peristiwa

- **Terima Maklumat Peristiwa**

  Apabila sesuatu Peristiwa berlaku, DingTalk secara aktif menghantar Permintaan POST ke URL HTTP yang dikonfigurasikan untuk menyampaikan maklumat Peristiwa berkaitan. Contohnya, selepas anda melanggan Peristiwa Kenalan, apabila Kenalan berubah, maklumat Peristiwa akan dihantar ke URL HTTP yang didaftarkan dalam format berikut.

  **Nota**

  Pelayan DingTalk menyampaikan maklumat secara masa nyata. Jika URL callback organisasi tidak mengembalikan maklumat tersulit yang betul kepada pelayan DingTalk dalam masa 1,500 milisaat, pelayan DingTalk akan menentukan push tersebut sebagai gagal.

  Format URL permintaan adalah seperti berikut:

  ```
  http://your registered HTTP URL?signature=111108bb8e6dbc2xxxx&timestamp=1783610513&nonce=380320111
  ```

  Data JSON yang disertakan adalah seperti berikut:

  ```
  {
      "encrypt":"1ojQf0NSvw2WPvW7LijxS8UvISr8pdDP+rXpPbcLGOmIBNbWetRg7IP0vdhVgkVwSoZBJeQwY2zhROsJq/HJ+q6tp1qhl9L1+ccC9ZjKs1wV5bmA9NoAWQiZ+7MpzQVq+j74rJQljdVyBdI/dGOvsnBSCxCVW0ISWX0vn9lYTuuHSoaxwCGylH9xRhYHL9bRDskBc7bO0FseHQQasdfghjkl"
  }
  ```

  Di mana:

  - signature ialah Tandatangan bagi Kandungan Mel.
  - timestamp ialah Cap masa.
  - nonce ialah string rawak.
  - encrypt ialah maklumat Peristiwa yang di-push dalam bentuk tersulit.

- **Balas Maklumat Peristiwa**

  Apabila anda menerima Permintaan pengesahan POST daripada Open Platform, nyahsulitkannya dan kembalikan string tersulit yang mengandungi **success** (dalam **format JSON**) dalam masa **1,500 ms**. Selepas DingTalk Open Platform menerima maklumat JSON yang dikembalikan, ia akan menyahsulitkannya. Jika string success yang betul diperoleh, push callback disahkan sebagai normal. Jika tidak, ia ditentukan sebagai callback yang gagal.

  Format data khusus yang dikembalikan kepada DingTalk adalah seperti berikut:

  **Nota**

  Format data yang dikembalikan mestilah JSON.

  ```
  {
    "msg_signature":"111108bb8e6dbce3c9671d6fdb69d1506xxxx",
    "timeStamp":"1783610513",
    "nonce":"123456",
    "encrypt":"1ojQf0NSvw2WPvW7LijxS8UvISr8pdDP+rXpPbcLGOmIxxxx"
   }
  ```

  Di mana:

  - msg_signature ialah Tandatangan bagi Kandungan Mel.
  - timeStamp ialah Cap masa.
  - nonce ialah string rawak.
  - encrypt ialah string success dalam bentuk tersulit.

## Penyulitan dan Penyahsulitan Mesej

Untuk memastikan keselamatan penghantaran data, DingTalk membawa token yang dikonfigurasikan untuk mengesahkan sumber Peristiwa apabila ia menyampaikan Peristiwa yang dilanggan. Ia juga menggunakan kunci ini untuk menyulitkan kandungan mesej secara simetri.

Klik [di sini](https://github.com/open-dingtalk/dingtalk-callback-Crypto) untuk mendapatkan pustaka penyulitan dan penyahsulitan callback berserta demo yang berkaitan.

Pelayan DingTalk mengekod Kandungan Mel teks biasa msg kepada `encrypt`. `encrypt = Base64_Encode(AES_Encrypt[random(16B) + msg_len(4B) + msg + $key])` ialah pengekodan Base64 bagi mesej teks biasa msg yang telah disulitkan. Di mana:

- **random** ialah string rawak 16-bait.
- **msg_len** ialah panjang msg 4-bait, dalam susunan bait rangkaian.
- **msg** ialah teks biasa bagi Kandungan Mel.
- **key** ialah App Key aplikasi tersebut.

Ekstrak medan encrypt daripada JSON yang dikembalikan:

- Nyahkod Base64 pada teks tersulit: aes_msg=Base64_Decode(encrypt);
- Gunakan AESKey untuk melakukan penyahsulitan AES: rand_msg=AES_Decrypt(aes_msg);

Contoh kod penyulitan dan penyahsulitan adalah seperti berikut:

**Nota**

- Proses penyulitan dan penyahsulitan dalam Contoh kod ini bergantung pada kelas utiliti **DingCallbackCrypto**. Rujuk [dingtalk-callback-Crypto](https://github.com/open-dingtalk/dingtalk-callback-Crypto).
- Constant.OWNER_KEY dalam Contoh ini diterangkan seperti berikut:

  - Apabila anda menggunakan kaedah dalam dokumen ini untuk menerima Peristiwa yang dilanggan yang di-push oleh DingTalk, ia di-push pada dimensi aplikasi. OWNER_KEY ialah App Key aplikasi tersebut, yang boleh diperoleh pada halaman butiran aplikasi dalam Developer Console.
  - Apabila anda menggunakan kaedah API pendaftaran callback HTTP untuk menerima Peristiwa yang dilanggan yang di-push oleh DingTalk, ia di-push pada dimensi Organisasi. OWNER_KEY ialah CorpId.

```
public Map<String, String> callBack(
                                    @RequestParam(value = "msg_signature", required = false) String msg_signature,
                                    @RequestParam(value = "timestamp", required = false) String timeStamp,
                                    @RequestParam(value = "nonce", required = false) String nonce,
                                    @RequestBody(required = false) JSONObject json) {
    try {
        // 1. Dapatkan parameter penyulitan dan penyahsulitan daripada Permintaan HTTP

        // 2. Gunakan jenis penyulitan dan penyahsulitan
        // Penerangan Constant.OWNER_KEY:
        // 1. Peristiwa langganan yang dikonfigurasikan dalam Developer Console ialah push Peristiwa peringkat aplikasi, dalam kes ini OWNER_KEY ialah APP_KEY aplikasi tersebut.
        // 2. Peristiwa yang dilanggan dengan memanggil API langganan peristiwa ialah push Peristiwa peringkat Organisasi,
        //      dalam kes ini OWNER_KEY ialah: appkey Organisasi (Aplikasi dalaman) atau SUITE_KEY (Aplikasi pihak ketiga)
        DingCallbackCrypto callbackCrypto = new DingCallbackCrypto(Constant.AES_TOKEN, Constant.AES_KEY, Constant.OWNER_KEY);
        String encryptMsg = json.getString("encrypt");
        String decryptMsg = callbackCrypto.getDecryptMsg(msg_signature, timeStamp, nonce, encryptMsg);

        // 3. Nyahjerlirkan data JSON Peristiwa callback
        JSONObject eventJson = JSON.parseObject(decryptMsg);
        String eventType = eventJson.getString("EventType");

        // 4. Kendalikan mengikut Kategori berdasarkan EventType
        if ("check_url".equals(eventType)) {
            // Uji ketepatan URL callback
            bizLogger.info("Uji ketepatan URL callback");
        } else if ("user_add_org".equals(eventType)) {
            // Kendalikan Peristiwa penambahan pengguna Kenalan
            bizLogger.info("Peristiwa berlaku: " + eventType);
        } else {
            // Tambah Peristiwa lain yang didaftarkan
            bizLogger.info("Peristiwa berlaku: " + eventType);
        }

        // 5. Kembalikan data success dalam bentuk tersulit
        Map<String, String> successMap = callbackCrypto.getEncryptedMap("success");
        return successMap;

    } catch (DingTalkEncryptException e) {
        e.printStackTrace();
    }
    return null;
}
```

Berikut ialah format data Peristiwa perubahan Kenalan selepas dinyahsulitkan:

```
{
    "EventType": "user_add_org",
    "TimeStamp": 43535463645,
    "UserId": ["user1" , "user2"],
    "CorpId": "dinge8a56572f80b02a8ffexxxx"
}
```

## Soalan Lazim

- **Penerangan Masalah**

  Apabila anda mengklik Simpan, halaman melaporkan ralat "HTTP request result verification returned field value failed", seperti ditunjukkan dalam rajah di bawah.
- **Punca**

  - Salah satu nilai medan dalam maklumat JSON yang dikembalikan kepada pelayan DingTalk adalah tidak betul.
  - Maklumat yang dikembalikan kepada pelayan DingTalk bukan dalam format JSON.
- **Penyelesaian**

  Bina satu method main, gunakan empat nilai medan yang dikembalikan oleh URL callback, panggil API penyulitan, dan sahkan sama ada nilai yang diperoleh ialah string success.

  Contohnya:

  ```
  // Bina kelas penyulitan dan penyahsulitan. Parameter yang digunakan kekal tidak berubah.
  DingTalkEncryptor dingTalkEncryptor = new DingTalkEncryptor("123456", "1234567890123456789012345678901234567890123", "dingsnotzck6pm5veliw");
  // Sampaikan empat parameter yang dikembalikan oleh URL callback anda kepada pelayan DingTalk ke dalam method penyulitan.
  String result = dingTalkEncryptor.getDecryptMsg("9a95a004dd16f5c307e849b994173f76aa26e5eb", "1614767836", "A7Co0cJLMzIDtMMI", "YvkvaGe4hQxd3VxRmEty0dVlnCOAqwf56xwTRHDHoOURqhalbmBJQk5FNcRk42Gl5T0YQXZNwpwWSm1xAFJ5ZA==");
  System.out.println(result);
  ```

  Hasil larian pada ketika ini adalah seperti berikut:

  - Jika anda memperoleh string success, nilai yang dikembalikan adalah betul, dan masalah terletak pada format parameter nilai yang tidak betul yang dikembalikan oleh API callback kepada pelayan DingTalk. Sahkan semula parameter tersebut.
  - Jika larian menghasilkan ralat, ralat larian yang biasa berlaku dan puncanya adalah seperti berikut:

    | Ralat | Punca | Kaedah Pelarasan |
    | --- | --- | --- |
    | The corpid of the decrypted text does not match | Parameter `OWNER_KEY` dalam DingTalkEncryptor tidak betul. | Bagi Langganan peristiwa aplikasi semasa dalam Developer Console, `owner_key` mesti menghantar nilai appkey aplikasi semasa. |
    | Invalid aes key | Parameter `ENCODING_AES_KEY` dalam DingTalkEncryptor tidak betul. | `ENCODING_AES_KEY` ialah string tetap tersuai sepanjang 43 aksara yang hanya menyokong huruf besar, huruf kecil dan digit. |
    | Signature calculation failed | Parameter yang digunakan dalam method penyahsulitan tidak betul. | Empat parameter dalam method penyahsulitan getEncryptedMap semuanya berasal daripada nilai yang dibawa oleh permintaan pelayan DingTalk. |
