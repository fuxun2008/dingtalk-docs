# Integrasi kelulusan pantas untuk sistem pihak ketiga: Kelulusan satu klik di Pusat Tugasan dan kad mesej

## Gambaran keseluruhan

Penyelesaian ini sesuai untuk organisasi yang tugasan kelulusannya tersebar di beberapa sistem perniagaan. Ia juga sesuai untuk pengurus yang ingin mengendalikan kelulusan pihak ketiga tanpa meninggalkan DingTalk. Pusat Proses Kelulusan OA menyediakan API kelulusan pantas tersuai dan mekanisme callback. Sistem perniagaan pihak ketiga menggunakannya untuk menyegerakkan tugasan kelulusan ke Pusat Kelulusan DingTalk. Butang kelulusan pantas tersuai kemudian dipaparkan dalam senarai Pusat Tugasan dan pada kad mesej Kelulusan OA. Apabila penyokong mengklik butang, DingTalk membuat callback kepada sistem pihak ketiga. Sistem tersebut mengemas kini status tugasan dan menyegerakkannya semula ke Pusat Kelulusan DingTalk. Penyokong menikmati pengalaman kelulusan yang lancar dan menyeluruh di satu tempat.

### Latar belakang

Organisasi menjana sejumlah besar tugasan kelulusan dalam sistem perniagaan pihak ketiga, seperti sistem kawalan perbelanjaan, perolehan dan HR. Pekerja perlu log masuk ke setiap sistem dan mengendalikan tugasan satu demi satu. Prosesnya panjang dan tidak cekap. Penyelesaian ini menyambungkan kelulusan pihak ketiga ke Pusat Tugasan DingTalk dan menyokong kelulusan satu klik dalam kad mesej. Pekerja mengendalikan semua kelulusan di satu tempat dalam DingTalk tanpa bertukar ke sistem asal.

Organisasi lazimnya berdepan masalah berikut:

- **Log masuk berulang merentas sistem:** Pekerja log masuk ke lebih daripada 5 sistem perniagaan setiap hari untuk mengendalikan kelulusan. Setiap kelulusan mengambil masa purata 3 minit, membazirkan lebih daripada 40 minit sehari.
- **Kemajuan kelulusan tidak telus:** Selepas menghantar kelulusan, pekerja tidak dapat menjejak statusnya dalam DingTalk secara masa nyata. Mereka perlu log masuk ke sistem asal berulang kali untuk menyemak, dan susulan bergantung pada komunikasi manual.
- **Pengalaman kelulusan mudah alih yang lemah:** Kebanyakan sistem pihak ketiga tidak dioptimumkan untuk mudah alih. Pekerja yang berada dalam perjalanan perniagaan atau bekerja dari rumah tidak dapat mengendalikan kelulusan segera tepat pada masanya, lalu melambatkan urusan perniagaan.
- **Data kelulusan sukar dihimpunkan:** Metrik seperti jumlah kelulusan dan purata masa pemprosesan bagi setiap jabatan tersebar di pelbagai sistem. Pengurus tidak dapat memperoleh gambaran menyeluruh dalam DingTalk.

### Nilai teras

Penyelesaian ini memberikan nilai dalam tiga aspek:

- **Kelulusan satu klik:** Butang kelulusan pantas daripada sistem pihak ketiga dipaparkan terus dalam senarai Pusat Tugasan DingTalk dan pada kad mesej Kelulusan OA. Penyokong menyelesaikan kelulusan ringkas tanpa bertukar ke sistem perniagaan.
- **Penyegerakan gelung tertutup:** Apabila penyokong mengklik butang pantas, DingTalk membuat callback kepada sistem pihak ketiga untuk mengemas kini status tugasan. Sistem pihak ketiga kemudian menyegerakkan status terkini semula ke Pusat Kelulusan DingTalk, sekali gus melengkapkan gelung data.
- **Penyesuaian fleksibel:** Sistem pihak ketiga boleh menyesuaikan label, ikon dan syarat keterlihatan butang pantas. Konfigurasikan tindakan pantas yang berbeza untuk jenis kelulusan yang berbeza mengikut keperluan perniagaan.

### Kes penggunaan

Penyelesaian ini sesuai untuk organisasi yang mempunyai sumber kelulusan pelbagai dan bahagian kelulusan ringkas yang tinggi. Kes penggunaan biasa termasuk:

- **Kelulusan sehenti untuk eksekutif:** Eksekutif seperti CEO dan CFO mengendalikan kelulusan daripada beberapa sistem pihak ketiga setiap hari. Kebanyakannya ialah pengesahan ringkas yang ingin mereka selesaikan dengan satu klik dalam DingTalk tanpa bertukar sistem.
- **Kelulusan ringan berfrekuensi tinggi:** Kelulusan seperti pengesahan tuntutan perbelanjaan, lanjutan cuti dan permohonan daftar masuk susulan kerap berlaku dan ringkas. Penyokong boleh mengendalikannya terus dalam senarai Tugasan.
- **Kelulusan segera daripada kad mesej:** Selepas menerima pemberitahuan kad mesej Kelulusan OA, penyokong menyelesaikan kelulusan terus pada kad tanpa membuka halaman perincian.

## Senario perniagaan biasa

### Senario 1: Kelulusan operasi pantas untuk rangkaian hotel (hospitaliti dan pelancongan)

#### Masalah

Sebuah rangkaian hotel nasional mengendalikan lebih daripada 80 hartanah. Ia menggunakan PMS dalaman untuk kelulusan tempahan bilik, sistem perolehan untuk kelulusan permohonan bekalan, dan sistem HR untuk penjadualan syif kakitangan dan cuti ganti. Tugasan kelulusan berjalan secara berasingan dalam ketiga-tiga sistem. Pengarah operasi kumpulan dan pengurus cawangan mengendalikan jumlah kelulusan yang besar setiap hari. Proses sedia ada mempunyai isu berikut:

- **Kelulusan ringkas memakan masa:** Jumlah kelulusan harian melebihi 60, dan 40% daripadanya ialah tindakan ringkas seperti pengesahan tempahan berlebihan dan pengesahan penambahan stok. Setiap satu memerlukan log masuk ke PMS atau sistem perolehan, mencari tugasan dan mengklik Terima, dengan purata 2 minit.
- **Pengalaman mudah alih yang lemah:** Pengurus cawangan mengendalikan kelulusan pada telefon semasa pemeriksaan hartanah. Mereka mengklik pautan dalam mesej DingTalk untuk membuka halaman mudah alih PMS, yang lambat dimuatkan dan sukar digunakan. Respons yang lewat terhadap pengesahan tempahan berlebihan yang mendesak menjejaskan pengalaman tetamu.
- **Tiada tindakan dalam kad mesej:** Apabila kad mesej "Tempahan bilik berlebihan memerlukan pengesahan" diterima, pengurus hanya boleh mengklik untuk melihat perincian. Mereka tidak dapat mengesahkan terus pada kad dan terlepas tempoh terbaik untuk menyelaraskan pertukaran bilik.

#### Pengesahan nilai

- **Aliran kerja automatik**

  Integrasi ini mengikut aliran lima langkah:

  1. **Integrasi pelbagai sistem** – sambungkan Kelulusan OA rasmi, PMS, HR dan sistem perolehan.
  2. **Paparan Tugasan terhimpun** – senarai Tugasan bersepadu dengan penapisan mengikut sistem sumber.
  3. **Pendaftaran butang pantas** – konfigurasikan tindakan Sahkan/Tolak dan callback masing-masing.
  4. **Kelulusan dalam kad** – bertindak terus pada kad tanpa membuka halaman perincian.
  5. **Penyegerakan status gelung tertutup** – peristiwa callback memastikan data konsisten merentas sistem.

  Kad Kelulusan OA memaparkan medan **Pemohon**, **Masa Permohonan**, **Amaun** dan **Sebab**, serta butang **Luluskan**, **Tolak** dan **Lagi** yang terbenam.
- **Kelebihan utama**

  - **Kecekapan satu klik:** Kelulusan pengesahan ringkas berkurang daripada 2 minit kepada 5 saat, menjimatkan 40 minit sehari. Masa respons pengesahan tempahan berlebihan berkurang daripada 15 minit kepada 30 saat.
  - **Mesra mudah alih:** Pengurus cawangan meluluskan terus daripada senarai Tugasan DingTalk pada telefon tanpa membuka halaman mudah alih PMS. Mereka mengendalikan tempahan berlebihan yang mendesak secara masa nyata semasa pemeriksaan.
  - **Tindakan terus pada kad:** Butang pantas dibenamkan dalam kad mesej Kelulusan OA. Pengurus mengesahkan terus pada kad sebaik sahaja pemberitahuan tempahan berlebihan diterima dan tidak terlepas tempoh untuk menyelaraskan pertukaran bilik.

### Senario 2: Integrasi kelulusan pelbagai pihak untuk projek pembinaan besar (pembinaan dan kejuruteraan)

#### Masalah

Sebuah syarikat pembinaan besar menjalankan 15 projek serentak. Ia menggunakan sistem pengurusan projek dalaman untuk kelulusan kemajuan pembinaan, sistem bahan untuk kelulusan pemeriksaan penghantaran bahan, dan sistem keselamatan untuk kelulusan pemeriksaan dan pemulihan bahaya. Ketiga-tiga proses kelulusan berjalan secara bebas. Pengurus projek dan pengarah keselamatan mengendalikan jumlah kelulusan yang besar setiap hari. Proses sedia ada mempunyai isu berikut:

- **Kelulusan di tapak yang menyusahkan:** Pengurus projek bekerja di tapak. Apabila isyarat mudah alih tidak stabil, halaman mudah alih sistem pengurusan projek lambat dimuatkan. Pengesahan penghantaran bahan yang lewat melambatkan kerja pembinaan.
- **Respons lambat terhadap bahaya keselamatan:** Apabila pegawai keselamatan menemui bahaya, mereka menghantar kelulusan pemulihan. Pengarah keselamatan perlu membuka halaman perincian daripada kad mesej untuk melihat foto dan lokasi bahaya sebelum membuat keputusan. Proses tradisional mengambil masa terlalu lama, dan terlepas tempoh pemulihan terbaik boleh mengakibatkan kemalangan.
- **Kerjasama pelbagai pihak yang tidak cekap:** Satu kelulusan pemeriksaan bahan memerlukan pengesahan daripada jabatan projek, jabatan bahan dan pihak penyelia, masing-masing dalam sistem berasingan. Penyelarasan boleh mengambil masa sehingga 2 hari.

#### Pengesahan nilai

- **Aliran kerja automatik**

  Aliran integrasi mempunyai lima peringkat:

  1. **Akses pelbagai sistem** — sambungkan sistem projek, bahan dan keselamatan ke DingTalk.
  2. **Paparan Tugasan terhimpun** — item belum selesai daripada semua sumber dipaparkan dalam satu **Pusat Tugasan** bersepadu, boleh ditapis mengikut **Semua**, **Projek**, **Bahan** dan **Keselamatan**.
  3. **Pendaftaran butang tindakan pantas** — konfigurasikan butang untuk tindakan penerimaan, semakan semula dan pemulihan.
  4. **Luluskan terus daripada kad** — bertindak pada kad Kelulusan OA tanpa membuka halaman perincian, menggunakan butang **Luluskan**, **Tolak** dan **Lagi**.
  5. **Penyegerakan status masa nyata** — peristiwa callback memastikan data sistem sumber kekal konsisten.

  Kad kelulusan memaparkan tajuk permohonan, **Sumber**, pemohon, masa penghantaran dan kandungan.
- **Kelebihan utama**

  - **Kecekapan di tapak:** Pengesahan pemeriksaan bahan berkurang daripada 3 minit kepada 5 saat. Walaupun isyarat lemah di tapak, pengurus dapat menyelesaikannya dengan pantas dalam DingTalk dan mengelakkan kelewatan pembinaan.
  - **Respons keselamatan lebih pantas:** Kelulusan pemulihan bahaya dikendalikan terus daripada kad mesej. Masa respons berkurang daripada 1 jam kepada 5 minit, mengurangkan risiko insiden keselamatan.
  - **Kerjasama gelung tertutup:** Kelulusan pengesahan pelbagai pihak menggunakan butang pantas dan callback untuk menyegerakkan status secara masa nyata. Masa penyelarasan berkurang daripada 2 hari kepada 4 jam.

## Panduan pelaksanaan

### Seni bina teknikal

Seni bina teknikal merangkumi komponen teras berikut:

- **Lapisan pengesahan:** Mengurus kelayakan aplikasi dan mendapatkan access token untuk mengesahkan identiti setiap panggilan API.
- **Lapisan penyegerakan templat:** Memanggil API yang menyimpan templat kelulusan bersepadu luaran dalam Pusat Proses. Ia menyegerakkan templat kelulusan daripada sistem perniagaan pihak ketiga ke Pusat Kelulusan DingTalk dan mendapatkan kod unik templat `processCode`.
- **Lapisan penciptaan tugasan:** Memanggil API yang mencipta atau mengemas kini tugasan kelulusan. Ia menyegerakkan tugasan kelulusan daripada sistem pihak ketiga ke Pusat Kelulusan DingTalk serta mendaftarkan butang kelulusan pantas tersuai dan URL callback.
- **Lapisan pengendalian callback:** Sistem pihak ketiga menyediakan API callback HTTPS. Ia menerima callback kelulusan pantas daripada DingTalk, mengemas kini status tugasan setempat dan menyegerakkan status terkini semula ke Pusat Kelulusan DingTalk untuk menutup gelung data.
- **Lapisan panggilan balik peristiwa:** Mendengar peristiwa perubahan status tugasan kelulusan untuk memastikan sistem pihak ketiga dan Pusat Kelulusan DingTalk kekal konsisten.

### Prasyarat

- **Penyediaan aplikasi:** Lengkapkan proses [penciptaan dan konfigurasi aplikasi](/ms/open/dingstart/create-application).
- **Keperluan kebenaran:** Miliki kebenaran Admin Organisasi atau Sub Admin DingTalk, dan mohon kebenaran API berikut:

  - `qyapi_aflow` (kebenaran pengurusan data aliran kelulusan)
  - `Workflow.Form.Write` (kebenaran tulis templat aliran kerja)
  - `Workflow.Form.Read` (kebenaran baca templat aliran kerja)
  - `Workflow.Instance.Write` (kebenaran tulis instans aliran kerja)
  - `Premium.Workflow.ReadWrite.All` (kebenaran baca/tulis aliran kerja Kelulusan OA, eksklusif untuk OA Edisi Premium)
- **Persekitaran pembangunan:** Pasang persekitaran pembangunan Java (JDK 1.6 atau lebih baharu) dan alat binaan Maven.
- **Penyediaan SDK:** Muat turun SDK Bahagian pelayan DingTalk, tersedia untuk Java, Python, Go dan bahasa lain.
- **Penyediaan gateway:** Daftarkan API callback sistem pihak ketiga sebagai gateway dalam "Pengurusan Sumber Data" DingTalk. Untuk perincian, lihat Sumber data.

### Pelaksanaan kod

Langkah 1: Pergi ke halaman perincian aplikasi dan dapatkan Client ID serta Client Secret aplikasi.

Langkah 2: Mohon kebenaran API. Mohon kebenaran "Kelulusan OA" yang berkaitan.

Langkah 3: Dapatkan kredensial akses aplikasi. Lihat [Dapatkan access token aplikasi dalaman](/ms/open/development/obtain-the-access-token-of-an-internal-app). Semasa memanggil API, gunakan access token untuk mengesahkan pemanggil.

Langkah 4: Panggil API teras:

1. Daftarkan API callback untuk butang kelulusan pantas tersuai. Semua callback gateway ke API data di luar DingTalk mesti didaftarkan sebagai gateway dalam "Pengurusan Sumber Data". Untuk perincian, lihat Sumber data.
2. Panggil Server API baharu yang menyimpan templat kelulusan bersepadu luaran dalam Pusat Proses untuk mendapatkan kod unik templat `processCode`.
3. Jika anda tidak menyimpan `processCode`, panggil API [Dapatkan kod templat](/ms/open/development/obtain-the-template-code) untuk mendapatkannya.
4. Selepas templat kelulusan dicipta, pergi ke Admin Console Kelulusan OA DingTalk. Lihat templat borang kelulusan pihak ketiga anda, lihat atau cari data templat, dan eksport atau padam data templat.
5. Gunakan kod templat `processCode` untuk memanggil API yang menyimpan instans kelulusan bersepadu luaran dalam Pusat Proses. Ini memulakan instans kelulusan dan mengembalikan ID instans kelulusan `processInstanceId`.
6. Selepas instans kelulusan dicipta, pergi ke Pusat Kelulusan OA DingTalk. Lihat senarai kelulusan (Belum Selesai, Telah Diproses, Dimulakan dan Diterima), cari data instans kelulusan dan laksanakan kelulusan.
7. Gunakan instans kelulusan `processInstanceId` dan tugasan senarai Tugasan untuk memanggil API yang menyimpan tugasan kelulusan bersepadu luaran dalam Pusat Proses. Ini menyegerakkan maklumat nod kelulusan daripada sistem pihak ketiga ke Kelulusan OA DingTalk, mengembalikan taskId setiap item tugasan dan menjana tugasan DingTalk yang sepadan.
8. Panggil API [Tanya tugasan kelulusan OA yang diintegrasikan melalui Pusat Proses](/ms/open/development/query-oa-approval-tasks-integrated-through-process-center) untuk menanya tugasan kelulusan pengguna yang sedang berjalan.
9. Gunakan instans kelulusan `processInstanceId` dan taskId tugasan kelulusan untuk memanggil API [Kemas kini status tugasan Pusat Proses](/ms/open/development/update-process-center-task-status) dan menyegerakkan status item tugasan kelulusan anda sendiri.

### Nota

   Dalam senario seperti kelulusan tandatangan-ATAU (OR-sign), panggil API [Batalkan berbilang tugasan belum selesai dalam Pusat Proses](/ms/open/development/cancel-multiple-oa-approval-tasks) untuk menetapkan semua item tugasan yang sedang berjalan di bawah sesuatu instans kelulusan kepada CANCELED secara pukal.
10. Gunakan instans kelulusan `processInstanceId`, status instans, keputusan instans dan data lain untuk mencetuskan peristiwa seperti permulaan, penamatan dan penyerahan tugasan kelulusan, atau permulaan, penamatan, penghentian dan pemadaman instans kelulusan. Peristiwa ini mengemas kini status instans.
11. Untuk membersihkan data templat kelulusan, panggil API [Padam templat](/ms/open/development/self-owned-approval-deletion-template). Ini memadam templat kelulusan yang dicipta untuk organisasi anda, bersama semua instans dan tugasan yang dicipta daripadanya.

## Langkah pelaksanaan

### **Langkah 1: Dapatkan kelayakan aplikasi**

1. Log masuk ke [DingTalk Developer Console](https://open-dev.dingtalk.io/).
2. Pilih aplikasi sasaran untuk membuka halaman perinciannya.
3. Klik **Maklumat Asas** > **Kelayakan dan Maklumat Asas**.
4. Rekodkan `Client ID` dan `Client Secret` aplikasi.

### Nota

   Simpan `Client Secret` dengan selamat dan jangan sekali-kali kongsikannya dengan pihak ketiga. Simpan dalam pemboleh ubah persekitaran atau sistem pengurusan kunci, bukan secara hardcode.

### Langkah 2: Tambah kebenaran API

1. Pada halaman perincian aplikasi, klik **Urus kebenaran**.
2. Masukkan pengecam kebenaran berikut dalam kotak carian kebenaran dan mohon kebenaran tersebut:

   - `qyapi_aflow` (kebenaran pengurusan data aliran kelulusan): Mengemas kini status tugasan Pusat Proses.
   - `Workflow.Form.Write` (kebenaran tulis templat aliran kerja): Mendapatkan kod templat.
   - `Workflow.Form.Read` (kebenaran baca templat aliran kerja): Mencipta atau mengemas kini instans kelulusan.
   - `Workflow.Instance.Write` (kebenaran tulis instans aliran kerja): Membatalkan tugasan belum selesai dalam Pusat Proses secara pukal.
   - `Premium.Workflow.ReadWrite.All` (kebenaran baca/tulis aliran kerja Kelulusan OA, eksklusif untuk OA Edisi Premium): Mendapatkan data senarai Belum Selesai, Telah Diproses, Dimulakan dan Diterima pengguna dalam Pusat Kelulusan DingTalk.

<Note>
Senario perniagaan yang berbeza mungkin memerlukan gabungan kebenaran yang berbeza. Mohon mengikut keperluan sebenar anda.
</Note>

### Langkah 3: Dapatkan kredensial akses (Access Token)

Gunakan Client ID dan Client Secret daripada Langkah 1 untuk mendapatkan kredensial akses aplikasi. Lihat [Dapatkan access token aplikasi dalaman](/ms/open/development/obtain-the-access-token-of-an-internal-app).

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**Amalan terbaik**:

- **Strategi cache**: `accessToken` sah selama 2 jam. Simpan dalam cache memori atau Redis, dan muat semula 5 minit sebelumnya ia tamat tempoh.
- **Kawalan keserentakan**: Elakkan berbilang thread memuat semula token pada masa yang sama sehingga menyebabkan konflik. Gunakan kunci teragih (distributed lock).
- **Cuba semula ralat**: Cuba semula secara automatik apabila berlaku gangguan rangkaian, sehingga 3 kali, dengan selang yang semakin meningkat (1s → 2s → 4s).

### Langkah 4: Panggil API teras

1. **Daftarkan API callback untuk butang kelulusan pantas tersuai:** Apabila penyokong bertindak terus dalam Pusat Tugasan DingTalk atau pada kad mesej Kelulusan OA, DingTalk membuat callback kepada sistem pihak ketiga. Sistem pihak ketiga mengemas kini tugasan dan menyegerakkan maklumat tugasan baharu semula ke Pusat Kelulusan DingTalk, sekali gus menutup gelung.

### Nota

   Semua callback gateway ke API data di luar DingTalk mesti didaftarkan sebagai gateway dalam "Pengurusan Sumber Data". Untuk perincian, lihat Sumber data.
2. **Segerakkan data templat kelulusan ke DingTalk:** Panggil Server API baharu yang menyimpan templat kelulusan bersepadu luaran dalam Pusat Proses untuk mendapatkan kod unik templat `processCode`. **Dalam senario ini, anda tidak perlu mengkonfigurasikan processFeatureConfig untuk integrasi Pusat Proses.**

   ```json
   {
     "name": "Kelulusan Pantas",
     "description": "Simpan templat kelulusan bersepadu luaran dalam Pusat Proses (API Edisi Premium)",
     "formComponents": [
       {
         "componentType": "TextField",
         "props": {
           "componentId": "TextField-1",
           "label": "Medan teks satu baris",
           "required": true,
           "bizAlias": "TextField-bizAlias",
           "disabled": false
         }
       }
     ],
     "templateConfig": {
       "disableSendCard": false
     }
   }
   ```

### Parameter permintaan

   - `name`: Nama templat kelulusan.
   - `description`: Penerangan templat.
   - `formComponents`: Tatasusunan konfigurasi komponen borang.
   - `templateConfig`: Konfigurasi templat. `disableSendCard` menentukan sama ada penghantaran kad mesej dinyahaktifkan.

### Medan respons

   - `processCode`: Kod unik templat borang kelulusan.
3. Jika anda tidak menyimpan `processCode`, panggil API [Dapatkan kod templat](/ms/open/development/obtain-the-template-code) untuk mendapatkannya.

   ```java
   public void getProcessCodeByName() throws Exception {
       Config config = new Config();
       config.protocol = "https";
       config.regionId = "central";

       com.aliyun.dingtalkworkflow_1_0.Client client = new com.aliyun.dingtalkworkflow_1_0.Client(config);

       GetProcessCodeByNameHeaders getProcessCodeByNameHeaders = new GetProcessCodeByNameHeaders();
       getProcessCodeByNameHeaders.xAcsDingtalkAccessToken = "accessToken";

       GetProcessCodeByNameRequest request = new GetProcessCodeByNameRequest()
               .setName("Nama");

       try {
           GetProcessCodeByNameResponse getProcessCodeByNameResponse = client.getProcessCodeByNameWithOptions(
                   getProcessCodeByNameRequest,
                   getProcessCodeByNameHeaders,
                   new com.aliyun.teautil.models.RuntimeOptions()
           );
       } catch (TeaException err) {
           if (!com.aliyun.teautil.Common.empty(err.code) && !com.aliyun.teautil.Common.empty(err.message)) {
               // err mengandungi atribut code dan message untuk membantu mengenal pasti isu
               System.out.println(err.code);
               System.out.println(err.message);
           }
       } catch (Exception _err) {
           TeaException err = new TeaException(_err.getMessage(), _err);
           if (!com.aliyun.teautil.Common.empty(err.code) && !com.aliyun.teautil.Common.empty(err.message)) {
   ```

## Soalan lazim

- **S: Bagaimanakah cara mengendalikan tamat masa API callback?**

  Callback DingTalk ke API sistem pihak ketiga tamat masa selepas 5 saat. Jika sistem pihak ketiga tidak mengembalikan HTTP 200 dalam masa 5 saat, DingTalk akan mencuba semula sehingga 3 kali, pada selang 1s, 2s dan 4s. Pastikan API callback ringan dan proses logik yang kompleks secara tak segerak.
- **S: Adakah penyokong perlu mengesahkan sekali lagi selepas mengklik butang pantas?**

  Secara lalai, pengesahan kedua tidak diperlukan. Tindakan dilaksanakan serta-merta apabila diklik. Jika senario perniagaan anda memerlukan pengesahan kedua, kembalikan kod status tertentu daripada API callback pihak ketiga. DingTalk kemudian akan memaparkan dialog pengesahan sebelum melaksanakan tindakan.
