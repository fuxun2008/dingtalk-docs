Sebelum memanggil DingTalk OpenAPI, sesuatu aplikasi perlu mendapatkan access token daripada DingTalk Open Platform. Token ini mengandungi maklumat identiti aplikasi serta kebenaran aksesnya terhadap sumber DingTalk, dan berfungsi sebagai kelayakan pengesahan yang wajib untuk panggilan API.

## Latar belakang

Bagi membantu pembangun memahami mekanisme pengesahan identiti dengan jelas dalam pelbagai senario, dokumen ini memberikan pengenalan sistematik tentang empat jenis access token yang disokong oleh DingTalk Open Platform, subjek yang berkenaan, skop kebenaran, dan cara penggunaannya. Dokumen ini juga menyediakan garis panduan operasi yang lengkap serta perkara penting untuk memastikan pembangun dapat menyelesaikan persiapan panggilan API dengan betul dan cekap.

## Gambaran keseluruhan kebenaran

DingTalk Open Platform menggunakan dua model kebenaran untuk menguruskan akses aplikasi kepada sumber, bagi mengimbangi keselamatan dan fleksibiliti:

<Note>
Tidak kira jenis kebenaran yang digunakan untuk memanggil DingTalk OpenAPI, anda perlu mendapatkan access token bagi jenis kebenaran yang berkaitan terlebih dahulu.
</Note>

### **Jenis 1**: Kredensial akses identiti **Pengguna**

- **Definisi**: Kredensial akses identiti pengguna (kebenaran delegasi). Aplikasi memerlukan kebenaran pengguna untuk memanggil DingTalk OpenAPI bagi pihak pengguna yang log masuk untuk mengendalikan sumber.
- **Ciri-ciri**:

  - Pengguna mesti secara aktif memberikan kebenaran supaya aplikasi dapat mengakses data peribadi mereka atau melakukan tindakan bagi pihak mereka.
  - Semasa memanggil API, `access token` pengguna digunakan, dan hasil operasi dihadkan oleh kebenaran pengguna tersebut.
  - Sesuai untuk senario yang melibatkan data peribadi pengguna, seperti membaca acara peribadi atau nombor telefon bimbit peribadi.

### **Jenis 2**: Kredensial akses identiti Aplikasi

- **Definisi**: Kredensial akses identiti aplikasi (kebenaran aplikasi). Sesuai untuk aplikasi yang tidak memerlukan log masuk pengguna. Apabila aplikasi dipasang, admin boleh memberikan kebenaran terlebih dahulu.
- **Ciri-ciri**:

  - Aplikasi boleh memanggil API tanpa bergantung pada identiti pengguna dan mengakses sumber peringkat organisasi secara terus.
  - Menggunakan `access token` bagi aplikasi dalaman atau aplikasi pihak ketiga.
  - Sesuai untuk tugas backend, pemprosesan pukal, operasi automatik, dan senario yang seumpamanya.

## Access token

Access token dikeluarkan oleh DingTalk Open Platform untuk mengesahkan identiti pemanggil dan memastikan pemanggil mempunyai kebenaran yang diperlukan untuk melaksanakan tindakan yang dimaksudkan.

DingTalk Open Platform kini menyediakan empat jenis access token berikut, yang masing-masing sepadan dengan senario aplikasi dan tahap kebenaran yang berbeza:

<Warning>
Memanggil API yang sama dengan access token yang berbeza mungkin mengembalikan data yang berbeza. Untuk butiran lanjut, rujuk dokumentasi API yang berkenaan.
</Warning>

| Kredensial kebenaran | Senario | Cara mendapatkan |
| --- | --- | --- |
| User access token | Aplikasi yang memerlukan kebenaran pengguna yang log masuk. | [Dapatkan user token](/open/development/obtain-user-token) |
| Internal app access token | Aplikasi dalaman yang memanggil Server API untuk mengakses sumber aplikasi. | [Dapatkan access token aplikasi dalaman](/open/development/obtain-the-access-token-of-an-internal-app) |
| Third-party enterprise app access token | Aplikasi perusahaan pihak ketiga atau aplikasi tersuai yang memanggil Server API untuk mengakses sumber aplikasi. | Dapatkan access token bagi organisasi yang telah memberikan kebenaran kepada aplikasi pihak ketiga |
| Third-party enterprise app suiteAccessToken | Dapatkan maklumat tentang aplikasi perusahaan pihak ketiga. | Dapatkan suiteAccessToken bagi aplikasi perusahaan pihak ketiga |

## Cara menggunakan access token

Untuk memanggil DingTalk OpenAPI, sertakan access token sebagai Bearer token dalam header Authorization permintaan HTTP. Contohnya:

```http
GET https://api.dingtalk.io/v1.0/me/ HTTP/1.1
Host: api.dingtalk.io
Authorization: Bearer EwAoA8lxxxx=
```

Untuk operasi lengkap, rujuk:

- Dapatkan kredensial akses pengguna yang log masuk: rujuk tutorial dokumentasi [Dapatkan kelayakan identiti](/open/development/obtain-identity-credentials).
- Dapatkan kredensial akses apabila tiada pengguna yang log masuk: rujuk tutorial dokumentasi [Dapatkan kelayakan akses API aplikasi](/open/development/used-application-authorization).

## Perkara penting

| Perkara penting | Penerangan |
| --- | --- |
| 🔐 Risiko kebocoran Client Secret | Jangan sekali-kali paparkan Secret dalam kod frontend, pada bahagian klien, atau dalam log. |
| 🕒 Tempoh sah access token | Sah selama 7,200 saat secara lalai. Laksanakan mekanisme muat semula automatik. |
| 🧩 Jenis access token yang disokong oleh sesuatu API | Sentiasa semak dokumentasi API yang berkenaan untuk mengesahkan. Jangan campurkan jenis token. |
