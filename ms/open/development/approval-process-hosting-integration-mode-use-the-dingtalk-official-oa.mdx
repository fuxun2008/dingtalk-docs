# Pengehosan proses kelulusan: Integrasikan proses DingTalk dengan halaman pihak ketiga

## Gambaran keseluruhan

Penyelesaian ini menggunakan mod integrasi pengehosan proses kelulusan. Mod ini menghubungkan enjin aliran kerja Kelulusan OA rasmi DingTalk dengan halaman perniagaan tersuai yang dibina oleh pihak ketiga. Sistem perniagaan memanggil API Kelulusan OA DingTalk untuk mencipta instans aliran kerja kelulusan. Sistem itu menetapkan URL halaman butiran sistem kelulusan pihak ketiga semasa penciptaan. Apabila penyokong membuka butiran kelulusan dalam DingTalk, DingTalk mengalihkan penyokong secara automatik ke halaman tersuai dalam sistem perniagaan untuk melengkapkan kelulusan. Pendekatan ini menggunakan semula enjin aliran kerja rasmi DingTalk dan mengekalkan paparan tersuai borang perniagaan yang kompleks. Hasilnya, integrasi dapat disiapkan dengan cepat pada kos rendah.

### Latar belakang

Organisasi sering membina atau membeli sistem OA pihak ketiga yang mempunyai proses dan halaman kelulusan sendiri. Pekerja perlu bertukar antara beberapa sistem untuk mengendalikan kelulusan. Keadaan ini memecahkan aliran kerja mereka dan mengurangkan kecekapan. Apabila proses kelulusan sendiri disambungkan ke Pusat Kelulusan OA DingTalk, pengguna boleh membuka halaman sistem perniagaan dan meluluskan permohonan terus dalam DingTalk melalui pengalaman sehenti.

Organisasi biasanya berdepan dengan cabaran berikut:

- **Titik masuk kelulusan berselerak:** Pekerja mengendalikan kelulusan secara berasingan dalam beberapa sistem. Peringatan DingTalk To-Do tidak meliputi tugasan kelulusan dalam sistem dalaman, jadi tugasan mudah terlepas.
- **Pengalaman kelulusan tidak konsisten:** Halaman kelulusan dalam sistem dalaman tidak sepadan dengan gaya DingTalk. Pengguna perlu menyesuaikan diri dengan corak interaksi yang berbeza, jadi lengkung pembelajaran meningkat.
- **Capaian notifikasi tugasan yang rendah:** Sistem dalaman bergantung pada e-mel atau SMS untuk notifikasi kelulusan. Saluran ini perlahan dan tidak dapat memanfaatkan tolak mesej DingTalk serta pusat To-Do.
- **Data kelulusan terasing:** Status kelulusan, rekod pemprosesan dan data lain berselerak merentas sistem. Pengurus tidak dapat melihat kemajuan kelulusan di satu tempat dalam DingTalk.

### Nilai teras

Penyelesaian ini memberikan nilai dalam tiga aspek:

- **Integrasi fleksibel:** Gabungkan aliran kerja Kelulusan OA rasmi DingTalk dengan halaman perniagaan tersuai pihak ketiga. Guna semula keupayaan aliran kerja enjin Kelulusan OA rasmi. Sambungkan dengan lancar ke Sembang, To-Do dan Notifikasi DingTalk untuk kelulusan yang cekap.
- **Kos lebih rendah:** Gunakan halaman perniagaan tersuai pihak ketiga sebagai halaman butiran kelulusan. Medan setiap komponen borang tidak perlu diselaraskan ke DingTalk. Usaha integrasi berkurang, manakala proses dan susun atur halaman yang sudah biasa kepada pengguna dikekalkan.
- **Pengalaman konsisten:** Mulakan proses daripada sistem perniagaan. Panggil API Kelulusan OA rasmi DingTalk untuk mencipta proses Kelulusan OA. Penyokong membuka halaman tersuai sistem perniagaan terus daripada Kelulusan OA, To-Do atau kad mesej DingTalk dengan pengalaman yang konsisten.

### Kes penggunaan

Penyelesaian ini sesuai untuk sistem perniagaan yang memerlukan enjin aliran kerja rasmi DingTalk tetapi mempunyai halaman borang yang kompleks. Kes biasa termasuk:

- **Kelulusan borang kompleks:** Sistem perniagaan mempunyai borang kelulusan dengan banyak medan komponen tersuai. Konfigurasi satu per satu dalam DingTalk Admin Console tidak praktikal. Oleh itu, borang perlu dipaparkan sepenuhnya pada halaman tersuai.
- **Integrasi sistem sedia ada:** Sistem sudah mempunyai halaman kelulusan dan logik interaksi yang matang. Anda mahu menggunakan aliran kerja DingTalk dengan perubahan minimum dan mengekalkan pengalaman pengguna sedia ada.
- **Kelulusan kolaboratif merentas sistem:** Proses kelulusan memerlukan keterkaitan data merentas beberapa sistem perniagaan. Halaman tersuai perlu membuat pertanyaan dan memaparkan maklumat merentas sistem secara masa nyata.

## Senario perniagaan biasa

### Senario 1: Kelulusan perintah kerja pengeluaran untuk pengeluar besar (Pembuatan)

#### Cabaran

Sebuah syarikat pembuatan besar menggunakan sistem MES dalaman untuk mengurus perintah kerja pengeluaran. Kelulusan perintah kerja melibatkan berpuluh-puluh medan, seperti nombor peralatan, laluan proses, senarai bahan dan piawaian pemeriksaan kualiti. Kelulusan ini juga memerlukan pautan masa nyata ke data inventori ERP dan lukisan PLM. Proses sedia ada mempunyai isu berikut:

- **Konfigurasi borang yang berat:** Menyelaraskan semua medan perintah kerja ke Admin Console Kelulusan OA DingTalk memerlukan penyelenggaraan ratusan pemetaan komponen. Setiap medan baharu memerlukan perubahan pada konfigurasi DingTalk dan juga sistem perniagaan, jadi kos penyelenggaraan meningkat.
- **Tiada keterkaitan data:** Borang kelulusan asli DingTalk tidak dapat membuat pertanyaan inventori ERP atau lukisan PLM secara masa nyata. Penyokong perlu bertukar antara sistem, jadi kerja mereka menjadi perlahan.
- **Tabiat pengguna terganggu:** Ketua pasukan bengkel telah lama menggunakan halaman kelulusan perintah kerja MES tersuai dan sudah biasa dengan susun atur serta pintasannya. Peralihan kepada borang asli DingTalk meningkatkan lengkung pembelajaran dan menerima tentangan kuat.

#### Bukti nilai

- **Aliran automatik**

  Aliran integrasi automatik terdiri daripada 5 langkah:

  1. **MES memulakan perintah kerja**: pelan pengeluaran / penciptaan perintah kerja.
  2. **Cipta instans kelulusan**: antara muka integrasi / penciptaan instans.
  3. **Kelulusan dalam DingTalk**: penghalaan kelulusan / paparan borang.
  4. **Tindakan penyokong**: kelulusan mudah alih / pengendalian pantas.
  5. **Selaraskan keputusan ke MES**: tulis balik status / penyelarasan data.

  Aliran manual tradisional (eksport ke Excel → e-mel → isi secara manual → beberapa pusingan e-mel → arkib secara manual) tidak cekap, terdedah kepada ralat, sukar dikesan dan memberikan pengalaman yang lemah. Sebaliknya, aliran automatik (sistem MES → Kelulusan DingTalk → kelulusan mudah alih → tulis balik data ke MES) lebih cekap, lebih tepat, boleh dikesan dan memberikan pengalaman yang lebih baik.
- **Kelebihan utama**

  - **Tiada migrasi borang:** Paparkan berpuluh-puluh medan perintah kerja MES terus pada halaman tersuai tanpa menyelaraskannya ke DingTalk Admin Console. Medan baharu hanya memerlukan perubahan pada bahagian hadapan MES, tanpa perubahan di pihak DingTalk.
  - **Keterkaitan data masa nyata:** Halaman tersuai memanggil API ERP dan PLM secara terus. Penyokong melihat baki inventori, versi lukisan dan perintah kerja terdahulu pada satu halaman. Kecekapan membuat keputusan meningkat lebih daripada 50%.
  - **Pengalaman lancar:** Ketua pasukan bengkel terus menggunakan antara muka dan aliran kerja kelulusan MES yang sudah biasa. Hanya aliran kerja asas yang beralih kepada enjin DingTalk, jadi kos latihan hampir sifar.

### Senario 2: Integrasi sistem kelulusan kredit untuk institusi kewangan (Kewangan)

#### Cabaran

Sebuah bank perdagangan menggunakan sistem kelulusan kredit dalaman untuk memproses permohonan pinjaman. Borang kelulusan mengandungi data sensitif seperti laporan kredit pelanggan, bukti pendapatan, penilaian cagaran dan output model penarafan risiko. Borang juga perlu memaparkan gabungan medan yang berbeza mengikut peringkat kelulusan. Proses sedia ada mempunyai isu berikut:

- **Kebimbangan keselamatan data:** Menyelaraskan medan sensitif seperti laporan kredit dan bukti pendapatan ke Admin Console Kelulusan OA DingTalk menimbulkan risiko kebocoran data. Jabatan pematuhan tidak akan meluluskannya.
- **Medan dinamik yang kompleks:** Kelulusan kredit mempunyai tiga peringkat, iaitu semakan awal, semakan kedua dan semakan akhir. Setiap peringkat memaparkan medan dan komponen yang berbeza. Borang asli DingTalk sukar menyokong rendering bersyarat atau logik papar/sembunyi dinamik.
- **Rantaian kelulusan yang panjang:** Penyokong bertukar berulang kali antara sistem kredit dan DingTalk untuk menyemak semua bahan. Purata 15 minit tambahan diperlukan bagi setiap kelulusan.

#### Bukti nilai

- **Aliran automatik**

  Aliran integrasi terdiri daripada 5 langkah:

  1. **Sistem pinjaman memulakan permohonan**: permohonan pinjaman / penciptaan borang.
  2. **Cipta instans kelulusan**: tetapkan `detailUrl` dan dapatkan `instanceId`.
  3. **Kelulusan dalam DingTalk**: penghalaan kelulusan / paparan borang.
  4. **Tindakan penyokong**: kelulusan mudah alih dengan butang **Tolak** dan **Luluskan**. Masukkan komen kelulusan dalam medan **Komen Kelulusan**.
  5. **Selaraskan keputusan kembali ke sistem pinjaman**: tulis balik status / penyelarasan data.
- **Kelebihan utama**

  - **Data sensitif kekal dalam domain:** Medan sensitif seperti laporan kredit dan bukti pendapatan hanya dipaparkan pada halaman tersuai sistem kredit. Data ini tidak pernah melalui DingTalk Admin Console, jadi keperluan pematuhan kewangan dipenuhi.
  - **Borang dinamik adaptif:** Halaman tersuai menukar gabungan medan dan peraturan pengesahan secara automatik mengikut peringkat kelulusan. Semakan awal memaparkan maklumat asas, semakan kedua menambah penilaian risiko dan semakan akhir memaparkan kesimpulan muktamad. Logik kekal jelas.
  - **Kecekapan kelulusan lebih tinggi:** Penyokong menyemak semua bahan dan mengambil tindakan pada satu halaman tanpa bertukar sistem. Setiap kelulusan mengambil masa 12 minit lebih singkat dan daya pemprosesan harian meningkat sebanyak 30%.

## Panduan pelaksanaan

### Seni bina teknikal

Seni bina teknikal penyelesaian ini merangkumi komponen teras berikut:

- **Lapisan pengesahan:** Mengurus kelayakan aplikasi dan mendapatkan access token untuk mengesahkan identiti di sebalik setiap panggilan API.
- **Lapisan enjin aliran kerja:** Menggunakan semula enjin aliran kerja Kelulusan OA rasmi DingTalk untuk mengendalikan penghalaan kelulusan, penghalaan nod, penugasan tugasan dan logik teras lain.
- **Lapisan integrasi halaman:** Menetapkan URL halaman butiran pihak ketiga apabila kelulusan dimulakan. Lapisan ini mengalihkan pengguna ke halaman tersuai sistem perniagaan apabila kelulusan dibuka dalam DingTalk.
- **Lapisan panggilan balik peristiwa:** Mendengar perubahan status instans Kelulusan OA DingTalk dan peristiwa callback tugasan kelulusan. Lapisan ini kemudian menyelaraskan status kelulusan dalam sistem perniagaan.

### Prasyarat

- **Penyediaan aplikasi:** Lengkapkan [penciptaan dan konfigurasi aplikasi](/ms/open/dingstart/create-application).
- **Keperluan kebenaran:** Pastikan anda mempunyai kebenaran Admin Organisasi atau Sub Admin DingTalk. Mohon kebenaran API berikut:

  - `Workflow.Form.Write` (kebenaran tulis untuk templat aliran kerja)
  - `Workflow.Instance.Write` (kebenaran tulis untuk instans aliran kerja)
  - `Workflow.Instance.Read` (kebenaran baca untuk instans aliran kerja)
- **Persekitaran pembangunan:** Pasang persekitaran pembangunan Java (JDK 1.6 atau lebih baharu) dan alat binaan Maven.
- **Penyediaan SDK:** Muat turun SDK Bahagian pelayan DingTalk. SDK ini tersedia untuk Java, Python, Go dan bahasa lain.

### Pelaksanaan kod

Langkah 1: Buka halaman butiran aplikasi dan dapatkan client ID serta Client Secret.

Langkah 2: Mohon kebenaran API. Mohon kebenaran yang berkaitan dengan "Kelulusan OA".

Langkah 3: Dapatkan kredensial akses aplikasi. Rujuk [Dapatkan Access Token aplikasi dalaman](/ms/open/development/obtain-the-access-token-of-an-internal-app). Apabila anda memanggil API, access token digunakan untuk mengesahkan pemanggil.

Langkah 4: Panggil API Kelulusan OA:

1. Panggil Server API baharu [Cipta atau kemas kini templat borang kelulusan](/ms/open/development/create-an-approval-form-template) untuk mendapatkan kod templat unik `processCode`.
2. Selepas templat kelulusan dicipta, pengguna boleh melihat dan **mengedit** templat borang kelulusan OA rasmi dalam Admin Console Kelulusan OA DingTalk. Pengguna juga boleh melihat dan mencari data templat, serta mengeksport atau memadam data templat.
3. Gunakan kod templat `processCode` untuk memanggil Server API baharu [Cipta instans kelulusan](/ms/open/development/create-an-approval-instance). Mulakan instans kelulusan dan dapatkan ID instans kelulusan `instanceId`.
4. Selepas instans kelulusan dicipta, buka Pusat Kelulusan OA DingTalk untuk melihat empat senarai kelulusan (Belum Selesai, Telah Diproses, Telah Dimohon dan Salinan kepada Saya). Cari data instans kelulusan dan ambil tindakan kelulusan.
5. Untuk menambah lampiran pada komen kelulusan, muat naik fail ke ruang Drive kelulusan terlebih dahulu. Kemudian, panggil Server API baharu [Tambah komen kelulusan](/ms/open/development/official-approval-adds-approval-comments).
6. Panggil Server API baharu [Dapatkan maklumat ruang Drive kelulusan](/ms/open/development/obtains-the-information-about-approval-nail-disk) untuk mendapatkan kebenaran muat naik bagi ruang Drive dan ID ruang Drive kelulusan `spaceId`.
7. Panggil JSAPI Bahagian klien `uploadAttachmentToDingTalk` untuk mendapatkan maklumat asas fail. Contoh ini menggunakan [JSAPI Explorer](https://open.dingtalk.io/tools/explorer/jsapi?id=10318).
8. Selepas mendapatkan `spaceId` ruang Drive kelulusan, panggil Server API baharu [Tambah komen kelulusan](/ms/open/development/official-approval-adds-approval-comments) dengan `instanceId` instans kelulusan untuk menambah komen pada borang kelulusan.
9. Untuk pratonton atau muat turun lampiran, panggil Server API [Benarkan muat turun fail Drive kelulusan](/ms/open/development/download-the-approval-nail-file) dan [Benarkan pratonton lampiran kelulusan](/ms/open/development/official-authorized-preview-approval-attachment) untuk membenarkan akses kepada fail Drive kelulusan. Kemudian, panggil Server API [Muat turun lampiran kelulusan](/ms/open/development/download-an-approval-attachment) untuk mendapatkan pautan fail `downloadUri` dan muat turun fail. Untuk tutorial terperinci, rujuk [Integrasi Kelulusan OA: Muat turun dan pratonton lampiran dalam kelulusan](/ms/open/development/new-version-of-attachment-approval-process).
10. Dengan menggunakan `instanceId` instans kelulusan, sistem perniagaan memanggil Server API baharu [Dapatkan butiran satu instans kelulusan](/ms/open/development/obtains-the-details-of-a-single-approval-instance-pop). Sistem mendapatkan butiran instans kelulusan dan maklumat bagi setiap nod tugasan kelulusan.
11. Gunakan `instanceId` instans kelulusan dan `taskId` untuk memanggil Server API baharu [Luluskan atau tolak tugasan kelulusan](/ms/open/development/approve-or-reject-the-approval-task). Ambil tindakan pada tugasan kelulusan.
12. Jika borang kelulusan yang dihantar mengandungi ralat dan instans kelulusan perlu dibatalkan, panggil Server API baharu [Batalkan instans kelulusan](/ms/open/development/revoke-an-approval-instance) dengan `instanceId` instans kelulusan untuk membatalkan borang kelulusan.
13. Apabila status borang kelulusan berubah, Kelulusan OA menolak peristiwa callback ke sistem perniagaan. Peristiwa ini termasuk permulaan, penamatan dan serahkan tugasan kelulusan, serta permulaan, penamatan, penghentian dan pemadaman instans kelulusan.

## Langkah pelaksanaan

### **Langkah 1: Dapatkan kelayakan aplikasi**

1. Log masuk ke [DingTalk Developer Console](https://open-dev.dingtalk.io/).
2. Pilih aplikasi sasaran untuk membuka halaman butiran aplikasi.
3. Klik **Maklumat Asas** > **Kelayakan dan Maklumat Asas**.
4. Rekodkan `Client ID` dan `Client Secret` aplikasi.

### Nota

   Simpan `Client Secret` anda dengan selamat dan jangan sekali-kali kongsikannya dengan pihak ketiga. Simpan nilai ini dalam pemboleh ubah persekitaran atau sistem pengurusan kunci. Jangan kod keras nilai ini.

### Langkah 2: Tambah kebenaran API

1. Pada halaman butiran aplikasi, klik **Urus kebenaran**.
2. Dalam kotak carian kebenaran, masukkan pengecam kebenaran berikut dan mohon kebenaran tersebut:

   - `Workflow.Form.Write` (kebenaran tulis untuk templat aliran kerja): Mencipta atau mengemas kini templat borang kelulusan.
   - `Workflow.Instance.Write` (kebenaran tulis untuk instans aliran kerja): Memulakan instans kelulusan dan menghantar keputusan kelulusan.
   - `Workflow.Instance.Read` (kebenaran baca untuk instans aliran kerja): Mendapatkan butiran instans kelulusan dan maklumat tugasan kelulusan.

<Note>
Senario perniagaan yang berbeza mungkin memerlukan gabungan kebenaran yang berbeza. Mohon kebenaran yang diperlukan oleh senario anda.
</Note>

### Langkah 3: Dapatkan kredensial akses (Access Token)

Gunakan Client ID dan Client Secret daripada Langkah 1 untuk mendapatkan kredensial akses aplikasi. Rujuk [Dapatkan Access Token aplikasi dalaman](/ms/open/development/obtain-the-access-token-of-an-internal-app).

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**Amalan terbaik**:

- **Strategi cache**: `accessToken` sah selama 2 jam. Cache token dalam memori atau Redis, dan muat semula token secara proaktif 5 minit sebelumnya ia tamat tempoh.
- **Kawalan keserentakan**: Elakkan konflik apabila beberapa thread memuat semula token pada masa yang sama. Gunakan kunci teragih.
- **Cuba semula apabila ralat**: Cuba semula secara automatik semasa rangkaian tidak stabil, sehingga 3 kali, dengan selang masa yang semakin panjang (1s → 2s → 4s).

## Soalan lazim

- **S: Bagaimanakah ruang letak `{processInstanceId}` dalam detailUrl digantikan?**

  Apabila DingTalk membuka butiran kelulusan, DingTalk menggantikan `{processInstanceId}` dengan ID instans kelulusan sebenar secara automatik. Sistem perniagaan tidak perlu mengendalikannya. Untuk menghantar parameter tambahan, tambahkan rentetan pertanyaan tersuai pada URL.
- **S: Adakah halaman butiran pihak ketiga perlu menyokong log masuk senyap DingTalk?**

  Ya. Apabila penyokong dialihkan dari DingTalk ke halaman butiran pihak ketiga, DingTalk menambahkan parameter authorization_code log masuk senyap `code` pada URL. Sistem perniagaan mesti melaksanakan log masuk senyap.
- **S: Bagaimanakah saya mengkonfigurasi URL tolakan untuk peristiwa callback instans kelulusan?**

  Pada halaman butiran aplikasi dalam DingTalk Developer Console, tambahkan langganan di bawah Langganan peristiwa dan masukkan URL callback HTTPS sistem perniagaan. DingTalk menolak data peristiwa dalam format JSON melalui POST.
- **S: Bagaimanakah DingTalk mengendalikan halaman butiran pihak ketiga yang gagal dimuatkan atau tamat masa?**

  DingTalk memaparkan halaman ralat lalai dan tidak menyekat proses kelulusan. Pastikan halaman butiran mempunyai ketersediaan tinggi. Sediakan mesej ralat yang jelas dan mekanisme cuba semula apabila halaman gagal dimuatkan.
- **S: Adakah keputusan kelulusan yang dihantar pada halaman tersuai diselaraskan ke DingTalk To-Do?**

  Ya. Selepas anda menghantar keputusan kelulusan melalui API Luluskan atau tolak tugasan kelulusan, tugasan yang berkaitan dalam DingTalk To-Do mengemas kini statusnya secara automatik. Penyokong juga menerima notifikasi.
