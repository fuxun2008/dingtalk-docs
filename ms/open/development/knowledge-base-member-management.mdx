title: "Pengurusan ahli Knowledge Base"
description: "Gunakan API ahli Knowledge Base untuk memberikan akses, melaraskan peranan, dan membatalkan akses secara programatik bagi senario pengambilan pekerja baharu, perubahan peranan, dan pemberhentian pekerja."
---

Dalam operasi harian Knowledge Base organisasi, apabila keperluan kolaborasi pasukan berkembang, admin sering perlu melaraskan kebenaran akses secara fleksibel—contohnya, menambah pekerja baharu ke dalam Knowledge Base semasa mereka mula bekerja, melaraskan peranan pengguna, atau membatalkan akses selepas pekerja meninggalkan syarikat. API pengurusan ahli Knowledge Base membolehkan anda melaksanakan operasi ini secara programatik dan mengautomasikan pengurusan Kebenaran Knowledge Base.

## Kes penggunaan

Pilih aliran yang sesuai berdasarkan senario di bawah:

- **Senario 1**: Apabila pekerja baharu mula bekerja, kolaborator luar menyertai, atau jabatan/kumpulan perlu mengakses Knowledge Base, admin boleh menggunakan aliran ini untuk menambah ahli secara pukal dan menetapkan peranan.
- **Senario 2**: Apabila seorang ahli dinaikkan pangkat menjadi admin, atau anda perlu menyekat operasi seorang ahli, gunakan aliran ini untuk menukar peranan mereka.
- **Senario 3**: Apabila seorang ahli meninggalkan syarikat, projek tamat, atau anda perlu membatalkan akses bagi pengguna atau jabatan tertentu, gunakan aliran ini untuk mengeluarkan mereka daripada Knowledge Base.
- **Senario 4**: Apabila organisasi mahu menjadikan Knowledge Base (seperti dasar syarikat atau manual produk) boleh diakses oleh semua pekerja tanpa menambah ahli satu demi satu.
- **Senario 5**: Digunakan apabila anda perlu mengaudit Kebenaran Knowledge Base, menyelesaikan masalah kebenaran, atau mengesahkan peranan semasa ahli sebelum melaksanakan operasi pukal.

## Gambaran keseluruhan kebenaran

### Peranan kebenaran (roleId)

| roleId | Nama peranan | Keupayaan |
| --- | --- | --- |
| **OWNER** | Pemilik | Kebenaran tertinggi. Baca, tulis, urus ahli, dan serahkan Knowledge Base. |
| **MANAGER** | Admin | Baca, tulis, dan urus ahli (tidak termasuk penyerahan). |
| **EDITOR** | Editor | Papar, edit, dan muat naik kandungan. |
| **DOWNLOADER** | Paparan dan muat turun | Papar dan muat turun kandungan. |
| **READER** | Paparan sahaja | Hanya boleh memaparkan kandungan; muat turun tidak dibenarkan. |

> **Nota**: Peranan **OWNER** tidak boleh ditambah atau dikeluarkan melalui API. Pencipta Knowledge Base ialah pemilik secara lalai.

### Jenis ahli (members.type)

| Nilai type | Penerangan | Maksud members.id |
| --- | --- | --- |
| **USER** | Pengguna | userId pekerja |
| **DEPT** | Jabatan | deptId jabatan. corpId mesti dihantar pada masa yang sama. |
| **CONVERSATION** | Sembang Kumpulan | chatId kumpulan DingTalk |
| **ORG** | Semua pekerja dalam organisasi | corpId organisasi. Hanya peranan **EDITOR**, **DOWNLOADER**, dan **READER** disokong. |

## Senario 1: Berikan akses Knowledge Base kepada ahli baharu

1. Panggil API [Dapatkan Senarai Knowledge Base](/ms/open/development/get-knowledge-base-list) dan baca medan `rootNodeId` daripada Respons. Ini ialah `dentryUuid` bagi nod akar Knowledge Base.
2. Dapatkan ID ahli:

   - Untuk menambah **pengguna**: Panggil API [Tanya butiran pengguna](/ms/open/development/query-user-details) untuk mendapatkan `userId`, atau gunakan [Dapatkan Senarai userId jabatan](/ms/open/development/query-the-list-of-department-userids) untuk mendapatkannya secara pukal.
   - Untuk menambah **jabatan**: Panggil API [Dapatkan Senarai jabatan](/ms/open/development/user-management-acquires-the-list-departments) untuk mendapatkan `deptId`.
   - Untuk menambah **sembang kumpulan**: Gunakan `chatId` kumpulan tersebut.
3. Panggil API [Tambah Kebenaran](/ms/open/development/add-permissions-file) dan pilih peranan yang sesuai berdasarkan keperluan perniagaan anda (contohnya, **EDITOR** untuk penyuntingan kolaboratif, **READER** untuk akses baca sahaja) untuk menambah ahli ke dalam Knowledge Base.

   > **Petua**: Satu Permintaan menyokong sehingga 30 ahli. Bahagikan kepada beberapa panggilan jika melebihi had ini.

   ```http lines
   POST /v2.0/storage/spaces/dentries/{dentryUuid}/permissions?unionId={unionId pengendali} HTTP/1.1
   Host: api.dingtalk.io
   x-acs-dingtalk-access-token: {ACCESS_TOKEN}
   Content-Type: application/json

   {
     "roleId": "EDITOR",
     "members": [
       { "type": "USER", "id": "userId pekerja" },
       { "type": "DEPT", "id": "deptId jabatan", "corpId": "corpId organisasi" }
     ]
   }
   ```

## Senario 2: Laraskan peranan seorang ahli dalam Knowledge Base

1. Untuk mengesahkan peranan semasa seorang ahli, panggil dahulu API [Dapatkan Senarai Kebenaran](/ms/open/development/get-permission-list).
2. Panggil API [Ubah suai Kebenaran](/ms/open/development/modify-permissions-file) dan nyatakan ahli serta peranan sasaran untuk menukar peranan tersebut.

   > **Nota**: Seorang ahli hanya boleh memegang satu peranan dalam Knowledge Base yang sama. Selepas perubahan, peranan lama akan digantikan secara automatik.

   ```http lines
   PUT /v2.0/storage/spaces/dentries/{dentryUuid}/permissions?unionId={unionId pengendali} HTTP/1.1
   Host: api.dingtalk.io
   x-acs-dingtalk-access-token: {ACCESS_TOKEN}
   Content-Type: application/json

   {
     "roleId": "MANAGER",
     "members": [
       { "type": "USER", "id": "userId pekerja" }
     ]
   }
   ```

## Senario 3: Batalkan akses Knowledge Base seorang ahli

1. Sahkan peranan yang sedang dipegang oleh ahli tersebut. Panggil API [Dapatkan Senarai Kebenaran](/ms/open/development/get-permission-list) untuk mendapatkan peranan semasa ahli tersebut (`roleId`). Peranan yang dinyatakan untuk dikeluarkan mesti sepadan dengan peranan sebenar yang dipegang.
2. Panggil API [Padam Kebenaran](/ms/open/development/delete-permissions-file).

   > **Nota**: `roleId` mesti sepadan dengan peranan yang sebenarnya dipegang oleh ahli tersebut; jika tidak, operasi tersebut tidak sah. Peranan **OWNER** tidak boleh dikeluarkan.

   ```http lines
   POST /v2.0/storage/spaces/dentries/{dentryUuid}/permissions/remove?unionId={unionId pengendali} HTTP/1.1
   Host: api.dingtalk.io
   x-acs-dingtalk-access-token: {ACCESS_TOKEN}
   Content-Type: application/json

   {
     "roleId": "EDITOR",
     "members": [
       { "type": "USER", "id": "userId pekerja" }
     ]
   }
   ```

## Senario 4: Jadikan Knowledge Base boleh diakses oleh semua pekerja

Panggil API [Tambah Kebenaran](/ms/open/development/add-permissions-file), tetapkan jenis ahli kepada **ORG**, dan nyatakan peranan awam yang berkaitan.

> **Nota**: Selepas Kebenaran **ORG** diberikan, semua pekerja dalam organisasi boleh mengakses Knowledge Base dengan peranan yang dinyatakan. Ahli jenis **ORG** tidak akan muncul dalam hasil pertanyaan Senarai ahli. Untuk membatalkan akses bagi semua pekerja, panggil API pengeluaran dengan cara yang sama dan hantar **ORG** sebagai `type`.

```http
POST /v2.0/storage/spaces/dentries/{dentryUuid}/permissions?unionId={unionId pengendali} HTTP/1.1
Host: api.dingtalk.io
x-acs-dingtalk-access-token: {ACCESS_TOKEN}
Content-Type: application/json

{
  "roleId": "READER",
  "members": [
    { "type": "ORG" }
  ]
}
```

## Senario 5: Tanya Senarai ahli semasa bagi sesuatu Knowledge Base

Panggil API [Dapatkan Senarai Kebenaran](/ms/open/development/get-permission-list). Penapisan mengikut peranan dan penomboran halaman disokong.

```http
POST /v2.0/storage/spaces/dentries/{dentryUuid}/permissions/query?unionId={unionId pengendali} HTTP/1.1
Host: api.dingtalk.io
x-acs-dingtalk-access-token: {ACCESS_TOKEN}
Content-Type: application/json

{
  "option": {
    "maxResults": 30,
    "filterRoleIds": ["MANAGER", "EDITOR"]
  }
}
```

Setiap rekod dalam Respons mengandungi jenis, ID, nama, dan peranan ahli tersebut. Jika `nextToken` tidak kosong, terdapat lebih banyak data yang tersedia. Hantar `nextToken` dalam Permintaan seterusnya untuk terus mendapatkan hasil.

## Nota

- Pengendali mesti mempunyai Kebenaran **OWNER** atau **MANAGER** ke atas Knowledge Base; jika tidak, API akan mengembalikan Ralat Kebenaran tidak mencukupi.
- Peranan **OWNER** tidak boleh ditambah atau dikeluarkan melalui API. Pencipta Knowledge Base ialah pemilik secara lalai.
- Apabila mengeluarkan seorang ahli, `roleId` mesti sepadan dengan peranan yang sebenarnya dipegang oleh ahli tersebut; jika tidak, operasi tersebut tidak sah.
- Satu Permintaan menyokong sehingga 30 ahli dalam Senarai `members`. Bahagikan kepada beberapa panggilan jika melebihi had ini.
