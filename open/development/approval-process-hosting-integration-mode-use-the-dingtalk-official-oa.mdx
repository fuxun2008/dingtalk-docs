# Approval Process Hosting: Integrate DingTalk Processes with Third-Party Pages

## Overview

This solution uses the approval process hosting integration mode. It connects the DingTalk official OA Approval workflow engine with custom business pages built by third parties. The business system calls the DingTalk OA Approval API to create an approval workflow instance and specifies the detail page URL of the third-party approval system at creation time. When an approver opens the approval details in DingTalk, DingTalk automatically redirects the approver to the custom page in the business system to complete the approval. This approach reuses the official DingTalk workflow engine and keeps the custom display of complex business forms, so you can integrate quickly at low cost.

### Background

Organizations often build or purchase third-party OA systems with their own approval processes and pages. Employees must switch between multiple systems to handle approvals, which fragments their work and reduces efficiency. When you connect your own approval processes to the DingTalk OA Approval Center, users can open business system pages and approve requests directly in DingTalk, with a one-stop experience.

Organizations commonly face the following challenges:

- **Scattered approval entry points:** Employees handle approvals separately in multiple systems. DingTalk To-Do reminders do not cover approval tasks in in-house systems, so tasks are easily missed.
- **Inconsistent approval experience:** Approval pages in in-house systems do not match the DingTalk style. Users must adapt to different interaction patterns, which raises the learning curve.
- **Low reach of to-do notifications:** In-house systems rely on email or SMS for approval notifications. These channels are slow and cannot take advantage of DingTalk message push and the To-Do center.
- **Isolated approval data:** Approval status, processing records, and other data are scattered across systems. Managers cannot view approval progress in one place in DingTalk.

### Core Value

This solution delivers value in three areas:

- **Flexible integration:** Combine the official DingTalk OA Approval workflow with custom third-party business pages. Reuse the workflow capabilities of the official OA Approval engine and connect seamlessly with DingTalk Chat, To-Do, and Notifications for efficient approvals.
- **Lower cost:** Use custom third-party business pages as approval detail pages. You do not need to sync every form component field to DingTalk. This reduces integration effort and preserves the processes and page layouts users already know.
- **Consistent experience:** Initiate processes from the business system and call the official DingTalk OA Approval API to create OA Approval processes. Approvers open the custom business system page directly from DingTalk OA Approval, To-Do, or message cards, with a consistent experience.

### Use Cases

This solution fits business systems that need the official DingTalk workflow engine but have complex form pages. Typical cases include:

- **Complex form approval:** The business system has approval forms with many custom component fields. Configuring them one by one in the DingTalk Admin Console is impractical, so the forms must be fully rendered on a custom page.
- **Legacy system integration:** The system already has mature approval pages and interaction logic. You want to adopt the DingTalk workflow with minimal changes and keep the existing user experience.
- **Cross-system collaborative approval:** The approval process requires data linkage across multiple business systems. The custom page must query and display cross-system information in real time.

## Typical Business Scenarios

### Scenario 1: Production Work Order Approval for a Large Manufacturer (Manufacturing)

#### Challenges

A large manufacturer uses an in-house MES system to manage production work orders. Work order approval involves dozens of fields, such as equipment number, process route, bill of materials, and quality inspection standards. It also requires real-time links to ERP inventory data and PLM drawings. The existing process has the following issues:

- **Heavy form configuration:** Syncing all work order fields to the DingTalk OA Approval Admin Console requires maintaining hundreds of component mappings. Each new field requires changes to both the DingTalk configuration and the business system, which drives up maintenance costs.
- **Missing data linkage:** Native DingTalk approval forms cannot query ERP inventory or PLM drawings in real time. Approvers must switch between systems, which slows them down.
- **Disrupted user habits:** Workshop team leaders have long used the custom MES work order approval page and know its layout and shortcuts. Switching to native DingTalk forms raises the learning curve and meets strong resistance.

#### Value Validation

- **Automated Flow**

  The automated integration flow consists of 5 steps:

  1. **MES Initiates Work Order** — production plan / work order creation.
  2. **Create Approval Instance** — integration interface / instance creation.
  3. **Approval Within DingTalk** — approval routing / form display.
  4. **Approver Action** — mobile approval / quick handling.
  5. **Sync Result to MES** — status write-back / data sync.

  The traditional manual flow (export to Excel → email → manual filling → multiple email rounds → manual archiving) is inefficient, error-prone, hard to trace, and offers a poor experience. In contrast, the automated flow (MES system → DingTalk Approval → mobile approval → write data back to MES) is more efficient, more accurate, traceable, and offers a better experience.
- **Key Advantages**

  - **Zero form migration:** Render the dozens of MES work order fields directly on the custom page without syncing them to the DingTalk Admin Console. New fields only require changes to the MES frontend, with no changes on the DingTalk side.
  - **Real-time data linkage:** The custom page calls ERP and PLM APIs directly. Approvers view remaining inventory, drawing versions, and historical work orders on a single page, improving decision efficiency by more than 50%.
  - **Seamless experience:** Workshop team leaders keep using the familiar MES approval interface and workflows. Only the underlying workflow switches to the DingTalk engine, so training costs are close to zero.

### Scenario 2: Credit Approval System Integration for a Financial Institution (Finance)

#### Challenges

A commercial bank uses an in-house credit approval system to process loan applications. The approval form contains sensitive data such as customer credit reports, proof of income, collateral valuations, and risk rating model outputs. It must also display different field combinations depending on the approval stage. The existing process has the following issues:

- **Data security concerns:** Syncing sensitive fields such as credit reports and proof of income to the DingTalk OA Approval Admin Console creates a risk of data leakage, and the compliance department will not approve it.
- **Complex dynamic fields:** Credit approval has three stages: initial review, secondary review, and final review. Each stage displays different fields and components. Native DingTalk forms cannot easily support conditional rendering or dynamic show/hide logic.
- **Long approval chain:** Approvers switch repeatedly between the credit system and DingTalk to review all materials, adding an average of 15 minutes per approval.

#### Value Validation

- **Automated Flow**

  The integration flow consists of 5 steps:

  1. **Lending system initiates** — loan application / form creation.
  2. **Create approval instance** — specify `detailUrl`, obtain `instanceId`.
  3. **Approval within DingTalk** — approval routing / form display.
  4. **Approver action** — mobile approval with **Reject** and **Approve** buttons; enter approval comments in the **Approval Comments** field.
  5. **Sync result back to lending system** — status write-back / data sync.
- **Key Advantages**

  - **Sensitive data stays in-domain:** Sensitive fields such as credit reports and proof of income display only on the custom page of the credit system and never pass through the DingTalk Admin Console, meeting financial compliance requirements.
  - **Adaptive dynamic forms:** The custom page switches field combinations and validation rules automatically by approval stage. Initial review shows basic information, secondary review adds risk assessment, and final review shows the final conclusion, keeping the logic clear.
  - **Higher approval efficiency:** Approvers review all materials and take action on a single page without switching systems. Each approval takes 12 minutes less, and daily throughput increases by 30%.

## Implementation Guide

### Technical Architecture

The technical architecture of this solution includes the following core components:

- **Authentication layer:** Manages App credentials and obtains access tokens to verify the identity behind every API call.
- **Workflow engine layer:** Reuses the official DingTalk OA Approval workflow engine to handle approval routing, node routing, task assignment, and other core logic.
- **Page integration layer:** Specifies the third-party detail page URL when an approval is initiated and redirects to the custom business system page when it is opened in DingTalk.
- **Event callback layer:** Listens for DingTalk OA Approval instance status changes and approval task callback events, then syncs the approval status in the business system.

### Prerequisites

- **App preparation:** Complete [App creation and configuration](/open/dingstart/create-application).
- **Permission requirements:** Have DingTalk Organization Admin or Sub Admin permissions, and apply for the following API permissions:

  - `Workflow.Form.Write` (write permission for workflow templates)
  - `Workflow.Instance.Write` (write permission for workflow instances)
  - `Workflow.Instance.Read` (read permission for workflow instances)
- **Development environment:** Install a Java development environment (JDK 1.6 or later) and the Maven build tool.
- **SDK preparation:** Download the DingTalk Server-side SDK, available for Java, Python, Go, and other languages.

### Code Implementation

Step 1: Go to the App details page and get the client ID and Client Secret.

Step 2: Apply for API permissions. Request the permissions related to "OA Approval".

Step 3: Get the App access credential. See [Get the Access Token of an Internal App](/open/development/obtain-the-access-token-of-an-internal-app). When you call an API, the access token authenticates the caller.

Step 4: Call the OA Approval APIs:

1. Call the new Server API [Create or Update an Approval Form Template](/open/development/create-an-approval-form-template) to get the unique template code `processCode`.
2. After the approval template is created, users can view and **edit** the official OA approval form template, view and search template data, and export or delete template data in the DingTalk OA Approval Admin Console.
3. Using the template code `processCode`, call the new Server API [Create an Approval Instance](/open/development/create-an-approval-instance) to initiate an approval instance and get the approval instance ID `instanceId`.
4. After the approval instance is created, go to the DingTalk OA Approval Center to view the four approval lists (Pending, Processed, Initiated, and CC'd to Me), search approval instance data, and take approval actions.
5. To add attachments to approval comments, first upload the files to the approval Drive space, then call the new Server API [Add Approval Comments](/open/development/official-approval-adds-approval-comments).
6. Call the new Server API [Get Approval Drive Space Information](/open/development/obtains-the-information-about-approval-nail-disk) to get upload permission for the Drive space and the approval Drive space ID `spaceId`.
7. Call the Client-side JSAPI `uploadAttachmentToDingTalk` to get basic file information. This example uses [JSAPI Explorer](https://open.dingtalk.io/tools/explorer/jsapi?id=10318).
8. After you get the approval Drive space `spaceId`, call the new Server API [Add Approval Comments](/open/development/official-approval-adds-approval-comments) with the approval instance `instanceId` to add comments to the approval form.
9. To preview or download attachments, call the Server APIs [Authorize Download of Approval Drive Files](/open/development/download-the-approval-nail-file) and [Authorize Preview of Approval Attachments](/open/development/official-authorized-preview-approval-attachment) to authorize access to approval Drive files. Then call the Server API [Download an Approval Attachment](/open/development/download-an-approval-attachment) to get the file link `downloadUri` and download the file. For a detailed tutorial, see [OA Approval Integration: Download and Preview Attachments in Approvals](/open/development/new-version-of-attachment-approval-process).
10. Using the approval instance `instanceId`, the business system calls the new Server API [Get the Details of a Single Approval Instance](/open/development/obtains-the-details-of-a-single-approval-instance-pop) to get the approval instance details and the information for each approval task node.
11. Using the approval instance `instanceId` and `taskId`, call the new Server API [Approve or Reject an Approval Task](/open/development/approve-or-reject-the-approval-task) to act on the approval task.
12. If a submitted approval form contains errors and the approval instance must be revoked, call the new Server API [Revoke an Approval Instance](/open/development/revoke-an-approval-instance) with the approval instance `instanceId` to revoke the approval form.
13. When the approval form status changes, OA Approval pushes callback events to the business system, including approval task start, end, and transfer, and approval instance start, end, termination, and deletion.

## Implementation Steps

### **Step 1: Get the App Credential**

1. Sign in to the [DingTalk Developer Console](https://open-dev.dingtalk.io/).
2. Select the target App to open the App details page.
3. Click **Basic Information** > **Credentials and Basic Information**.
4. Record the App's `Client ID` and `Client Secret`.

### Note

   Keep your `Client Secret` secure and never share it with third parties. Store it in environment variables or a key management system instead of hard-coding it.

### Step 2: Add API Permissions

1. On the App details page, click **Manage permissions**.
2. In the permission search box, enter the following permission identifiers and apply for them:

   - `Workflow.Form.Write` (write permission for workflow templates): Creates or updates approval form templates.
   - `Workflow.Instance.Write` (write permission for workflow instances): Initiates approval instances and submits approval results.
   - `Workflow.Instance.Read` (read permission for workflow instances): Gets approval instance details and approval task information.

<Note>
Different business scenarios may require different permission combinations. Apply for the permissions your scenario needs.
</Note>

### Step 3: Get the Access Credential (Access Token)

Use the Client ID and Client Secret from Step 1 to get the App access credential. See [Get the Access Token of an Internal App](/open/development/obtain-the-access-token-of-an-internal-app).

```java
public void getAccessToken() throws Exception {
  Config config = new Config();
  config.protocol = "https";
  config.regionId = "central";
  com.aliyun.dingtalkoauth2_1_0.Client client = new com.aliyun.dingtalkoauth2_1_0.Client(config);
  GetAccessTokenRequest accessTokenRequest = new GetAccessTokenRequest()
    .setAppKey("din*********hgn")
    .setAppSecret("9G_O************mBkhgGIO");
  GetAccessTokenResponse accessToken = client.getAccessToken(accessTokenRequest);
  System.out.println(JSON.toJSONString(accessToken.getBody()));
}
```

**Best practices**:

- **Caching strategy**: The `accessToken` is valid for 2 hours. Cache it in memory or Redis, and refresh it proactively 5 minutes before it expires.
- **Concurrency control**: Prevent conflicts caused by multiple threads refreshing the token at the same time. Use a distributed lock.
- **Error retries**: Retry automatically during network fluctuations, up to 3 times, with increasing intervals (1s → 2s → 4s).

   - `success`: Whether the operation succeeded.

## FAQ

- **Q: How is the `{processInstanceId}` placeholder in detailUrl replaced?**

  When DingTalk opens the approval details, it automatically replaces `{processInstanceId}` with the actual approval instance ID. The business system does not need to handle this. To pass additional parameters, append a custom query string to the URL.
- **Q: Does the third-party detail page need to support DingTalk silent login?**

  Yes. When an approver is redirected from DingTalk to the third-party detail page, DingTalk appends the silent login authorization code parameter `code` to the URL. The business system must implement silent login.
- **Q: How do I configure the push URL for approval instance callback events?**

  On the App details page in the DingTalk Developer Console, add a subscription under event subscription and enter the HTTPS callback URL of the business system. DingTalk pushes event data in JSON format via POST.
- **Q: How does DingTalk handle a third-party detail page that fails to load or times out?**

  DingTalk displays a default error page and does not block the approval process. Ensure high availability for the detail page, and provide a clear error message and a retry mechanism when the page fails to load.
- **Q: Do approval results submitted on the custom page sync to DingTalk To-Do?**

  Yes. After you submit the approval result through the Approve or Reject an Approval Task API, the corresponding task in DingTalk To-Do updates its status automatically, and the approver receives a notification.
