# Integrate OA Approval: Query Visible Forms and Pending Approval Counts

## Overview

### Background

After employees sign in to DingTalk, they need to see their approval permissions, the forms they can view, and the number of approvals waiting for them. The existing OA Approval system has no unified personal approval workbench. The APIs for querying visible forms and pending approval counts let you build a personalized approval Dashboard in DingTalk. Employees can then prioritize their approval work more effectively.

Organizations often face the following challenges in daily operations:

- **Unclear approval permissions:** Employees do not know which form types they can view or approve. In new business scenarios, they must repeatedly ask the Admin to confirm their permission scope. Communication is costly, and responses are slow.
- **Invisible to-do counts:** The DingTalk To-Do center shows only a task list. It cannot summarize pending approvals by form type. Employees cannot see how their workload is distributed, which makes it hard to plan the order of work.
- **Scattered cross-system approvals:** Approvals from OA, expense control, HR, and other systems sit behind separate entry points. Employees must sign in to each system to check pending items, which takes more than 15 minutes every day.
- **Unbalanced approval workload:** Managers cannot see team members' pending approval counts or backlogs in real time. Work assignment relies on subjective judgment, so some employees stay overloaded while others remain idle.

### Key Benefits

This solution delivers value in three areas:

- **Dynamic form lists:** Retrieve all manageable approval forms in your organization, or the forms visible to a specific user, in real time through APIs. No static form configuration table is needed in your business system.
- **Accurate to-do statistics:** Query a user's pending approval count by userId. Display personalized to-do reminders on the business system's Home page or message center.
- **Controlled permission isolation:** Form list queries automatically follow the DingTalk OA Approval permission system. Only forms the caller can access are returned, which keeps data secure.

### Use Cases

This solution fits scenarios where your own business system must show approval form entry points dynamically and display users' to-do counts in real time. Typical use cases include:

- **Unified approval workbench:** Aggregate all approval form entry points visible to a user, along with to-do counts, on the business system's Home page for one-stop approval access.
- **Smart form recommendation:** Filter the visible form list dynamically by user role and department. Show only approval types related to the user's responsibilities.
- **To-do notification push:** Poll changes in users' pending approval counts on a schedule. Trigger in-app messages or mobile push notifications.

## Implementation Guide

### Technical Architecture

The technical architecture of this solution includes the following core components:

- **Authentication layer:** Manages App credentials and obtains access tokens to verify the identity behind every API call.
- **Form query layer:** Calls query APIs to get manageable organization forms, user-visible forms, and pending approval counts, and returns structured form metadata.
- **Permission filtering layer:** Uses the DingTalk OA Approval permission system to filter out forms the caller cannot access, which keeps data secure.
- **Cache acceleration layer:** Caches form lists and to-do counts for short periods to reduce API call frequency and improve front-end rendering performance.

### Prerequisites

- **App preparation:** Complete the [App creation and configuration](/open/dingstart/create-application) process and obtain the client ID and Client Secret.
- **Permission requirements:** Have DingTalk Organization Admin or Sub Admin permissions, and apply for the following API permissions:

  - `Workflow.Form.Write` (workflow template write permission)
  - `Workflow.Form.Read` (workflow template read permission)
  - `Workflow.Instance.Write` (workflow instance write permission)
  - `Workflow.Instance.Read` (workflow instance read permission)
- **Development environment:** Install a Java development environment (JDK 1.6 or later) and the Maven build tool.
- **SDK preparation:** Download the DingTalk Server-side SDK, which supports Java, Python, Go, and other languages.

### Code Implementation

Step 1: Get the App credential information, including the client ID and Client Secret.

Step 2: Apply for API permissions related to OA Approval.

Step 3: Obtain the App access credential. See [Obtain the Access Token of an Internal App](/open/development/obtain-the-access-token-of-an-internal-app). Each API call authenticates the caller with the access token.

Step 4: Call the OA Approval APIs:

1. Call the new Server API [Create or Update an Approval Form Template](/open/development/create-an-approval-form-template) to get the unique template code `processCode`.
2. After creating multiple approval form templates, call the new Server API [Get All Manageable Forms for the Current Organization](/open/development/get-all-manageable-forms-for-the-current-enterprise) to get all approval forms the user can manage in the current organization. The user specified by userId must have OA Approval permissions for the organization.
3. After creating multiple approval form templates, call the new Server API [Get the List of Approval Forms Visible to a Specified User](/open/development/obtains-a-list-of-approval-forms-visible-to-the-specified) to get the approval forms visible to that user.
4. Call the new Server API [Create an Approval Instance](/open/development/create-an-approval-instance) with the template code `processCode` to create an approval instance and get its `instanceId`.
5. After creating multiple approval instances, call the new Server API [Get a List of Approval Instance IDs](/open/development/obtain-an-approval-list-of-instance-ids) with the template code `processCode` to get the approval instance IDs of relevant departments within your permission scope.
6. After creating multiple approval instances, you can also call the new Server API [Get the Number of Pending Approvals for a User](/open/development/queries-the-number-of-requests-to-be-approved-by-users) with the user's userId to get that user's pending approval count.

## Implementation Steps

### **Step 1: Get App Credentials**

1. Sign in to the [DingTalk Developer Console](https://open-dev.dingtalk.io/).
2. Select the target App to open its details page.
3. Click **Basic Information** > **Credentials and Basic Information**.
4. Record the App's `Client ID` and `Client Secret`.

### Note

   Keep the `Client Secret` secure and never disclose it to third parties. Store it in environment variables or a key management system instead of hard-coding it.

### Step 2: Add API Permissions

1. On the App details page, click **Manage permissions**.
2. Enter the following permission identifiers in the permission search box and apply for them:

   - `Workflow.Form.Write` (workflow template write permission): Creates or updates approval form templates.
   - `Workflow.Form.Read` (workflow template read permission): Gets manageable organization forms and user-visible form lists.
   - `Workflow.Instance.Write` (workflow instance write permission): Creates approval instances.
   - `Workflow.Instance.Read` (workflow instance read permission): Gets users' pending approval counts.

<Note>
Different business scenarios may require different permission combinations. Apply for permissions based on your actual needs.
</Note>

### Step 3: Get the Access Credential (Access Token)

Use the Client ID and Client Secret from Step 1 to obtain the App access credential. See [Obtain the Access Token of an Internal App](/open/development/obtain-the-access-token-of-an-internal-app).

**Best practices**:

- **Caching strategy:** The `accessToken` is valid for 2 hours. Cache it in memory or Redis, and refresh it proactively 5 minutes before it expires.
- **Concurrency control:** Prevent conflicts caused by multiple threads refreshing the token at the same time. Use a distributed lock.
- **Error retries:** Retry automatically on network fluctuations, up to 3 times, with increasing intervals (1s → 2s → 4s).

## FAQ

- **Q: Why does the form list API return an empty result?**

  Check whether the user specified by userId has OA Approval management permissions for the organization. Only users with OA Approval permissions can query the list of manageable forms.
- **Q: What is the difference between getting user-visible forms and getting manageable organization forms?**

  Getting manageable organization forms returns all forms the userId user can manage, typically from an Admin perspective. Getting user-visible forms returns the forms the user can submit as an applicant, typically from a regular employee perspective. The two cover different permission scopes.
- **Q: Which approval statuses does the count returned by the pending approval API include?**

  It includes only instances currently in the "Pending approval" status. It excludes approval instances that are Accepted, Declined, revoked, or terminated.
- **Q: Should I cache the results of the form list APIs?**

  Yes. Form metadata changes infrequently, so cache it in your business system for 5–10 minutes to reduce API call count. Do not cache the pending approval count for long. Poll it every 1–5 minutes to keep it up to date.
- **Q: If a user belongs to multiple departments, are visible forms returned more than once?**

  No. The API returns a deduplicated form list. Even if the same form matches multiple times through permissions from different departments, it appears only once in the result.
