# Configure Attendance Rules: Create Attendance Groups in Batch and Adjust Them Dynamically

## Overview

This solution automates attendance group management end to end. It uses the attendance group management APIs on the DingTalk Open Platform to integrate business platforms such as HR and OA systems with DingTalk Attendance.

### Background

Organizations face the following challenges in attendance management:

- **Complex attendance rules**: Fixed shift attendance, shift-based attendance, flexible working hours, and other modes coexist. Manual configuration is slow and error-prone.
- **Frequent personnel changes**: Onboarding, offboarding, and transfers require manual updates to attendance group members. Organizations with 1,000+ employees spend several hours on this every week.
- **No cross-system sync**: Organization Structure changes in the HR system do not reach DingTalk attendance groups in time, which causes clock-in data errors.
- **No batch operations**: Admins cannot create or update multiple attendance groups at once. Updating them one by one is highly inefficient.

### Key Benefits

This solution helps organizations achieve the following:

- **Automated attendance group management**: Create, query, update, and delete attendance groups through the API with zero manual intervention.
- **Smart shift association**: Create new shifts or associate existing ones automatically to keep attendance rules accurate.
- **Efficient batch execution**: Get, search, and update attendance groups in batch to significantly improve operational efficiency.
- **Unified cross-system data**: Sync HR, OA, and DingTalk Attendance data in real time to eliminate data silos.

### Use Cases

This solution fits the following typical business scenarios:

- **HR system integration**: Sync attendance rules from the HR management system to DingTalk attendance groups automatically.
- **Mergers and acquisitions**: Quickly create attendance groups and shift configurations in batch for newly acquired companies.
- **OA workflow integration**: Create or adjust the corresponding attendance group automatically when an Approval process ends.
- **Dynamic permission adjustment**: Update attendance group members and Admin permissions automatically based on Department changes.

## Typical Business Scenarios

### Scenario 1: Sync Attendance Groups from the HR System (Batch Creation and Management)

#### Pain Points

In the traditional model, after HR plans new attendance rules in the HR system, they must sign in to the DingTalk admin console and manually create each attendance group, configure shifts, and add members. Organizations with 1,000+ employees typically have 20 to 50 attendance groups. Manual setup takes hours and often leads to incorrect shifts or missing members.

#### Value Validation

- **Automated workflow**

  The API-based Automation flow runs in these steps:
  1. The HR system records a new Employee.
  2. The system finds the matching attendance group automatically based on the Employee's Department.
  3. The system adds new members in batch through the API.
  4. The system verifies and confirms the result in real time.
  5. Clock-in permission takes effect immediately.
- **Key advantages**

  - **Fully automatic trigger**: The API call runs automatically after HR enters a new Employee in the HR system. No one needs to sign in to the DingTalk admin console or start the action manually. Entry and sync happen together.
  - **Precise matching**: The system queries and matches the `groupKey` of the attendance group automatically based on the Employee's Department ID. This prevents clock-in errors caused by selecting the wrong attendance group manually.
  - **Immediate effect**: After the batch-add-employees API adds members in batch, the query-members-by-id API verifies the result immediately. Employees can clock in as soon as they join the attendance group.
  - **Audit trail**: Each API call records the operator, timestamp, attendance group ID, Employee `userId`, and other details to meet compliance auditing and traceability requirements.

### Scenario 2: Sync Attendance Groups Automatically after Organization Structure Changes

#### Pain Points

When departments merge or split, or when employees transfer, HR must manually update the member lists and scheduling rules of each affected attendance group. Large-scale restructuring can involve dozens of attendance groups. Manual updates are time-consuming and often miss some groups, which causes clock-in errors for employees.

#### Value Validation

- **Automated workflow**

  The Automation flow runs in five steps:

  1. **OA Approval trigger**: When an approval for a department merge or split or a personnel transfer is passed, the system automatically captures the change **event**.
  2. **Identify affected attendance groups**: The system queries all associated attendance groups automatically based on the changed Department ID.
  3. **API batch update**: The system calls the DingTalk attendance group update API to modify member lists and shift configurations in batch.
  4. **Real-time data validation**: Immediately after the update, the system calls the query API to verify data consistency across all attendance groups.
  5. **Sync complete**: Attendance group synchronization finishes and the updated attendance rules take effect with no manual intervention.
- **Key advantages**

  - **Automatic trigger**: The system captures the change event and runs the sync automatically when the OA Approval process ends. No one needs to start or monitor it. Approval and sync happen together.
  - **Precise batch processing**: The system identifies and updates all affected attendance groups at once. This prevents omissions from manual lookups and ensures 100% coverage of organizational changes.
  - **Real-time validation and Feedback**: The system calls the query API right after the update to verify data consistency and sends alerts automatically on errors. This ensures attendance rules take effect correctly.
  - **Complete audit logs**: Each API call records the operator, timestamp, and change Content to meet compliance auditing and traceability requirements.

## Implementation Guide

### Technical Architecture

This solution is built on the Server API of the DingTalk Open Platform. The core technical components are:

- **Authentication layer**: Uses the `Client ID` and `Client Secret` to get the `access_token` and secure API calls.
- **Attendance group management layer**: Provides complete API capabilities to create, query, update, and delete attendance groups. Supports fixed shift attendance groups and shift-based attendance groups.
- **Shift management layer**: Provides API capabilities to create and query shifts, which are prerequisite resources for attendance groups.
- **Error handling layer**: Provides a comprehensive error code system to help you locate and resolve issues quickly.

**API versions**: The Server API has new and legacy versions. Use the new version first for better performance and feature support.

### Prerequisites

Meet the following conditions before you implement the solution:

- **App preparation**: Create and configure an Internal app. For details, see [Create and Configure an App](/open/dingstart/create-application).
- **Permission requirements**: Have DingTalk Organization Admin or Sub Admin permissions, and apply for the following API permissions:

  - `qyapi_attendance_group_read` (attendance group query permission)
- **Development environment**: Install a Java development environment (JDK 1.6 or later) and the Maven build tool.
- **SDK preparation**: Download the DingTalk Server-side SDK. For details, see Server-side SDK Download. The SDK supports Java, Python, Go, and other languages.

**Best practices**:

- **Caching strategy**: The `access_token` is valid for 2 hours. Cache it in memory or Redis and Refresh it proactively 5 minutes before it expires.
- **Concurrency control**: Prevent multiple threads from refreshing the token at the same time, which causes Conflicts. Use a distributed lock.
- **Retry on errors**: Retry automatically on network fluctuations, up to 3 times, with increasing intervals (1s → 2s → 4s).

## FAQ

- **Q1: What should I do if I get a "Shift does not exist" error when creating an attendance group?**

  A: A fixed shift attendance group requires an existing shift. Call the [Create a Shift](/open/development/create-modify-shifts) API first, or call the [Get Shift Summaries](/open/development/enterprise-shift-query-in-batches) API to get an existing shift ID. Then create the attendance group.
- **Q2: How do I get information about all attendance groups in batch?**

  A: Follow two steps. First, call [Get Attendance Group Summaries in Batch](/open/development/batch-query-of-simple-information-of-the-attendance-group) to get brief information (including the `id`) for all attendance groups. Then call [Get Attendance Group Details in Batch](/open/development/batch-obtain-attendance-group-details) as needed to get the full details.
- **Q3: What is the difference between the attendance group id and groupKey?**

  A: `id` is the numeric identifier of the attendance group, and `groupKey` is its string identifier. Some APIs, such as Delete an Attendance Group, require the `groupKey`. Use the [Convert groupId to groupKey](/open/development/groupid-to-groupkey) API to convert between them.
- **Q4: Do I need to pass all fields when updating an attendance group?**

  A: No. Pass only the fields to modify and the attendance group `id`. Fields you omit keep their original values.
