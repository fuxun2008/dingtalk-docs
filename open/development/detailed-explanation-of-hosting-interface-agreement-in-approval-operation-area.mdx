## Approval Action Area Overview

The approval action area appears at the bottom of the approval details page and contains the action buttons. In the example, the area includes **Comment**, **Create group discussion**, **Delete**, **Return to original form**, **Reject**, and **Approve**. Third-party apps can customize the buttons in this area.

## How the Approval Action Area Works

When creating an approval template or approval instance, a third-party app can register callbacks that render custom buttons in the approval action area and submit requests. The app must provide two APIs for hosted rendering and for processing user requests:

- **Button rendering:** DingTalk calls back the third-party app to get the button definitions for the action area.
- **Approval operation:** DingTalk calls back the third-party API to receive and process approval actions that users submit.

The integration flow runs from the **Third-party app** to the **Approval backend: OA Open API**, then to the **Approval frontend**. The Approval frontend renders the result on three surfaces: **To-do**, **Approval Center**, and **IM interactive card**. The third-party app completes these steps in order:

1. Create template
2. Create instance
3. Register the Approval action area's Custom render Button & Submit request callback
4. Create task

During rendering and submission, the Approval frontend calls the third-party app through an **SPI callback (render / operate Approval)**. The **Approval backend: Open gateway** routes this callback. The **To-do** and **IM interactive card** surfaces trigger the operate-Approval callback.

## Core Model Definitions

- **ProcessFeatureConfig: Process Center Integration Configuration**

  In Process Center integration mode, this configuration lets third-party apps define custom logic for certain business feature modules. The approval page hosting solution builds on this configuration. Third-party apps can customize every button in the approval action area on the details page. Configure two additional callback APIs:

  - CUSTOM_ACTION_DEFINITION: DingTalk calls back the third-party app to get the button definitions for the action area (button rendering).
  - CUSTOM_ACTION_APPLY: DingTalk calls back the third-party API to receive and process approval actions that users submit (approval operation).

  ```text
  "featureConfig":{
    "features":  [
      {
        // Callback URL for getting action area (button) data (button rendering)
        "name":"CUSTOM_ACTION_DEFINITION",  
        "runType":"OUTBIZ_CUSTOM",
        "callback":{
          "apiKey":"customActionDefinitionApiKey",
          "appUuid":"appUuid",
          "version":"1"
        }
      },
      {
        // Callback URL invoked when an approval action is performed (approval operation)
        "name":"CUSTOM_ACTION_APPLY",  
        "runType":"OUTBIZ_CUSTOM",
        "callback":{
          "apiKey":"customActionApplyApiKey",
          "appUuid":"appUuid",
          "version":"1"
        }
      }
    ]
  }
  ```

  - **Details Page Action Area Button Categories**

    - ##### **General Buttons**

      The DingTalk OA Approval form details page hosting platform provides these buttons by default. Reuse them directly. The integrating party does not need to return any data for them. The default implementation defines their interactions. The business side can configure whether each button appears.

      |  |  |  |  |
      | --- | --- | --- | --- |
      | Button ID [actionType] | Capability | Interaction Type | Description |
      | INSTANCE_SHARE | Share the Approval form to a Group Chat | Click to open the group selector. The callback runs after confirmation. | The default implementation defines the interaction. The business side can configure whether the button appears. |
      | INSTANCE_DOWNLOAD | Download the Approval form. DingTalk sends the file through Work Notifications. | Click to run the callback and display a prompt. | The default implementation defines the interaction. The business side can configure whether the button appears. |
      | INSTANCE_PRINT | Print the Approval form | Click to open a button group. | The default implementation defines the interaction. The business side can configure whether the button appears. |
      | INSTANCE_DING | Reminder: the approval process initiator sends a reminder to the approver of the current node | Click to open the DING component. | The default implementation defines the interaction. The business side can configure whether the button appears. |
      | INSTANCE_IM_GROUP | Create a group discussion based on the instance | Click to open the user picker. A confirmation dialog appears after selection. | The default implementation defines the interaction. The business side can configure whether the button appears. |
      | INSTANCE_COMMENT | Comment on the Approval form | Click to open a comment confirmation dialog. | The default implementation defines the interaction. The business side can configure whether the button appears. |
    - ##### **Predefined Buttons**

      Form hosting presets these approval action buttons and implements common interaction mechanisms for them automatically. The business side passes these buttons as needed, based on the current process and users. The integrating party implements the actual capabilities, so behavior may differ slightly across process engines.

      |  |  |  |
      | --- | --- | --- |
      | Button ID [actionType] | Capability | Description |
      | TASK_APPROVE | Accept the approval task | Fixed interaction. Button text and callback logic are customizable. |
      | TASK_REJECT | Decline the approval task | Fixed interaction. Button text and callback logic are customizable. |
      | TASK_FORWARD | Transfer the approval task | Fixed interaction. Button text, selectable user list, and callback logic are customizable. |
      | TASK_APPEND | Sign request | Fixed interaction. Button text, selectable approvers for the sign request, sign request method, and callback logic are customizable. |
      | INSTANCE_REVERT | Return | Fixed interaction. Button text, list of nodes to return to, and callback logic are customizable. |
      | INSTANCE_MODIFY | Modify the Approval form | Fixed interaction. Button text, grayed-out state, gray-out reason, and similar properties are customizable. |
      | INSTANCE_TERMINATE | Undo the Approval form | Fixed interaction. Button text, confirmation prompt text, and callback logic are customizable. |
      | INSTANCE_DELETE | Delete the Approval form | Fixed interaction. Button text, confirmation prompt text, and callback logic are customizable. |
      | INSTANCE_EXTERNAL_DETAIL | Back to original form: displays a button on the approval details page that opens the external details page | Fixed interaction. Button text and visibility are customizable. |
    - ##### **Custom Business Buttons**

      The integrating third-party system defines these buttons. Apply a simple configuration to give them a style similar to predefined buttons. When a user clicks one of these buttons, DingTalk calls back the integrating party's system through the approval operation API. That system then runs the custom action logic.

      |  |  |  |  |
      | --- | --- | --- | --- |
      | Button ID [actionType] | Capability | Interaction Type | Description |
      | CUSTOM_ACTION_xxx | Custom business button | Standard interaction types the platform supports:  - link: redirect directly - confirm: confirmation dialog - modal: open a dialog (the business side can customize the components in the dialog) | Must not match any ID that the hosting platform reserves. |
  - **Button Sorting and Rendering Rules**

    By default, the hosting platform sorts and formats the buttons that the integrating party passes.

    - The hosting platform checks whether to add general buttons and adds them if needed.
    - DingTalk calls back the third-party app to get the button definitions for the action area (button rendering). It then renders the buttons from the returned data. If the callback returns an error, DingTalk falls back to the existing buttons of the ORIGIN hosting solution: Share, Download, Print, Accept, Decline, Comments, Create group discussion, Delete, and Back to original form.
    - Sorting of all buttons:

      - General buttons appear first, in a fixed order.
      - Predefined buttons and custom buttons follow, in the order they are passed.

### Step 5: Update the Process Center Approval Task Status

**Accept or decline approval tasks with custom logic:** An approver opens the custom approval page in DingTalk and selects an action such as Accept or Decline. DingTalk then calls the callback API configured in the `CUSTOM_ACTION_APPLY` module of Save Process Center External Integration Approval Template. After the third-party app runs its business logic, it must sync the task status to DingTalk. To update the status of its own approval To-Do items, call the [Update Process Center Task Status](/open/development/update-process-center-task-status) API with the approval instance ID `processInstanceId` and the approval To-Do task ID `taskId`.

In scenarios such as OR-sign, call the [Cancel Multiple Process Center Pending Tasks](/open/development/cancel-multiple-oa-approval-tasks) API. This API sets all running To-Do items under an approval instance to CANCELED in one batch.

```json
{
  "processInstanceId": "qZpLKAxxxx43810",
  "tasks": [
    {
      "taskId": 88094338042,
      "status": "COMPLETED",
      "result": "AGREE"
    }
  ]
}
```
