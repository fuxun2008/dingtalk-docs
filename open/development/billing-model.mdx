This article introduces the billing model of the App Development Platform.

The App Development Platform provides enterprise developers with multiple app types and rich app capabilities to support enterprise digital transformation. The Open API usage consumed by internal app development is metered, and the use of Webhook and Stream messaging by event subscription and Custom bots is billed.

## **Metering Rules**

- Failed calls caused by single-app QPS rate limits, global API QPS rate limits, network unreachability, and similar reasons are not counted toward the call count.
- Basic Open APIs are not billed. For details, see Appendix A: List of APIs Not Included in the Monthly Call Count Limit.
- Basic event subscriptions are not billed. For details, see Appendix B: List of Events Not Included in the Webhook and Stream Usage Limit.

## **Usage Recommendations**

To call DingTalk API endpoints more efficiently and reasonably, pay attention to the following points:

1. **Optimize the API call logic**: For example, if an API reads DingTalk data, avoid calling it on a loop timer (polling). If needed, integrate DingTalk callback notifications to effectively reduce the call count and better ensure data timeliness.
2. **Check the API error code**: For example, when an API call returns an error, determine the cause based on the error code. Do not retry indefinitely, and control the number of retries.
3. For app-level QPS rate limits on APIs, see Appendix C: How to Handle Rate Limiting on the DingTalk Server API.

To use the DingTalk Webhook and Stream messaging channel more efficiently and reasonably, pay attention to the following:

1. **Optimize your event subscription solution by following these principles**: Subscribe only to necessary events, deduplicate event handling, and respond and return quickly. For details, see Appendix D: Recommendations for Rational Use of Resources.
