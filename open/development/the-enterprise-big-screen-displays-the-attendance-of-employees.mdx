# Attendance Data Visualization: Real-Time On-Duty Monitoring and Anomaly Alerts

## Overview

This solution displays employee attendance on an enterprise dashboard from end to end. It uses the Stream push mechanism and attendance APIs of the DingTalk Open Platform to collect data in real time, determine statuses automatically, and output standardized data.

### Background

Organizations need real-time visibility into employee attendance. This is especially true in manufacturing workshops, customer service centers, and retail stores, where managers rely on a dashboard to view key metrics such as current on-duty headcount, late arrivals, and absences. However, native DingTalk attendance data resides in the admin console and cannot connect directly to an organization's own dashboard system. This causes the following problems:

- **Delayed data access**: HR must export attendance reports manually, so updates cannot happen in seconds.
- **Difficult system integration**: Without standardized APIs, embedding attendance data into in-house BI or dashboard systems is difficult.
- **Complex status determination**: Clock-in times alone cannot determine "Normal/Late/Absent." Staff must compare them against scheduling rules manually.
- **Monitoring blind spots**: Abnormal clock-ins, such as clock-ins from unexpected locations or buddy punching, cannot trigger real-time alerts.

### Key Benefits

This solution collects and analyzes attendance data in real time. It replaces manually exported offline data with an API-driven real-time stream, which significantly improves decision-making efficiency and data transparency.

- **Real-time data collection**: The Stream push mechanism sends a callback to your server within milliseconds of each clock-in, keeping data in sync with no noticeable latency.
- **Automatic status determination**: Clock-in times are automatically compared against scheduling rules to accurately identify statuses such as "Normal/Late/Early Leave/Absent."
- **Standardized API output**: A unified RESTful API integrates seamlessly with dashboards, BI systems, and OA Kanban boards.
- **Full historical tracking**: Batch queries of historical attendance records support monthly statistics, trend analysis, and other in-depth needs.

### Use Cases

This solution applies to the following business scenarios:

- **Manufacturing workshop dashboards**: Display on-duty headcount, absence rates, and late arrival alerts for each production line in real time to support production scheduling.
- **Customer service center monitoring**: Monitor agent attendance to ensure adequate staffing and reallocate resources promptly.
- **Retail store management**: Monitor employee clock-in status across stores to align scheduling with customer traffic.
- **Headquarters command centers**: Aggregate group-wide attendance data to support cross-region comparisons and anomaly alerts.

## Implementation Guide

### Technical Architecture

This solution uses the Server APIs and Stream push mechanism of the DingTalk Open Platform. The core technical components are:

- **Authentication layer**: Use the `Client ID` and `Client Secret` to get an `access_token` and secure API calls.
- **Real-time data ingestion layer**: Configure Stream push to subscribe to attendance clock-in events and receive callbacks on your server within milliseconds.
- **Status determination engine**: A local algorithm compares clock-in times with scheduling rules and identifies "Normal/Late/Seriously Late/Absent" statuses automatically.
- **Data storage and caching**: Attendance group scheduling rules are fully synced every hour. Clock-in records are written to the database and cached in real time.
- **Standardized API output layer**: RESTful APIs serve dashboards and BI systems, with support for multi-dimensional filtering and aggregate queries.

Data flow: An employee clocks in on the DingTalk App → Stream pushes a real-time callback → The enterprise server receives the data and determines the status → The data is written to the database and cached → The dashboard API returns the data.

   ```text
   public String determineAttendanceStatus(String userId, String groupId, String checkTime) {
       // 1. Get the scheduling rule for this attendance group from the cache
       ScheduleRule rule = cache.getScheduleRule(groupId);

       // 2. Parse the clock-in time
       LocalDateTime punchTime = LocalDateTime.parse(checkTime, formatter);

       // 3. Compare against the scheduled time
       if (punchTime.isBefore(rule.getStartTime().plusMinutes(rule.getLateThreshold()))) {
           return "Normal";  // On-time clock-in
       } else if (punchTime.isBefore(rule.getStartTime().plusMinutes(rule.getSeriousLateThreshold()))) {
           return "Late";    // Late arrival
       } else {
           return "SeriousLate";  // Seriously late
       }
   }
   ```

   | **Condition** | **Returned Status** | **Dashboard Color** |

   | Scheduled start time + Late threshold &lt; Clock-in time ≤ Serious late threshold | Late | 🟡 Yellow |
   | Clock-in time > Serious late threshold | SeriousLate (Seriously late) | 🔴 Red |

## FAQ

- **Q1: What is the difference between Stream push and polling?**

  A: The two methods retrieve data in completely different ways:

  - **Polling**: Your server calls the API on a schedule to query clock-in records. This introduces latency (typically 5–15 minutes), and frequent calls can easily trigger rate limits.
  - **Stream push**: DingTalk pushes data to your specified URL as soon as an employee clocks in. Latency is &lt;1 second, and no active queries are needed. This method suits real-time dashboards.

  **Key difference**: Stream push is event-driven and pushes data only when needed. Polling is schedule-driven and calls the API whether or not new data exists. Use Stream push whenever possible.
- **Q2: How do I determine whether an employee is "late" or "absent"?**

  A: Apply the following logic:

  - **Late arrival**: The employee has a clock-in record, but the clock-in time is later than the scheduled start time plus the late threshold (typically 10–30 minutes, configurable in the attendance group settings).
  - **Absent**: As of the current time (for example, 3:00 PM), the employee has no clock-in record for the day, and the scheduling rules require the employee to work today.

  **Note**: Always check the scheduling rules. If the employee has a scheduled day off, no clock-in does not count as an absence.
- **Q3: How do I handle clock-ins from unexpected locations or buddy punching?**

  A: The DingTalk attendance event callback includes the `LocationResult` field, which indicates whether the clock-in location is valid:

  - `Normal`: The clock-in location is within the range allowed by the attendance group.
  - `Outside`: The clock-in location is outside the allowed range, which suggests a clock-in from an unexpected location.

  **Handling strategy**:

  - Mark records with `LocationResult=Abnormal` as orange warnings on the dashboard.
  - Generate a daily report of abnormal clock-ins and send it to HR Admins for review.
  - Combine multi-factor verification, such as Wi-Fi and location, to reduce the risk of buddy punching.
- **Q4: How often should the dashboard refresh?**

  A: It depends on the business scenario:

  - **Manufacturing workshops/customer service centers**: Refresh every 1–5 seconds to ensure real-time visibility.
  - **Retail stores**: Refresh every 30 seconds to 1 minute to balance performance and timeliness.
  - **Headquarters command centers**: Refresh every 5–10 minutes, focusing on trend analysis rather than second-by-second monitoring.

  **Performance optimization**: Use incremental updates that push only changed data (such as new clock-in records) instead of full refreshes. This can reduce network overhead by more than 90%.
