## Prerequisites

- You are familiar with the basic concepts of the DingTalk Open Platform. For more information, see [Basic concepts](/open/dingstart/basic-concepts-beta).
- You are familiar with the app types on the DingTalk Open Platform. For more information, see the app type overview.
- If you encounter issues during development, submit a ticket through Technical Support.
- Before you start, obtain developer permissions to become a DingTalk developer.

## Create and configure an app

### Create an app

After you create an app, you can obtain its basic credentials and configure developers and API permissions.

To create a Third-party personal mini program app, follow these steps:

1. Sign in to the [DingTalk Developer Console](https://open-dev.dingtalk.io/).

### Note

   Only admins and sub admins can sign in to the Developer Console.
2. On the **App Development** page, select **Third-party personal app**, and then click **Create app**.

3. Enter the basic information of the app, and then click **Confirm creation**.

4. Click **Credentials and basic information** to obtain the AppId and App Secret of the app.

### User management

On the **User management** page, add developers and test users.

- When a mini program is created, its creator is automatically added as a developer. If multiple developers work on the app, the admin can add developers to the app by phone number. After being added, a developer can use the developer tools to build the app.
- Only users added as test users can use the test version of the mini program.

### Monitoring Center

On the **Monitoring Center** page, enable monitoring and configure the stability owner settings.

### Security Center

On the **Security Center** page, add HTTP security domains and webview security domains.

- HTTP security domains:

  For a mini program that requires network communication between the front end and the server, configure one or more server security domains (or IP addresses) in advance. The front end can only communicate with the server through the configured security domains (or IP addresses).

  When the security domains are updated, repackage and upload the mini program in the developer tools for the new domains to take effect.

  Essentially, the network communication between the front end and the back end of a mini program is the same as that of a regular H5 application. For a quick test, enter any domain or IP address that the front-end environment of the mini program can access, such as the local address of your office computer or a LAN address.
- Webview security domains:

  When the mini program uses the webview component to embed H5 pages, add the H5 page domains to the webview security domains.

## Silent login

With the capabilities provided by the DingTalk Open Platform, users can quickly complete identity verification without entering their account and password.

### Scope and limitations

This feature applies to the following scenarios:

- App type: **Third-party personal app**
- Runtime environment: **Mini program** only
- Authentication method: An authorization mechanism based on a temporary authorization code (authCode)

### Process overview

#### The front end initiates authorization and obtains the authCode

After a user opens the E mini program, the front end initiates an authorization request through the JSAPI provided by the DingTalk client to obtain a temporary authorization code (authCode) for silent login, and then sends the code to the app back end. This is typically done by calling the `dd.getAuthCode` API.

> **Key terms**: The `authCode` is a temporary authorization code obtained through a DingTalk client JSAPI such as `dd.getAuthCode`. It has a short validity period and can be used only once to exchange for the user's basic information on the back end.

#### The server calls the API to obtain user information

After the app back end receives the `authCode`, it calls the DingTalk server API `sns/getuserinfo_bycode` to obtain the user's basic information and complete the sign-in process.

### Note

- A per-minute rate limit applies. Control the request frequency accordingly.
- We recommend that you implement a retry mechanism and logging for error scenarios.

### Sample code

#### Front-end sample

```text
dd.getAuthCode({
    success: function(res) {
        const authCode = res.authCode;
        // Send the authCode to the app back end
    },
    fail: function(err) {
        console.error('Failed to get authCode', err);
    }
});
```

#### Server-side sample

After the call succeeds, the API returns user information including the `nick` (name), `openid`, and `unionid` fields.

```java
/**
 * Quickstart sample code
 * Implements the simplest Personal Account authentication.
 */
@RestController
public class IndexController {
    private static final Logger bizLogger = LoggerFactory.getLogger(IndexController.class);

    /**
     * Welcome page
     */
    @RequestMapping(value = "/welcome", method = RequestMethod.GET)
    public String welcome() {
        return "welcome";
    }

    /**
     * DingTalk user sign-in. Displays basic information of the current user.
     * @param authCode Temporary authorization code obtained by the JSAPI in the E app front end.
     */
    @RequestMapping(value = "/login", method = RequestMethod.POST)
    @ResponseBody
    public Object login(@RequestParam(value = "authCode") String authCode) {
        Long start = System.currentTimeMillis();
        ServiceResult serviceResult;
        try {
            DefaultDingTalkClient  client = new DefaultDingTalkClient(URL_GET_USERINFO_BY_CODE);
            OapiSnsGetuserinfoBycodeRequest req = new OapiSnsGetuserinfoBycodeRequest();
            req.setTmpAuthCode(authCode);
            OapiSnsGetuserinfoBycodeResponse response = client.execute(req,Constant.APP_ID,Constant.APP_SECRET);
            serviceResult = ServiceResult.success(response.getUserInfo());
            return serviceResult;
        } catch (Exception e) {
            bizLogger.error("loginFailed,authCode"+authCode,e);
            serviceResult = ServiceResult.failure("-1",e.getMessage());
            // Return the result
        }
        bizLogger.info("cost:"+(System.currentTimeMillis()-start));
        return serviceResult;
    }
}
```

### Caching recommendations

To improve user experience and reduce duplicate requests, manage the user's sign-in state through local caching:

- Use `dd.setStorage` to store the user information and timestamp on the client.
- When the user opens the page next time, read from the cache first.
- We recommend setting the cache validity period to 2 hours to avoid keeping an invalid sign-in state for an extended period.

### FAQ

- **Q: What are the common reasons for failing to obtain the authCode?**

  A: Common causes include not importing dd-sdk-js correctly, network errors, or not opening the page in the DingTalk client.
- **Q: The user information API returns errcode=40001. Why?**

  A: This indicates that the credential is invalid. Check whether the parameters are correct and whether the authCode has expired.
- **Q: Is silent login supported on PC?**

  A: This solution mainly applies to mini programs on mobile. For PC, use Scan QR Code sign-in or another authentication method.

## Send messages

Developers can use messages to reach users efficiently and notify them of the results and statuses of their actions. A message can be configured with an in-app redirect page. When the user views the message and clicks "Open app to view", the user is redirected to the page specified by the developer. For implementation details, see the development process in this document.

Before you start development, prepare the following:

- Obtain the **AppId** and **App Secret** from **Basic information > App information** to authenticate subsequent API calls.
- Make sure that the client-side mini program is released and the form submission can run on a real device.

### Limitations

- **Supported app type**: Third-party personal app
- **formId validity period**: The formId is a temporary authorization code that is valid for 7 days. After it expires, it can no longer be used to send messages.
- **Push frequency rule**: For each form submission, you can push one message to the user within 7 days. Multiple submissions allow multiple messages.

### Development process

1. Declare the `report-submit="true"` attribute on the form submitted by the user.

### Note

   This attribute takes effect only on a real device.

   ```xml lines
   <form onSubmit="formSubmit"  report-submit="true">
     <view class="section section_gap">
       <view class="section__title">Form type</view>
       <input name="text" maxlength="10" placeholder="Maximum length: 10" />
     </view>
     <view class="btn-area">
       <button formType="submit">Push message</button>
     </view>
   </form>
   ```
2. In the `onSubmit` event, obtain the temporary authorization code (code) required for pushing messages through `e.detail.formId`, and send the code to the developer server for storage.

   ```text lines
   formSubmit(e){
       // Get the temporary authorization code from e.detail.formId for pushing messages
       dd.httpRequest({
                           url: 'http://your-form-submit-server-url?code='+e.detail.formId,
                           method: 'POST',
                           headers:{"Content-Type":"application/json"},
                           data: { 
                           },
                           dataType: 'json',
                           success: function(res) {
                               if(res.data.success){
                                   dd.alert({content:'Form submission processed successfully'});
                               }else{
                                   dd.alert({title:"Form submission processing failed",
                                           content:JSON.stringify(res)});
                               }                            
                           },
                           fail: function(res) {
                                dd.alert({content: 'Form submission processing'});
                           }
                       });
       }
   ```
3. When your business needs to push a message to the user, call the message push API provided by DingTalk on the server and use the previously obtained code to send the message.

   ```java lines
   public static String sendMsg() throws RuntimeException {
       try {
           DefaultDingTalkClient  client = new DefaultDingTalkClient("https://oapi.dingtalk.io/sns/send_msg");
           OapiSnsSendMsgRequest req = new OapiSnsSendMsgRequest();
           req.setCode(code);
           OapiSnsSendMsgRequest.Eapp eapp = new OapiSnsSendMsgRequest.Eapp();
           eapp.setImg("@lALPBY0V5EuR4oDNAcrNAs4");
           eapp.setContent("Thank you very much for your feedback. \n\n"+System.currentTimeMillis());
           eapp.setTitle("Ticket replied");
           eapp.setLink("eapp://page/index?param=aaa");
           OapiSnsSendMsgRequest.Msg msg = new OapiSnsSendMsgRequest.Msg();
           msg.setMsgtype("eapp");
           msg.setEapp(eapp);
           req.setMsg(msg);
           OapiSnsSendMsgResponse response = client.execute(req,Constant.APP_ID,Constant.APP_SECRET)
       } catch (ApiException e) {
           bizLogger.error("sendMsg failed", e);
           throw new RuntimeException();
       }

   }
   ```

## Publish the app

After app development is complete, invite test users to try out the app. Once testing is complete, submit the app for review. After the review is approved, you can release the app.

### Test version

To make it easier for developers to try out and test a version they have developed, the Developer Console lets you set a development version as a test version without product release review. After the setting succeeds, test users can scan the QR Code to use this version. Follow these steps:

1. Add test users in User settings.
2. In Version management, select a development version and set it as the test version.

3. Have the test users scan the test QR Code to start the trial.

### Submit for review

Before a product is officially released, submit it for review. For the first release of an app, the DingTalk team reviews the product. After the review is approved, DingTalk users can open and use the app in DingTalk.

### Canary testing

After the review is approved, the developer can click "Canary" to start canary release of the version. After the new version enters the canary testing stage, the developer can increase the canary ratio. The canary ratio can only be increased and cannot be decreased. If defects are found during canary testing, the developer can choose not to release this version of the app.

### Release a version

After canary testing, the developer clicks **Release** to publish the app online. Users can open the app by scanning the QR Code or via a shared link, and all DingTalk users can use this version of the app.

### Note

- The DingTalk organization must complete Premium authentication.
- The DingTalk organization must complete onboarding as a product solution provider.

1. Click the app to be released, click **Version management**, and select the version to submit for review.

2. Click **Submit for review**.

### Note

   If DingTalk organization authentication and service provider authentication are not completed, you are prompted to complete them first. Follow the prompts in the Developer Console, or refer to the end-to-end partnership guide.
3. On the product review page, perform a security scan and product review in sequence.

   1. Click **Click to enter** under Security scan to scan the submitted app for security issues. The security scan report is displayed.
   2. View the product review standards. You can view the product design specifications for Third-party personal apps in the product design specifications.
   3. Click **Click to enter** under Submit for review to submit the app for review.
